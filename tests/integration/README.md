# Интеграционные проверки

Код против настоящих Postgres, Keycloak, Kafka, Redis и Centrifugo. Не
модульные тесты с подменами: здесь проверяется то, чего не видно в коде —
условия в SQL, права, порядок шагов и поведение при отказе.

```bash
make integration        # все проверки
make send-message       # отправка и получение сообщения
make local-test         # всё вместе: контракты, линтер, юниты, связность, интеграция
```

Одну проверку:

```bash
INTEGRATION_ONLY=relay_check.py scripts/integration-messenger.sh
```

## Как устроен запуск

Проверки выполняются **внутри кластера**, а не на машине разработчика.
Иначе пришлось бы пробрасывать порты к базе, брокеру и Keycloak, и путь
получился бы не тот, каким ходит сервис.

```
scripts/integration-messenger.sh
  ├── берёт образ из верхнеуровневого image в values.yaml
  │     ↳ тот же, что крутится в кластере: проверяется то содержимое,
  │       которое поедет дальше, а не рабочая копия
  ├── кладёт tests/integration/*.py и run.sh в ConfigMap
  ├── копирует секрет администратора Keycloak в namespace messenger
  │     ↳ секреты через границу namespace не видны; копия временная,
  │       значения переносятся в base64 через stdin, а не аргументом
  ├── поднимает под integration-<timestamp>
  │     ↳ те же переменные и те же права, что у сервиса: пароль базы
  │       от роли приложения, а не от суперпользователя — отказ по правам
  │       обязан находиться здесь, а не в проде
  │     ↳ метка finops.internal/component: test снимает вывод со сбора
  │       журналов: он для человека в терминале, а не для хранилища
  └── по завершении trap сносит под, ConfigMap и секрет
```

Код возврата берётся **из статуса пода**, а не из `kubectl logs`: журнал
печатается одинаково и при успехе, и при провале.

`run.sh` внутри пода перебирает файлы по алфавиту, поэтому порядок проверок —
алфавитный, а не порядок их появления.

## `make send-message` подробно

Две проверки подряд. Первая доводит сообщение до потоков Kafka, вторая —
до получателя в канале беседы.

### Путь сообщения

```
A ──POST /conversations/{id}/messages──► API
                                          │ одна транзакция:
                                          │ message + событие факта + событие содержимого
                                          ▼
                                       outbox
                                          │ аренда → публикация → отметка
                                   outbox-relay
                                          ├─► messenger.events.v1   факт: кто, когда, seq
                                          └─► messenger.content.v1  текст
                                                     │
                                          consumer-realtime
                                          │ собирает пару по message_id в Redis,
                                          │ отмечает «отдано» до публикации
                                          ▼
                                      Centrifugo  publish в conversation:{id}
                                          │
                                          ▼
                                          B  WebSocket
```

### `realtime_receive_check` — получение

1. Два пользователя заводятся через административное API Keycloak.
2. Оба входят **через настоящую страницу входа**: запрос формы, отправка
   пароля, перехват кода из перенаправления, обмен через `POST /auth/callback`.
3. A создаёт беседу.
4. B запрашивает `POST /realtime/token` — **после** создания беседы: каналы
   перечисляются на момент выдачи, и в более раннем токене этой беседы нет.
5. B открывает WebSocket и проходит connect-proxy.
6. Попытка подписаться вручную получает `already subscribed` — это
   подтверждение, а не отказ: сервер подписал клиента сам по списку из
   токена. Клиент не выбирает канал, иначе подписка на чужую беседу
   сводится к знанию её идентификатора.
7. A отправляет сообщение, ожидается `201`.
8. Проверка ждёт публикацию в сокете, **пропуская служебные кадры**:
   принять пинг за сообщение значило бы зелёный результат на пустом месте.
9. Сверяются текст, `seq`, отправитель — и то, что `recipient_ids` наружу
   не ушёл: иначе каждый участник узнаёт полный список получателей чужого
   сообщения.
10. **Условие выхода гейта.** У записей outbox снимается `published_at`,
    и настоящий отправитель публикует их в Kafka второй раз — так выглядит
    его смерть между публикацией и отметкой. Повтор не подделывается.
11. Проверка убеждается, что второго сообщения у B нет.

### `send_message_check` — отправка

Три участника: автор, получатель, посторонний.

| Случай | Ожидание |
| --- | --- |
| приём | `201`, `seq = 1`, поля контракта, текст вернулся как отправлен |
| повтор того же `client_message_id` | `200`, тот же `message_id` и `seq` |
| второй участник | `201`, `seq = 2` |
| посторонний | `404`, а не `403` |
| текст свыше предела | `413` |
| без токена | `401` |

Затем проверка ждёт, пока **опустеет очередь outbox** — ждёт именно
опустошения, а не появления записей в Kafka: очередь это то, за что
отвечает наша сторона, и её непустота через двадцать секунд означает
отказ доставки, а не медленный брокер. И только потом сверяет, что конец
лога вырос ровно на два в каждом топике.

### Ручной режим

```bash
KEEP_ACCOUNTS=1 make send-message
```

Первая проверка не убирает за собой и печатает беседу, логин с паролем,
токен и готовую строку `curl`. Токен живёт пять минут, логин с паролем —
постоянные. API наружу не опубликован, поэтому нужен проброс порта:

```bash
kubectl port-forward -n messenger svc/api 18080:80
```

### Чего `make send-message` не доказывает

- **Историю.** `GET /conversations/{id}/messages` ещё не существует — это G3.
  Доказано, что сообщение доходит до открытого сокета, а не что его увидит
  тот, кто подключится позже.
- **Порядок между топиками.** Факт и содержимое собираются по `message_id`,
  а не по времени прихода.
- **Офлайн-получателя.** Web Push — это G4.
- **Путь снаружи.** Проверка идёт изнутри кластера; шлюз и снятие префикса
  `/api/v1` не задействованы — API наружу пока не опубликован.

## Правила для новых проверок

Каждое из них появилось после того, как его отсутствие стоило зелёного
результата на неработающем коде.

**Убирать за собой при любом исходе.** Уборка внутри успешной ветки — это
уборка, которой не будет ровно тогда, когда она нужна: первый же отказ
оставил профиль в настоящей базе, и нашлось это не проверкой, а взглядом
в таблицу. Порядок удаления учитывает внешние ключи: соединения реального
времени ссылаются на сессии, сессии на пользователей.

**Не верить коду возврата команды.** `kafka-console-producer` возвращает
ноль и когда не ушло ни одной записи. Если действие можно измерить —
измеряйте: смещение, строка в базе, публикация в сокете.

**Латиница в заголовках и cookie.** Они кодируются в latin-1, и кириллица
в значении роняет запрос, не дойдя до сервера. Настоящие токены — base64url,
то есть ASCII.

**Ходить тем же путём, что сервис.** Через PgBouncer, а не в primary; от роли
приложения, а не от суперпользователя; через развёрнутый API, а не через
ASGI в том же процессе — если проверяется маршрут, а не функция.

**Пропускать служебные кадры и пустые ответы.** Зелёный результат,
полученный на пинге или на пустом списке, хуже красного.

**Одноразовые поды помечать `finops.internal/component: test`** — иначе их
вывод попадает в хранилище журналов, а имя с отметкой времени заводит
новый поток на каждый прогон.
