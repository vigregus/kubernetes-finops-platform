# Браузерная приёмка веб-клиента (G3-005, G3-006)

Здесь проверяется то, чего не покажет ни один модульный тест: `web` поднят в
кластере, вход через настоящий Keycloak работает, список бесед приходит от API, а
после перезагрузки состояние восстанавливается. Проверка идёт **с хоста и против
стенда** — только публичные имена, ни одного обращения внутрь кластера и ни одного
туннеля к нему. Смысл именно в этом: край, Keycloak, cookie и origin должны сойтись
снаружи, тем же путём, которым пойдёт браузер.

Две приёмки делят одну подготовку и один вход, но не одну спеку: `acceptance` —
это G3-005, `g3-006` — сон вкладки, обнаружение пропуска и синхронизация. Логика
входа и заголовков живёт в `support/auth.ts` **в одном экземпляре**: разошедшаяся
копия означала бы, что приёмка проверяет не тот вход, которым ходят люди. В этом
модуле нет `test()` верхнего уровня, и это несущее свойство: модуль с `test()`,
импортированный спекой, был бы собран в проект спеки — то есть подготовка
побежала бы второй раз, внутри приёмки.

## Как запускать

```bash
make web-e2e            # единственный вход приёмки
```

Цель запускает `scripts/web-e2e-fixture.sh`, и `npx playwright test` — **дочерний
процесс того же shell**. Это не деталь реализации, а условие исполнимости контракта
о паролях: пароль живёт в окружении процесса, и второй `make` окружения первого не
унаследует, а его `finally`-уборка завершится раньше, чем начнётся тест. Один
процесс — единственная форма, в которой уборка вообще что-то убирает.

```bash
make web-e2e-fixture    # диагностическая цель: завести фикстуры и показать их состояние
```

Диагностическая цель **не** является шагом приёмки и в отчёте называется так же.

## Фазы оркестратора

```
preflight   статические инварианты, доступность стенда, уборка остатков убитого прогона
generate    новые пароли на прогон
set         пароли в Keycloak через Admin API (там же заводятся учётные записи)
export      E2E_* в окружение процесса
setup       фикстуры, device_id, идемпотентная беседа      ← проект fixture
run         приёмка                                        ← проекты acceptance и g3-006
finally     logout в Keycloak → две таблицы одной транзакцией → четыре нуля
```

Оба проекта приёмок объявляют `fixture` своей зависимостью, поэтому порядок задан
раннером. `fixture.setup.ts` спекой **не импортируется**: модуль с `test()` верхнего
уровня, импортированный из спеки, был бы собран в её проект — то есть подготовка
побежала бы второй раз, внутри приёмки. У `g3-006` свой бюджет времени
(`timeout: 600_000`): сценарий отправляет 101 сообщение штатным путём и ждёт барьер
публикации — это минуты, и общий таймаут пришлось бы поднимать для обеих спек сразу,
ослабив G3-005.

## Что именно проверяется

Сценарий сформулирован на публичных именах и одном прогоне:

1. у нового посетителя просят вход, и это не «сессия истекла» — cookie у него нет
   вовсе, и говорить об истечении было бы утверждением о сессии, которой не было;
2. кнопка входа уводит на **настоящий** Keycloak: сверяются origin, путь
   авторизации, `client_id` и `redirect_uri`;
3. `POST /auth/callback` отвечает `200`; следом приложение само зовёт `GET /me` и
   `GET /conversations` — оба `200`, и `/me` отдаёт `user_id` той самой учётной
   записи, а `/conversations` — беседу, заведённую подготовкой этого прогона;
4. в сайдбаре есть строка `[data-conversation-id="<id из подготовки>"]`;
5. перезагрузка восстанавливает состояние по refresh-cookie и **не** уводит в
   Keycloak.

**Беседа ищется по атрибуту, а не по имени.** Имя — строка, которую фикстура могла
бы совпасть со стендовыми данными случайно; идентификатор известен только текущему
прогону и получен из API. Атрибут `data-conversation-id` несёт сама строка списка —
это требование к компоненту, а не подпорка под тест.

## G3-006: сон вкладки, обнаружение пропуска, синхронизация

Строка приёмки — «сон вкладки → `recovered=false` → `SYNCING` → догрузка →
`CONNECTED`». Сценарий идёт по `data-connection-state`, `data-sync-reason`,
`data-applied-through-seq`, `data-message-id` и `data-message-seq` — по реальной
разметке продукта, а не по человекочитаемой строке.

```
A и B входят настоящим входом, открывают одну беседу, ждут connected и снимок
A отправляет 1 сообщение штатным путём → B видит его БЕЗ перезагрузки   ← живость
S := B.data-applied-through-seq                       ← S назначается ЗДЕСЬ
contextB.setOffline(true) → B: data-connection-state = "disconnected"
A отправляет 101 сообщение (S+1 … S+101), ответы POST дают expected = [{message_id, seq}]
БАРЬЕР: у A состояние всё время "connected", "syncing" не наблюдался,
        все 101 expected в ленте, data-applied-through-seq = S+101
contextB.setOffline(false) → B: connecting → syncing(recovery-miss) → connected
лента монотонна по seq, уникальна по message_id, burst сверен с expected
```

### Офлайн задаётся `setOffline`, а не заморозкой вкладки

`Page.setWebLifecycleState("frozen")` останавливает таймеры и в пределе приводит к
потере WebSocket по пингу, но `navigator.onLine` при этом не обязан стать `false`, а
событие `offline` не наступает вовсе. Значит заморозка **не предъявляет** тот
production-вход, который введён для `DISCONNECTED`, и сценарий на ней доказывал бы
пустоту. Уход в офлайн делается `contextB.setOffline(true)` — тем же классом события
(связи нет достаточно долго, чтобы позиция стала недостижимой), — и подтверждается
**наблюдаемым** переходом: сценарий ждёт `disconnected` и падает громко, если перехода
не произошло. Литеральной заморозки вкладки сценарий не воспроизводит и не заявляет.

### Почему 101 сообщение

`history_size: 100` (`channels.json`) — окно восстановления канала. Сто одна
публикация делает прежнюю позицию невосстановимой **гарантированно**, а не «вероятно»:
при ста самая старая сохранённая публикация равна `S+1`, и восстановление проходит
целиком (`recovered=true`, `SYNCING` не наступает). Поэтому сценарий с сотней
сообщений обязан **краснеть** на утверждении перехода — иначе число выбрано наугад.

### Почему свидетель и предмет в разных контекстах

`BrowserContext.setOffline()` гасит **весь** контекст. Общий контекст на двоих погасил
бы вместе с предметом B свидетеля A, и барьер доказывал бы пустоту. Поэтому `A` и `B`
живут в разных `BrowserContext`, а `setOffline` зовётся только на `contextB` — это
проверяется статически в preflight.

Барьер доказывается **положительно**: B не возвращается в сеть, пока A не достиг цели.
Четыре условия сразу — состояние не покидало `connected`, `syncing` не наблюдался, все
101 `expected` `message_id` в ленте, граница равна `S+101` — говорят, что сообщения
прошли publication path, а не что A дочитал их своей догрузкой по REST.

### Переходы читает наблюдатель, а не опрос

`CONNECTING` может жить миллисекунды: `online` → React `connecting` → SDK
`connected`/`subscribed` → `syncing`. Чтение атрибута «когда понадобилось» этого не
доказывает — состояние успевает уехать. Поэтому приёмка ставит `MutationObserver` на
атрибуты продукта (`page.evaluate`, **до** воздействия) и записывает наблюдённые
переходы в массив. Это не test-only шов в production-коде: наблюдатель внедряет сама
приёмка, а читает он реальную разметку.

У B требуется порядок `disconnected → connecting → syncing → connected`
**подпоследовательностью**, а не равенством: между `connected` и `subscribed` React
может отрисовать промежуточный `connected`, и требование точной последовательности
краснело бы на исправном клиенте. У A требуется ровно `["connected"]` — свидетель не
покидал состояние и не входил в `syncing`.

### `S` назначается после live-probe

Проверка живости канала — это **отправленное сообщение**, и оно занимает
`seq = head₀ + 1`. Поэтому `S` читается после того, как B его увидел: иначе burst — это
`S+2 … S+102`, а все утверждения про `S+1 … S+101` неверны на единицу.

### Тождество и порядок — два разных утверждения

«Все `data-message-id` уникальны» верно и тогда, когда конкретное сообщение не доехало
вовсе. Поэтому проверок две: (1) вся лента монотонна по `data-message-seq` и уникальна
по `data-message-id`; (2) burst сверяется с `expected`, собранным из **ответов**
`POST /messages` (`openapi.yaml:812-833` отдаёт и `message_id`, и `seq`) — каждый
`message_id` присутствует ровно один раз, а множество `seq` в диапазоне `[S+1, S+101]`
равно в точности этому диапазону. Отдельно — граница: `data-applied-through-seq ==
S+101`.

### Отправка идёт штатным путём

101 сообщение отправляет A через `POST /api/v1/conversations/{id}/messages`; они
проходят Postgres → outbox → Kafka → consumer-realtime → Centrifugo. Ни одной прямой
публикации в канал: иначе догрузке по REST нечего было бы восстанавливать из source of
truth, а барьеру — нечего подтверждать. `429` контракт объявляет, но текущий обработчик
его на этом пути не применяет, поэтому 101 последовательный POST не конфликтует с
реализацией; любой иной код ответа сценарий называет сразу, а не разбирается с
последствиями в сверке burst.

### `ignoreHTTPSErrors`

`browser.newContext()` не наследует `use` проекта, поэтому доверие к сертификату
стенда задаётся в `signIn` явно. Сертификаты выписаны локальным удостоверяющим центром
стенда — имена при этом настоящие, подмены адреса нет, только доверие к сертификату.

## Уборка

Порядок — часть контракта, а не деталь реализации. Он одинаков в preflight и в
`finally`, и снимает следы в **обоих** источниках:

```
1. закрыть все Playwright contexts/pages
2. POST /admin/realms/messenger/users/<A>/logout и <B>/logout
3. BEGIN
     DELETE FROM realtime_connections WHERE user_id IN (A, B)
     DELETE FROM sessions             WHERE user_id IN (A, B)
   COMMIT
4. чтение нуля: realtime_connections = 0, sessions = 0 (Postgres);
   живых сессий у A = 0, у B = 0 (Keycloak)
```

Первый шаг выполняет тот, кто открыл контексты: подготовка закрывает свои, раннер —
страничный. `realtime_connections` снимается **до** `sessions`, потому что ссылается
на них; обратный порядок нарушает ссылочную целостность. Всё — одной транзакцией и
по закрытому списку ровно двух `user_id`: ни отбора по шаблону имени, ни удаления
без списка. `users` и `conversations` не трогаются никогда.

Четвёртый шаг — не формальность, а то, ради чего всё делается. Без второго источника
вход следующего прогона подхватывает живую сессию Keycloak, и `sessions` растут
снова — уборка была бы полумерой. «Ничего не накапливается» словами не проверяется;
проверяется чтением: четыре числа.

Пароль фикстуры живёт **один прогон**: генерируется перед запуском, ставится через
Admin API, передаётся только переменными окружения. В репозиторий, файл и
Kubernetes Secret он не попадает. В Keycloak при этом остаётся credential, без
которого следующий вход был бы невозможен, и на следующем прогоне он заменяется
новым случайным паролем — «на стенде пароля не остаётся» было бы неправдой.

## Что требуется от стенда

| Что | Откуда берётся |
| --- | --- |
| `messenger-web` в реалме `messenger`, PKCE `S256` | `messenger-keycloak/manifests/realm.yaml`; `redirectUris` уже покрывает `/callback` |
| Учётные записи фикстур `g3-web-e2e-a@…` и `g3-web-e2e-b@…` | создаются подготовкой идемпотентно, `emailVerified: true`, `requiredActions: []` |
| Парольный грант | **не используется**: у `messenger-web` `directAccessGrantsEnabled: false`, поэтому обе стороны проходят настоящий authorization-code login |
| Учётные данные администратора Keycloak | секрет через `kubectl` — чтение секрета, а не сетевой путь в кластер |
| База мессенджера | `kubectl exec` в под Postgres для уборки и чтения счётов |

## Отступления, названные явно

**`tests/e2e/tsconfig.json`.** В репозитории нет корневого `node_modules`, а раннер
ищет `@playwright/test` от файла спеки вверх по дереву каталогов — без карты путей
`npx playwright test --list` падает `Cannot find module '@playwright/test'`. Файл
обязателен и назван отступлением от закрытого списка файлов плана; он же даёт спеке
проверку типов (`tsc -p tests/e2e/tsconfig.json`) и **не** распространяется на
`apps/web` — в `include` только собственные `*.ts`. Ложка `support/*.ts` добавлена
вместе с `support/auth.ts`: `include` не рекурсивен, и помощники входа остались бы вне
проверки типов — то есть новый модуль не проверялся бы вовсе.

**`scripts/web-e2e-fixture.sh`.** Preflight расширен тем же коммитом, что и приёмка
G3-006, и это тоже названо: в `required` добавлены новая спека и `support/auth.ts`,
обход `tests/e2e` переведён с `glob("*.ts")` на `rglob("*.ts")` — иначе помощники
входа выпали бы из проверок `FORBIDDEN` и из запрета на удаление, то есть расширяющий
коммит **ослабил** бы существующую проверку. Добавлены и проверки самой спеки:
наличие `test(`, чтение `data-connection-state`, отсутствие `setWebLifecycleState`,
`setOffline` только на `contextB`, вход обеих сторон через общий `signIn`.

## Что не покрыто

Приёмка не трогает отправку сообщений **из браузера**: её в гейте нет, composer
остаётся проектным запасом. Presence и «печатает» — тоже вне объёма; поэтому ни одно
утверждение о присутствии в интерфейсе не проверяется как факт, а проверяется их
**отсутствие** (в модульных тестах). Отправка сообщения живёт в `make send-message` и
в интеграционных проверках, а в G3-006 с её помощью создаётся лишь фон для приёма.

**Дыра в `seq` живьём не воспроизводится.** У канала один издатель с монотонным
`conversation_seq`, поэтому пропуска в реальности не бывает, а восстановление проигрывает
историю. Детектор пропуска (`MSG-005`) доказывается на редьюсере, а браузером —
**общий путь починки**: `syncing` → `after_seq` → `has_more:false` → `connected` без
дублей. Числа в отчёте берутся из прогона и не переносятся из прошлых гейтов.
