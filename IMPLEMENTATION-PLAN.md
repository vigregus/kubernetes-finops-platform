# Implementation plan

Проектирование закрыто. Этот файл — рабочий, он обновляется по мере закрытия
гейтов; архитектура в нём не пересматривается.

**Источники.** Четыре архитектурных документа описывают систему, пятый —
приёмочную спецификацию (196 тестов в 38 группах), шестой — наблюдаемость
как отдельную плоскость. Все шесть лежат в
[docs/messenger/](docs/messenger/README.md). Здесь — порядок работ.

Реализация идёт **по зависимостям и вертикальным срезам**, а не по разделам
каталога. Порядок «MSG → RT → SEC → HA» был удобен для рассуждения об
архитектуре и непригоден для исполнения: он требует Kafka раньше, чем
существует пользователь.

## Правило готовности

```
требование + приёмочный тест + тест отказа + метрика + инвариант = DONE
```

Пятый пункт — вопрос: *какой инвариант возможность обязана сохранять при
дубликате, повторе, переупорядочивании, устаревших данных и частичном отказе?*
Эти четыре состояния не видны ни на одной схеме и остаются последним классом
дефектов.

**Шестой пункт — наблюдаемость**, и это не отдельный этап, а условие
зелёного цвета каждой возможности:

```
метрика + структурированные журналы + путь трассировки
       + дашборд или запрос + оповещение, если отказ виден пользователю
```

Оснащать телеметрией четыре готовых слоя задним числом — значит переписывать
их все, поэтому наблюдаемость растёт вместе с гейтами, а не появляется в G5.
Подробности — [docs/messenger/06-observability.md](docs/messenger/06-observability.md).

## Приоритеты

| Уровень | Что | Смысл |
| --- | --- | --- |
| **P0** | корректность ядра, вход, базовая безопасность | без этого продуктом пользоваться нельзя |
| **P1** | полный пользовательский опыт v1 | вложения, голосовые, push, админка, наблюдаемость |
| **RELEASE** | AWS, отказоустойчивость, нагрузка, восстановление | условие выхода в прод |
| **HARDENING** | ротации, плановое обслуживание, жизненный цикл Service Worker | после запуска |

Без этого разделения каталог превращается в вечный проект.

**G0 закрыт.** Чистый клон проходит `make local-up` и `make local-test` без
единой ручной настройки: одиннадцать приложений `Synced/Healthy`, контракты,
слои, проверка миграций, 33 модульных теста, три миграции и девять проверок
связности.

Единственное сознательное отступление — `G0-012`. Пакет в GHCR **закрытый**
по решению владельца, поэтому локальная выкатка идёт не по digest, а по тегу,
выведенному из содержимого образа: формально тег, по сути неподвижный. Чтобы
кластер тянул образ из реестра, нужен `imagePullSecret` с токеном на чтение
пакетов. В stage и проде образ идёт через реестр, там digest настоящий, и
`image.allowMutableTag` остаётся выключенным.

**Mesh в окружении разработки не используется.** Ambient снят с `observability`
и `cnpg-system`; Istio остаётся установленным как часть платформы. Причина
в журнале решений: после перезапуска кластера поды остались помеченными как
включённые в mesh, но перенаправление у них не восстановилось, и это выглядело
как проблема сети.

#### Bootstrap отделён от подъёма приложения

Локальный кластер уже несёт Cilium с Hubble, Istio ambient, Falco, CNPG,
оператор Kafka, Kyverno, cert-manager и наблюдаемость. Если смешать это с
подъёмом мессенджера, `make local-up` превратится в чудовище, которое никто не
будет запускать.

```
make bootstrap    Minikube и платформенные операторы; идемпотентно
make local-up     namespace, зависимости и сервисы мессенджера
                  (сам вызывает bootstrap, если платформы нет)
make local-test   контракты, интеграция, smoke
make local-down   только нагрузки мессенджера, данные по выбранной политике
```

Для нового участника верхнеуровневая команда остаётся одна — `make local-up`.

#### Проверка связности до бизнес-логики

Бизнес-логики ещё нет, но проводку надо доказать. Отдельный smoke, который не
трогает путь сообщения:

```
API → Postgres      API → Kafka        API → Redis
API → хранилище     Web → API          Web → рукопожатие Centrifugo
OIDC → Keycloak
```

#### Локальная почта

`AUTH-006` требует подтверждения адреса, поэтому в локальном окружении нужен
**приёмник почты** (Mailpit или подобный) — не провайдер рассылки, а локальный
сток. Без него G1 внезапно упрётся во внешнюю почту.

#### Ветки и слияния

```
main ← PR
обязательны: линтеры, юнит, контракты, интеграция, сканы, сборка
слияние только при зелёном
```

Веток `develop`, `stage`, `prod` нет. **Окружения живут в `messenger-gitops`, а
не в ветках.** Ключевой артефакт конвейера — `commit SHA → образ → sha256`; всё
дальнейшее ссылается на digest.

#### Критерий закрытия G0

Не «поды запущены», а один автоматический сценарий: чистый клон → `make
local-up` → платформа готова → ArgoCD `Synced/Healthy` → отвечают API, веб,
Keycloak, Postgres, Kafka, Centrifugo и хранилище → `make test-g0` → `CTR-001…004`
и `DEP-001` зелёные.

### G1 — идентичность и беседы · P0

Ещё без Kafka, без «печатает», без вложений.

**Схема G1 не объявляется стабильной**, пока не закрыты
[модель авторизации](docs/messenger/08-authorization.md) и жизненный цикл
данных. Причина не в порядке документов: `former-member`, границы видимости
истории и аудит привилегированных операций — это колонки и индексы, а не
логика поверх готовой схемы.

- `User`, `Session`, `Device`, `Conversation`, `ConversationMember`
- Keycloak, вход, подтверждение почты, жизненный цикл сессий
- Создание беседы один-на-один

**Тесты:** `AUTH-001…006`, `CONV-001…004`
**Выход:** A и B входят; A создаёт беседу с B; при встречном создании — **одна**
беседа и один `conversation_id` в обоих ответах.

**Что закрыл G1-001.** Доменные правила профиля — без базы; SQL — одним
запросом с `ON CONFLICT`, а не «сначала SELECT, потом INSERT»; пул через
PgBouncer в режиме transaction с выключенным кешем подготовленных выражений.
Недоступная база больше не роняет процесс и не отдаёт `ready` при пустом
списке проверок. Метрики `messenger_dependency_up` и
`messenger_db_pool_connections` сняты vmagent и лежат в VictoriaMetrics.

Появился отдельный уровень проверок — `make integration`: код против
настоящей базы, тем же образом и тем же путём, что и сервис. В CI он не
запускается: кластера там нет. Как он устроен, что доказывает каждая
проверка и какие правила обязана соблюдать новая —
[tests/integration/README.md](tests/integration/README.md).

**Что закрыл G1-002.** Реалма `messenger` не существовало вовсе: discovery
отдавал `404`, а `OIDC_ISSUER` приложения уже указывал на неё, и smoke при
этом был зелёный — он проверял `master`. Реалм заводит вход, регистрацию
и подтверждение адреса через локальный сток почты, браузерный клиент
с PKCE и ресурсный сервер с отображением аудитории.

Вскрылось свойство окружения, которое меняет настройку: **издатель и адрес
ключей — разные адреса**. Keycloak строит метаданные от своего `hostname`,
каким бы путём ни пришёл запрос, поэтому в токене стоит
`https://idp.finops.local/...`; ходить за ключами по этому адресу изнутри
кластера нечем — имя не резолвится, сертификат от локального центра.
Отсюда `OIDC_ISSUER` и `OIDC_JWKS_URL` вместо одного значения.

Связанные задачи закрыты в G1-004, G1-012 и G1-013: проверка проходит
живую страницу входа, ротация держит окно перекрытия ключей, а решения о
доступе принимает одна точка политики.

**Что закрыл G1-003.** Идентификатор сессии у нас тот же, что у Keycloak —
утверждение `sid` из токена. Свой отдельный потребовал бы таблицы
соответствия, которая существует ровно для того, чтобы однажды разойтись
с источником истины.

Главное свойство таблицы: **она может только отнять доступ, но не дать**.
Keycloak остаётся источником истины о том, вошёл ли человек; наша строка
отвечает на другой вопрос — не отозвали ли этот вход с тех пор. Это и есть
инвариант И-1: устаревшее состояние не расширяет права.

Проверено на живой базе то, чего не видно в коде: подобранный чужой
идентификатор устройства не перепривязывает устройство; чужим `sid` нельзя
перехватить сессию; повторный отзыв не переписывает время и причину
первого — иначе аудит терял бы момент, который расследуют; отозванная
сессия не воскресает следующим запросом с ещё живым токеном.

Немедленный отзыв уже действует для HTTP: отозванный вход отсекается
до всякой записи. Разрыв соединений WebSocket — отдельный путь доставки
события, `G1-008`; `GET /sessions` и `DELETE /sessions` как обработчики —
`G1-006` и `G1-007`.

**Что закрыл G1-004.** Обмен кода на токены делает сервер: только так токен
обновления попадает в cookie `HttpOnly` и остаётся недоступным скрипту
на странице (ADR 0005). Путь cookie узкий — на обычные запросы API браузер
её не приложит, — а на самих точках обмена проверяется источник, потому что
там она прикладывается автоматически. Контракт дополнен `/auth/callback`
и `/auth/refresh`; проверка совместимости добавление маршрутов принимает.

Проверка идёт от страницы входа Keycloak: запрос формы, отправка пароля,
перехват кода из перенаправления, обмен через наш обработчик, затем чтение
базы — профиль, сессия, устройство. Плюс отказы: повторно предъявленный
код, запрос с чужой страницы, негодная cookie.

**Два свойства окружения, найденные этой работой.**

`sid` в токене Keycloak 26.7 — **не UUID**, а короткая непрозрачная строка;
`session_state` пуст вовсе. Спецификация OIDC так и говорит. Наш
идентификатор теперь выводится из него через `uuid5` — миграция `0004`.

Страница входа строит абсолютные ссылки от `hostname`, то есть форма ведёт
на `https://idp.finops.local`, которого изнутри кластера нет. Браузеру это
подходит, проверке — нет, и она подменяет источник на внутренний. Та же
особенность, из-за которой издатель и адрес ключей разные.

**Осталось за рамками и ждёт своих задач:** ограничение частоты на точке
обмена (ADR 0005 требует его прямо; группа `ABUSE`, гейт G5); маршрут
до API на шлюзе со снятием префикса `/api/v1` — сейчас API наружу
не опубликован вовсе, это приходит с вебом в G3; обязательное действие
`Verify Profile` в реалме — учётная запись без имени и фамилии упирается
в него вместо входа, и это часть `G1-005`.

**Что закрыл G1-005.** Неподтверждённый адрес не отрезает пользователя от
приложения целиком: Keycloak выдаёт токен, а `/me` явно возвращает только
`read` и `send_message`; создание беседы появляется после подтверждения.
Первое письмо уходит один раз при создании локального профиля. Повторная
отправка доступна через `/auth/verify-email/resend`, ограничена тремя
письмами в час атомарным счётчиком Redis и при недоступном ограничителе
закрывается отказом, а не пропускает запрос.

Письма отправляет служебная запись API с минимальной ролью Keycloak. Реалм
сверяется при каждом применении GitOps, поэтому нужная настройка не зависит
от одноразового импорта. Сквозная проверка создаёт неподтверждённого
пользователя, читает письмо из Mailpit, проходит одноразовую ссылку,
повторный вход и отдельный подтверждающий клик Keycloak. Затем она проверяет
флаг административным API, получает новый токен, видит полный набор
возможностей и подтверждает синхронизацию локальной базы. Четвёртый повтор
в тот же час получает `429` и не создаёт лишнего письма.

**Что закрыл G1-006.** `GET /sessions` возвращает только активные входы
владельца предъявленного токена и помечает текущий. `DELETE
/sessions/{session_id}` отзывает одну принадлежащую ему сессию; чужой,
несуществующий и уже отозванный идентификаторы неразличимы, поэтому UUID
нельзя использовать для перечисления чужих входов. При выходе из текущей
сессии сервер снимает refresh-cookie, а её ещё живые access и refresh
отсекаются серверной отметкой отзыва.

Сквозная проверка создаёт у одного пользователя две независимые SSO-сессии
Keycloak на разных устройствах. После выхода из первой её access и refresh
получают `401`, в базе стоит ровно одна причина `logout_device`, а вторая
сессия остаётся видна и успешно обновляет токен. Разрыв уже открытого
WebSocket намеренно не приписан этой задаче: путь события до Centrifugo —
отдельный `G1-008`.

G1-008 — не деталь реализации входа, а отдельная задача: отложенный отзыв по
истечении токена и немедленный отзыв при выходе везде устроены по-разному, и
второй требует собственного пути доставки события.

**Что закрыл G1-008.** Centrifugo оставляет `user` доменным идентификатором
пользователя, поэтому presence и пользовательские операции не считают разные
устройства разными людьми. Короткий ticket предъявляется connect-proxy:
backend проверяет подпись и живую сессию до допуска WebSocket, сохраняет
назначенный Centrifugo `client` в отношении «одна сессия — много соединений»
и возвращает личный канал. Refresh-proxy повторяет проверку для долгоживущего
соединения; отозванный ticket нельзя использовать для переподключения.

Выход на устройстве под одной блокировкой отзывает сессию и забирает все её
соединения, затем разрывает каждое терминальным кодом из пользовательского
диапазона Centrifugo. Выход везде рвёт весь `user`. Разрыв best-effort и не
откатывает источник истины в Postgres, но логическая ошибка серверного API
при HTTP 200 больше не считается успехом. Живая проверка открывает две вкладки
одной сессии и отдельное устройство: обе первые вкладки закрываются, второе
устройство получает `session.revoked`, а старый ticket не переподключается.

**Что закрыл G1-009.** Тип беседы (`direct` или `group`), роль участника и
состояние членства представлены неизменяемыми доменными объектами. Прямая
беседа не существует без `direct_key`, группа не может его иметь, номер
последнего сообщения не бывает отрицательным, а бывший участник остаётся
отличимым и от действующего, и от постороннего.

Postgres-репозиторий записывает и читает беседы, добавляет членство, возвращает
бывшего участника для будущей проверки границы истории и отдельно перечисляет
только действующий состав и действующие беседы пользователя. Повторное
членство намеренно не является upsert: оно не может незаметно воскресить
вышедшего участника и стереть время выхода. Живая проверка выполняет все
операции через PgBouncer от роли приложения и откатывает транзакцию без следов.
Пользовательский сценарий создания диалога и разрешение встречной гонки
закрыты в G1-010 и G1-011.

**Что закрыли G1-010 и G1-011.** `POST /conversations` создаёт прямую беседу
только между разными подтверждёнными и не заблокировавшими друг друга
пользователями. Повторный и встречный запросы опираются на уникальный ключ
упорядоченной пары: проигравшая транзакция читает уже созданную беседу, поэтому
оба клиента получают один идентификатор. Проверка запускает встречные запросы
параллельно и подтверждает результат непосредственно в Postgres.

**Что закрыл G1-012.** Решения о чтении, записи, подписке и административном
действии проходят через единую `authorize()`. Кеш членства разрешён только для
READ и не может расширить права: WRITE и SUBSCRIBE всегда читают актуальное
состояние базы. Чужой и несуществующий ресурс внешне неразличимы, а разрешение
привилегированного действия возвращается только после долговечной записи
аудита.

**Что закрыли G1-013 и G1-014.** Обновление JWKS сохраняет одновременно старый
и новый действующие ключи, поэтому плановая ротация не разлогинивает всех.
Смена пароля доставляет подписанный OIDC Back-Channel Logout в API: подпись,
издатель, аудитория и тип события проверяются до обращения к базе, после чего
все локальные сессии отзываются с причиной `password_change`, а соединения
закрываются. Сквозная проверка использует отдельный временный OIDC-клиент и не
меняет конфигурацию рабочего `messenger-web`.

### G2 — надёжная доставка · P0

Ядро проекта. Здесь TDD применяется строже всего.

Сначала доменные единицы: уникальность `client_message_id`, выдача
`conversation_seq`, проверка членства, конечный автомат outbox, дедупликация
потребителя. Затем транзакция. И только потом путь целиком.

```
POST /messages → BEGIN: INSERT message + INSERT outbox → COMMIT
               → relay → Kafka → consumer-realtime → Centrifugo
```

**Первым делом — `G2-000`: разделение контракта события.** `message.created.v1`
несёт факт, `message.content.v1` — текст. Это ломающее изменение, и проверка
совместимости его честно отклоняет; делается оно сейчас именно потому, что
потребителей ещё нет. После G2 та же правка означала бы переписывание каждого.

**Что закрыл G2-000.** Факт появления сообщения и его содержимое физически
разнесены по `messenger.events.v1` и `messenger.content.v1`. Брокер больше не
принимает анонимные подключения: для relay и каждого потребителя Strimzi
создаёт отдельную SCRAM-учётную запись с минимальными ACL. Потребитель
непрочитанных может читать только факты; даже прямой запрос offsets закрытого
content-топика отклоняется авторизатором Kafka. Smoke сначала той же командой
доказывает доступ `realtime`, поэтому ошибка сети или клиента не может выдать
ложный зелёный результат.

**Что закрыл G2-001.** Сообщение стало неизменяемым доменным объектом, где
серверный номер беседы отделён от клиентского ключа идемпотентности. Номер
начинается с единицы; текст ограничен теми же 4096 символами, что и OpenAPI;
голосовое сообщение требует положительную длительность, а `system` нельзя
принять как пользовательский вид. Удаление представлено надгробием с пустым
payload: строка и её номер остаются в истории, содержимое наружу не выходит.

**Что закрыл G2-002.** Активное членство проверяется одновременно с
блокировкой строки беседы, поэтому две реплики API выдают последовательные
номера из одного серверного счётчика. После блокировки повтор с тем же
`client_message_id` возвращает исходные `message_id` и seq, не создавая новых
событий. Новый запрос записывает сообщение и два события — факт и содержимое —
одной транзакцией. Живая инъекция отказа на второй вставке outbox доказала,
что Postgres откатывает также сообщение, первое событие и увеличение seq.

**Что закрыл G2-003.** Событие доходит из базы в Kafka тремя шагами
в строгом порядке: аренда с закрытой транзакцией, публикация по сети,
отметка. Публиковать до аренды нельзя — две реплики отправят одно и то же;
отмечать до публикации нельзя — процесс, умерший в этот момент, потеряет
событие навсегда. Умереть между публикацией и отметкой можно, и это
допущено сознательно: аренда истечёт, запись уйдёт второй раз, а дубль
отсеет потребитель по `event_id` из заголовка.

Отказ останавливает пачку: следующая запись может быть содержимым того же
сообщения, и опубликовать её после неудачи с фактом значило бы показать
потребителю содержимое сообщения, о появлении которого он ещё не знает.
Запись с неизвестным типом события не уходит никуда — поток по умолчанию
означал бы утечку содержимого, — но и очередь собой не закрывает: живая
проверка подтвердила, что следующее событие публикуется поверх застрявшего.

Отправитель — отдельная нагрузка без пробы готовности: входящих запросов
у него нет, а живость видна по возрасту самой старой неотправленной
записи. Ради этой метрики процесс поднимает единственный слушатель, и
снимается она с пода, а не со службы. В хранилище уже лежат
`messenger_outbox_published_total`, `messenger_outbox_pending`
и `messenger_outbox_oldest_age_seconds`.

**Что закрыл G2-004.** Сообщение можно отправить снаружи, и путь проверен
целиком: страница входа Keycloak → токен → создание беседы →
`POST /conversations/{id}/messages` → запись в Postgres → outbox →
отправитель → оба потока Kafka. Ни один шаг не обходит HTTP.

Повтор с тем же `client_message_id` возвращает `200` и то же сообщение
с тем же номером — клиенту важно отличить его от `201`, потому что второй
код означает «первый запрос всё-таки дошёл». Проверка содержимого идёт
до обращения к базе: негодный запрос не должен занимать соединение
и ждать блокировку строки беседы. Слишком длинный текст отвечает `413`
отдельно от прочих отказов — повторять его без правки бессмысленно.
Посторонний получает `404`, а не `403`: подтверждение существования
беседы превратило бы перебор идентификаторов в способ узнать, кто
с кем переписывается.

Отправить сообщение вручную: `make send-message`.

**Что закрыл G2-005.** Сообщение доходит до получателя: `POST` от одного
участника — публикация в канале беседы у другого, по WebSocket. Путь целиком
проверен живьём, без подмены единого шага.

Факт и содержимое собираются обратно тем единственным потребителем, кому
положены обе половины; половина, пришедшая первой, ждёт свою пару в Redis —
не в памяти процесса, потому что реплик может быть несколько. Отдавать факт
без содержимого нельзя: клиент увидел бы пустое сообщение, а потом его
подмену текстом.

**Условие выхода гейта доказано.** Повтор не имитировался подделкой: у записей
outbox снималась отметка об отправке, настоящий отправитель публиковал их
в Kafka второй раз — так выглядит его смерть между публикацией и отметкой, —
и получатель второго сообщения не увидел. Отметка «отдано» ставится
до публикации, а не после, и `SET NX` атомарен, поэтому две реплики
потребителя не отдадут одно сообщение дважды.

Токен Centrifugo перечисляет каналы бесед явно, и подписывает клиента сам
сервер: попытка подписаться вручную получает `already subscribed`. Клиент
не выбирает канал — иначе подписка на чужую беседу сводится к знанию
её идентификатора.

**Тесты:** `TX-001…003`, `MSG-001…004`, `CONS-001…004`, `SEC-010`
**Выход:** убить relay после публикации в Kafka, но до отметки — Kafka получает
дубль, **B видит сообщение ровно один раз**. Пока это не работает, дальше не
двигаемся.

### G3 — согласованность клиента · P0

Здесь живут самые неприятные дефекты. Делается одним куском, потому что части
проверяют друг друга.

- История, пагинация по ключу, обнаружение пропусков
- Переподключение и догрузка при `recovered=false`
- Квитанции, непрочитанные, присутствие, несколько вкладок

Клиента до этого гейта нет вовсе: `apps/web` не существует, JS-тулчейна
в репозитории нет. Поэтому гейт начинается с контракта и схемы, продолжается
серверной половиной — её проверяют уже существующие проверки в кластере, —
и только потом доходит до браузера.

**«Печатает» в этот гейт не входит** и остаётся в G4: событие эфемерное,
лимитируется на стороне Centrifugo и ничего не говорит о согласованности
состояния. Как отдельный класс событий оно нужно `DEG-001` — «под давлением
печатает отключается, сообщения продолжают идти», — а это G5.

#### Решения, принятые до начала G3

**Догрузка.** `before_seq` и `after_seq` взаимно исключающие, и обе границы
исключающие: `before_seq=100` — это `seq < 100`, `after_seq=100` — `seq > 100`.
Ответ на догрузку идёт по возрастанию номера: это синхронизация вперёд, а не
листание назад. Продолжение обязательно — `has_more` и `next_after_seq`, —
иначе сценарий «пропустил 50» работает, а «пропустил 50 000» превращается
в новый дефект.

Курсор выше головы беседы — `400`, и это не формальность валидации. Такого
номера не выдавал никто: `last_seq = k` наблюдаемо ровно тогда, когда
наблюдаемо сообщение `k`. Ответь на него сервер пустой страницей с
`sync_to_seq` ниже курсора — клиент прочитал бы это как «догнал» и больше
не запросил историю никогда. Поэтому инвариант догрузки: `after_seq ≤ bound ≤
head`, где `bound` — `through_seq`, если он задан, и голова, если нет; голова
читается **до** страницы всегда, но границей остаётся названное первым
запросом. Проверка курсора против головы гонку не возвращает: она отвергает
будущее и ничего не замораживает. Тот же предел есть у `int64`: без него
`?before_seq=999999999999999999999999999` доезжал бы до драйвера и оборачивался
`500` на ошибку клиента.

**Синхронизация идёт до неподвижной точки.** Голова беседы движется, пока
клиент догружает: пока он читает 101–150, приходят 201–300, и часть того же
диапазона уже несёт поток. Догонять движущуюся голову по REST и одновременно
принимать те же номера по WebSocket — гонка, которую клиент не может выиграть:
он не знает, где кончается снимок и начинается поток, и `has_more` остаётся
`true` вечно. Поэтому первый запрос без `through_seq` замораживает границу —
сервер берёт голову на момент чтения и возвращает её как `sync_to_seq`, —
а продолжения идут с `through_seq`, равным этой границе, и выше неё не видят
ничего. Диапазон страницы: `after_seq < seq <= through_seq`. Когда снимок
исчерпан: `has_more: false`, `next_after_seq: null`, всё выше границы приходит
только потоком.

Это часть контракта, а не деталь реализации, и определяется она сейчас именно
поэтому. `G3-001` обязан реализовывать уже определённый протокол
восстановления, а не обнаружить в ходе реализации, что пагинация вперёд есть,
а зафиксировать, до какого состояния мы синхронизируемся, — нет. После
появления браузера та же правка стоила бы переписывания обеих сторон.

Два случая с `through_seq` расходятся, и это расхождение намеренное.
Равенство `through_seq` и `after_seq` — законный пустой снимок: `200`,
пустые `items`, `has_more: false`, синхронизация завершена. Так выглядит
повтор запроса, который клиент уже выполнил; ответить на него ошибкой значит
наказать за повтор, а повтор после обрыва связи — обычное дело, не сбой
клиента. Обратный случай, `through_seq` меньше `after_seq`, — `400`: такого
диапазона не существует, и пустая страница здесь была бы хуже отказа, потому
что клиент прочёл бы её как «синхронизация завершена» и молча потерял бы всё
пропущенное. Отвергается невозможное, а не повторённое.

**Доставлено — это квитанция клиента, а не подтверждение публикации.** Путь
`POST /conversations/{id}/receipts` с `delivered_seq` и `read_seq` уже выбран
в [решениях](docs/messenger/04-decisions.md); публикация в Centrifugo его не
заменяет — она доказывает, что сообщение принял сервер, а не что устройство
получателя его увидело. Инварианты: обе величины только вперёд,
`read_seq ≤ delivered_seq`, `delivered_seq ≤ conversations.last_seq`.
При нескольких устройствах агрегат по максимуму: доставлено, если хотя бы одно
устройство получило; прочитано, если хотя бы одно прочитало до этого номера.
Квитанции батчатся по номеру, а не шлются на каждое сообщение.

**Номер выше головы беседы отвергается, а не ограничивается максимумом.**
Уточнение того же решения, сделанное `G3-002` перед кодом. Молчаливое
ограничение выглядит для клиента применённой квитанцией: приславший `head + 1`
получил бы `200` и никогда не узнал, что объявил невозможное. У объявленного
в контракте `400` обязан быть производитель, иначе он недостижим по
построению, — тот же довод, которым отвергает невозможное `validate_bound`
в истории. Цена названа вслух: клиент, считающий номера локально, получит
отказ вместо тихого согласия. Клиента на этом контракте ещё нет — он пишется
в `G3-007`, — поэтому правка и стоит прозой контракта, а не ломающим
изменением поведения.

Бывший в контракте `PUT /conversations/{id}/read` этим отменён: два
номера — одно состояние, и везти их двумя запросами значит разрешить состояние,
в котором доставлено меньше, чем прочитано. Делается оно в G3-000 именно
потому, что клиента ещё нет; после G3 та же правка означала бы переписывание
каждого.

**Ломающее изменение вносится поимённо, а не ослаблением проверки.** Проверка
сравнивает контракт с предыдущим коммитом, поэтому одиночный разрыв красит CI
ровно один раз — в самом сломавшем коммите. Так прошёл `G2-000`: `CTR-001…003`
на том коммите красный, и это видно в истории. Ослаблять проверку целиком
нельзя — её смысл в том, что случайное удаление обязано падать. Поэтому разрыв
вносится записью в `packages/contracts/compat-allowlist.yaml`: поимённо, с
причиной и датой. Проверка превращает в примечание ровно названное и оставляет
ошибкой всё остальное. Сопоставление идёт по виду и имени элемента, а не по
тексту сообщения: сообщение можно переформулировать, а разрешение обязано
остаться привязанным к самому элементу, иначе одна запись однажды разрешит
чужой разрыв.

**Разрешение одноразовое, и держится это отказом, а не обещанием.** Запись,
не совпавшая ни с одним разрывом, — ошибка CI, а не замечание. Пока разрыв
есть, запись совпадает с ним и разрешает ровно его; как только разрыв попал
в базу сравнения, совпадать перестаёт, и следующий запуск требует её удалить.
Замечание здесь не годилось бы: сопоставление идёт по имени, поэтому забытая
запись через год разрешила бы новое удаление маршрута с тем же именем — то
есть исключение пережило бы то, что исключало. Порядок работы: сломать
совместимость и добавить запись одним коммитом, убрать запись следующим.
Список закрыт и не расширяется — как `GRANDFATHERED` в проверке миграций.

**Миграция не опирается на то, что данных нет.** `0009_delivery_receipts`
заводит `last_delivered_seq` значением по умолчанию `0`, но `0` — это
утверждение, которого никто не проверял: строка с `last_read_seq = 495`
и нулевой доставкой нарушает отношение в момент появления. Поэтому строки
приводятся к `last_delivered_seq = last_read_seq` — прочитанное получено, —
и только потом ставится ограничение. Ограничение идёт парой: `ADD ...
CHECK ... NOT VALID` по ADR 0006 не сканирует таблицу под исключительной
блокировкой, а следующий за ним `VALIDATE CONSTRAINT` берёт `SHARE UPDATE
EXCLUSIVE` и записи не останавливает — проверено живой гонкой с открытым
писателем. В одиночку `NOT VALID` проверяет лишь новые и изменённые строки,
оставляя открытой возможность невозможной строки ровно там, где её не видно,
в лежащих данных; `VALIDATE` превращает «мы уверены, что таких нет»
в проверенный факт.

Пустая таблица — обстоятельство, а не свойство схемы. Закладывать его
в миграцию значит оставить в ней утверждение, которое перестанет быть верным
молча; проверка на данных это и показала.

**Границы курсоров контракт объявляет, но не доказывает.** Взаимное исключение
`before_seq` и `after_seq` — свойство запроса целиком, а `parameters` в OpenAPI
описывают параметры по одному: связать их схемой нечем. Поэтому контракт
объявляет правило и ответ `400`, а доказывает его `HIST-004` — «ровно на
границе, включительно или исключительно, но одинаково всегда». Тест требует
живого маршрута, поэтому в G3-000 его быть не может: там нечего исполнять.
Он остаётся в G3-001, и `G3-000` закрывается без него. Обещать «проверено
схемой» в строке готовности значило бы записать в доказательства то, чего
проверка не делает.

**Проверка без принуждения не проверка.** `G2-000` прошёл при красном
`CTR-001…003`, и объяснение оказалось хуже, чем «проверка не обязательна»:
у `main` не было защиты вовсе — `Branch not protected`, наборов правил нет,
обязательных проверок нет. Задача прогонялась, падала и ни на что не влияла.
Отсюда порядок работ: сначала обязательность, потом разрешающая запись —
allowlist поверх необязательной проверки не отличается от комментария в коде.

Включено: обязательные проверки `CTR-001..003`, `DEP-001 — образ по digest`,
`Миграции применяются с нуля`, `Слои и модульные тесты`; `strict: true`;
`enforce_admins: true`; слияние только через PR (ноль обязательных одобрений —
свой PR смёржить можно, а пушить в `main` напрямую нельзя). `strict` здесь
не украшение: совместимость сравнивается с `pull_request.base.sha`, поэтому
устаревшая база делает зелёную проверку утверждением о позавчерашнем `main`.

Проверено не чтением настроек, а поведением: временная ветка от `main`
с теми же правилами, в неё — прямой push. GitHub отказал `GH006` с двумя
причинами сразу — «Changes must be made through a pull request» и «4 of 4
required status checks are expected», — ветка осталась на исходном коммите.
Обходного пути для администратора нет, и это то, что требовалось.
Аварийный порядок — в [14-incidents.md](docs/messenger/14-incidents.md):
ослабляется одно правило, требование PR сохраняется, возврат привязан
к смягчающей правке. Снятие защиты целиком аварийным механизмом не является.

Два ограничения выведены из того, как проверки устроены, и записаны, чтобы
их не пришлось выводить заново:

- у `contracts.yml` снят фильтр по путям у `pull_request`. Обязательная
  проверка и фильтр несовместимы: PR, не трогающий перечисленные пути,
  не запустил бы workflow, проверка осталась бы в состоянии «ожидание»,
  и такой PR не смёржился бы никогда. Проверка, которая иногда не
  выполняется, не может быть условием слияния;
- `build` из `image.yml` обязательным не сделан и не должен быть: этот
  workflow запускается только на `push` в `main` и `workflow_dispatch`,
  на PR не отчитывается вовсе, и обязательная проверка по нему заперла бы
  все PR навсегда. То же правило для любой будущей задачи: обязательной
  может быть только та, что отчитывается на каждом PR.

Отсюда же следствие для одноразовой записи. Проверка идёт на каждом PR,
поэтому запись обязана исчезнуть сразу после того, как разрыв попал в `main`:
иначе следующий же PR — любой, не только контрактный, — упадёт на ней как
на несовпавшей. Порядок такой: PR с разрывом и записью (зелёный, потому что
запись совпадает), затем PR, удаляющий запись (зелёный, потому что записи
больше нечего разрешать).

**Состав PR определён так же строго, как его проверки.** Первый PR содержит
ровно разрыв и то, что делает его законным: удаление `PUT /read`, добавление
`POST /receipts`, границы `after_seq` / `through_seq` / `sync_to_seq`,
миграцию `0009` с догрузкой и проверенным ограничением, запись в allowlist,
изменение `validate.py`, обязательность проверки в workflow и документацию
этих решений. Кода `G3-001` в нём нет: история должна читаться как «вот
коммит, сознательно изменивший контракт до появления клиента», а не как
смешанный набор. Второй PR содержит только удаление записи.
Это не эстетика: если второй PR покраснел, известно, что сломан именно
механизм одноразового исключения, а не соседний код.

**Признак чистого baseline** — то, что проверяется после второго PR, а не то,
во что верят после первого:

```
GET  /conversations/{id}/messages   с after_seq и through_seq — норма
PUT  /conversations/{id}/read                                 — отсутствует
POST /conversations/{id}/receipts                             — норма
packages/contracts/compat-allowlist.yaml                      — пуст или удалён
проверка совместимости                                        — без исключений
```

Пустой `allowed: []` и отсутствие файла равнозначны: `load_allowlist`
возвращает пустой список в обоих случаях, и «разрешено ничего» — это
разрешено ничего, а не отсутствие проверки. `G3-001` начинается после того,
как baseline чист, — на исключении, которое ещё лежит, строить следующий
разрыв нельзя.

**Пройдено, а не предположено.** Разрыв влит первым PR, запись снята вторым.
На промежуточном `main` проверка падала на отслужившей записи — «не совпал
ни с одним разрывом — удалить», — то есть одноразовость наблюдалась в CI,
а не следовала из кода. Обе половины механизма зелёные по отдельности:
первый PR потому, что запись совпала с разрывом, второй потому, что
разрешать стало нечего. Средняя — красная — и есть та, ради которой
механизм существует.

**Квитанция и телеметрия — разные плоскости.** Квитанция — надёжный
продуктовый протокол, меняющий `sent → delivered → read`; телеметрия —
измерение, `sampled` и `best-effort`. `G3-008` не заменяет и не подменяет
`G3-002`: первая отвечает «доставлено ли», вторая — «сколько это заняло».

**Три задержки, а не одна.** Существующая `messenger_realtime_publish_duration`
заканчивается на подтверждённой публикации в Centrifugo, то есть на `t5`, —
это серверный участок, а не `T_realtime` из документа, который идёт до `t6`,
момента получения браузером. Развести надо явно: серверная публикация — до `t5`,
`T_realtime` — до `t6`, `T_delivery` — до `t7`. Иначе имя метрики обещает
пользовательскую задержку, а измеряет серверную, и это расхождение обнаружится
только при разборе, когда доверия к цифре уже нет.

**Счётчик непрочитанных — проекция, а не источник истины.** Источник —
`messages` и `last_read_seq`; счётчик инкрементируется на чужое событие
и корректируется при квитанции. `COUNT(*)` на каждое событие не делается:
на целевой нагрузке это read amplification. Требование теста от этого не
меняется — повтор не удваивает, чтение пересчитывает состояние, — а потеря
проекции не должна менять существенный ответ системы.

**Идемпотентность держится порядком, а не журналом `event_id`.** Правка
прежнего решения: здесь стояло «после дедупликации по `event_id`». События
`message.created` партиционируются по `conversation_id`, поэтому порядок внутри
беседы сохраняется, и монотонного чекпойнта по `conversation_seq` достаточно:
повтор — это событие, номер которого не больше применённого. Журнал
доставленных `event_id` пришлось бы хранить вечно — момент, после которого
событие уже не придёт, потребителю неизвестен, — и он был бы вторым источником
истины рядом с чекпойнтом. `event_id` остаётся идентификатором события
и ключом корреляции; описание поля в схеме приведено к этому решению.

**Чекпойнт — один на беседу, а не на пару (пользователь, беседа).** Разница
видна на последовательности 10 (B→A), 11 (A→B), 12 (B→A): чекпойнт
пользователя A, сдвигаемый только чужими сообщениями, остановился бы на 10
и, увидев 12, счёл бы 11 потерянным — хотя 11 собственное сообщение A, и
непрочитанное оно не увеличивает. Поэтому чекпойнт двигается **любым**
`message.created`, а «чужое» фильтруется только при приращении.

**Один предикат на все пути.** Приращение, пересчёт по квитанции и пересборка
трактуют одно и то же одинаково; предикат живёт в двух экземплярах — на Python
и на SQL, — и тождество не постулируется: интеграционная сверка `reconciliation`
доводит проекцию только событиями, пересобирает её из источника истины и
сравнивает числа поимённо по каждому участнику. Квитанция пересчитывает
синхронно, но **не дальше чекпойнта потребителя**: сообщение, уже лежащее
в Postgres, но ещё не применённое, в счёт не входит и позже честно даёт `+1`.

**Два случая потери — разной природы, и различие не тонкость.** Уцелевшая
строка проекции отвечает **асинхронно**: число в ней меньше источника истины
ровно на ещё не применённое, и это согласованность в конечном счёте — догоняет
потребитель, а не список. Строка потерянная отвечает **синхронно**: её
восстанавливают из источника истины в момент запроса, потому что догонять
нечем — события, которых проекция не видела, могли уйти по сроку хранения.
Отсюда и граница работы `restore_lost_counts`: он включается **отсутствием**
строки, а не отставанием потребителя. Сверка головы с чекпойнтом на каждом
чтении подменила бы потребителя списком и вернула бы `COUNT` на каждый запрос —
ровно то, ради устранения чего проекция и заведена. Поведение закреплено
юнитом (`test_отставшая_строка_не_догоняет_потребителя`): строка есть,
чекпойнт 10, голова 11 — пересборки нет и число остаётся прежним.

**Ремонт идёт транзакцией на беседу, а не одной на страницу.** Граница
согласованности у ремонта та же, что у потребителя и квитанции, — «замок
беседы плюс обе записи», — но она не тянется через всю страницу. Одна
транзакция на всех означала бы, что замок первой беседы держится, пока
пересобраны остальные, и потребитель с квитанцией этой беседы ждали бы ремонта
последней; в начальной загрузке, где теряется сразу вся страница, это обычный
случай, а не редкий. Дольше беседы замок держать незачем: числа бесед
независимы. Сортировка потерянных осталась, но уже не как защита от
взаимоблокировки — одна транзакция держит не больше одного замка беседы, — а
ради детерминированности журнала и тестов. Закреплено юнитами
`test_беседа_не_удерживает_замок_чужого_ремонта` (журнал: транзакция
закрывается до следующего замка) и
`test_потерянные_беседы_обходятся_по_возрастанию` (транзакция на каждую
беседу, ни одной страничной).

**Долг: негодное событие оставляет проекцию отставшей навсегда.** Пропуск
негодного события и неразобранной записи виден в журнале (`unread_event`
`result="invalid"`), но видимость — не лечение. Если пропущенное событие было
для беседы последним, следующего не будет, разрыва номеров не случится,
а восстановление на чтении смотрит на отсутствие строки, а не на отставание, —
и проекция останется отставшей, причём по числам это неотличимо от верной.
Настоящая защита — карантин записей, сверка проекции с источником истины или
ручная пересборка. Это отдельная работа усиления, а не `G3-003`: внутренний
продюсер обязан выпускать валидный `message.created`, а очереди отклонённых
записей (DLQ) в первой версии нет. Записано, чтобы запись в журнале не
читалась как решённая задача согласованности.

**`RT-004` и `MSG-005` протокольной проверкой не закрываются.** Проверка
протоколом доказывает `recovered=false`, работу `after_seq`, отсутствие дублей
и дыр. Она не доказывает `SYNCING`, `DEGRADED` и слияние состояния в браузере.
Поэтому `RT-004` остаётся ⬜ после G3-001 и закрывается только в G3-006 —
иначе зелёная строка в статусе будет означать не то, что прочитал человек.

**`DB-001` — `pending stage`, а не ✅.** Локально реплики нет: `messenger-db-1`
один инстанс, пул идёт в писателя. Поднимать read-replica ради одного теста
значит вводить компонент, которого в AWS в таком виде не будет. В G3-001
проверяется политика маршрутизации — свежие страницы с писателя, глубокая
история через абстракцию чтения, — а настоящее отставание проверяется на
stage, где реплика появляется вместе с RDS.

**Реплика не обслуживает страницы, пока не умеет отвечать за границу.**
`ReadMode`, `read_settings`, `read_pool` и `connection(mode=…)` остаются —
шов на месте и проверен, — но выбирает по нему `Runtime`, и сегодня
`STALE_OK` тоже ведёт к писателю (`_READER_SERVES_PAGES = False` в
`services/runtime.py`). Причина в цене ошибки: писатель на номере 100,
реплика на 90, страница `before_seq = 96` вернула бы 90…86, и 95…91 не увидел
бы никто — следующий ответ снова выглядит непрерывным, а сравнить клиенту
не с чем. Локально это невоспроизводимо вовсе: `DATABASE_READ_HOST` не задан,
обе ветки идут в один пул, и зелёный `HIST-001` ничего об этом не говорит.
Условие включения — проверка отставания (догнала ли реплика ту границу,
с которой читается страница) и поведение при её отказе; это отдельная правка
вместе с настоящей репликой на stage. Заодно реплики нет в пути запроса:
иначе лежащая реплика добавляла бы к каждому запросу свой `connect_timeout`,
а поднявшаяся и умершая позже — ломала бы чтение вместо того, чтобы отдать
его писателю.

**История закрыта на живой беседе (прогон 19.09.2026).** `HIST-001…004`,
восстановление вперёд и обе половины `DB-001` — 30 проверок в кластере против
настоящего Postgres через PgBouncer, тем же образом и тем же путём, что
рабочий запрос; надгробие создано настоящим `UPDATE`, а не вызовом сервиса.
Ещё 339 модульных проверок — форма ответа, коды отказов и решение
маршрутизатора без базы. Прогон нашёл дефект, которого модульные проверки
увидеть не могли: `# noqa` на первой строке `f"""…"""` уехал внутрь SQL и
валил разбор запроса только против настоящей базы, тогда как поддельное
соединение принимает любой текст. Отсюда отдельная проверка текста запроса —
на то, что комментарий Python не доезжает до драйвера.

**Список бесед закрыт там же (прогон 19.09.2026).** `LIST-001…003` — 17 проверок
в кластере, в одной транзакции с откатом: `ON DELETE CASCADE` в схеме нет
ни одного, а отправка сообщения оставляет записи в `outbox`, поэтому откат
короче и безопаснее уборки в обратном порядке. Ожидаемый порядок проверка
считает **в Python** — сортировкой `(updated_at, conversation_id)` по выборке
**без** `ORDER BY`, — а не повторяет запросом: вторая копия того же `ORDER BY`
доказывала бы только то, что Postgres дважды сортирует одинаково. Всего после
обеих половин — 375 модульных проверок, 36 из них на список.

**Половина `DB-001` про «своё не исчезает» проверяется другим соединением.**
В одной транзакции это утверждение вырождается в «транзакция видит
собственную незакоммиченную запись» — верное для Postgres и неверное для
сервиса, где запись коммитит один HTTP-запрос, а читает её следующий. Пул
отдаёт освобождённое соединение повторно, поэтому в проверке оба соединения
держатся одновременно, а запись к моменту чтения закоммичена. Следы
коммитящей фазы снимаются вручную и в порядке, обратном созданию: в схеме
нет ни одного `ON DELETE CASCADE`, а `outbox` не ссылается на `messages`
вовсе, и уборка, о которой не спросили, оставила бы мусор молча.

**`sync_to_seq` — не `null` тогда и только тогда, когда задан `after_seq`.**
`through_seq` его значение не меняет: он эхо, а не пересчёт. Проверка головы
(`after_seq ≤ bound ≤ head`) ничего не замораживает и потому эхо не отменяет.

**Долг: поля, обязательные в контракте и необязательные в схеме.** Это класс,
а не единичный случай, и `sender_id` у сообщения стёртого автора — только
первый его экземпляр. `0002_erasure.sql` снимает `NOT NULL` не с него одного:
`users.display_name` лишается того же ограничения (`0002_erasure.sql:42`),
а `UserSummary.display_name` (`openapi.yaml:729-734`) объявлен обязательным
и не нулевым. Механика отказа одна и та же, и `UserId`/`str` её не поймают:
`NewType` не проверяет ничего, обработчик собирает ответ строкой, то есть
клиент получит строку `"None"` там, где контракт объявляет `format: uuid`.
Отказ при этом не виден ни в метриках, ни в журналах: маршрут объявлен
`response_model=dict[str, object]`, по полям ничего не валидируется, и `500`
не будет — будет тихо неверный ответ. Сегодня недостижимо (пути стирания
в коде нет), и комментарий в `repositories/messages.py::_to_message` долг
фиксирует.

Оговорка, чтобы не преувеличить вес списка бесед: он **не первое** место, где
`display_name` вылезет. `POST /conversations` отдаёт `participants[]` с тем же
полем с самого начала, так что путь уже открыт, и новый маршрут лишь
добавляет к нему второй.

Решается вместе с erasure-путём (`09-data-lifecycle`), а не отдельной правкой:
вероятное решение — `[string, null]` в контракте — расширяет тип
и проходит через `make contracts` и правила expand-contract
(`13-client-compatibility.md`). Там же решается, что клиент делает
с сообщением стёртого автора и с безымянным участником, потому что на `null`
он упадёт не так, как на `"None"`. Обе половины `G3-001` этим долгом
не блокировались.

**Список бесед — отдельный read-model, а не растянутая старая выборка.**
Существовавшая `list_active_user_conversations()` отдавала коллекцию целиком,
тогда как стандарт (`07-engineering-standard.md:114`) требует от имени `list_*`
пагинации всегда. Растягивать её до `last_message` значило бы закрепить
расхождение имени с поведением и добавить к нему вес, поэтому она заменена
на keyset-выборку страницы, а имя исчезло вместе со своим единственным
вызывающим (`G1-009`).

**Курсор — пара компонентов, потому что одного не хватает.** `updated_at`
беседы — единственный кандидат в «activity»: его двигает единственная запись
в системе, `allocate_sequence` при отправке сообщения. Но отметка
**не уникальна**: `now()` в Postgres — время транзакции, а не момента, поэтому
беседы, созданные или изменённые одной транзакцией, получают одинаковое
значение до микросекунды. Строгое `<` по одному времени теряет на стыке
страниц всю группу равных, нестрогое — дублирует её. Поэтому порядок, предикат
и продолжение — по паре `(updated_at DESC, conversation_id DESC)`:
`before_conversation_id` в запросе, `next_before_conversation_id` в ответе.
Собственный `next_*` отдаёт пару всегда, поэтому пагинация нашего клиента
точна.

**Курсор принимается только целым, и это правка по итогам ревью.** Первая
редакция оставляла одиночный `before_activity_at` законным — «объявлен
контрактом, отвергать значит сузить обещанное» — и закрепляла интеграционной
проверкой, что на группе равных он отдаёт пустую страницу. Ревью назвало это
тем, чем оно было: проверка закрепляла известную потерю данных как допустимое
поведение, а довод про объявленный контракт защищал не клиента (клиента нет,
веб-клиент — `G3-005`), а саму потерю. Теперь «только отметка» и «только
идентификатор» дают `400 invalid_cursor` до обращения к базе; `conversation_id`
в `ActivityCursor` обязателен, варианта «строго старше отметки» в репозитории
не осталось вместе с его предикатом. Пустая страница на месте отказа была бы
хуже ошибки: она неотличима от конца списка, и клиент на ней останавливается,
о потере не узнав.

Сужение семантики уже объявленного параметра — разрыв, который проверка
совместимости **не умеет увидеть**: параметр на месте, схема его не изменилась.
В allowlist такой разрыв не записывается не потому, что он не разрыв, а потому
что записывать его нечем; решение зафиксировано прозой — в контракте, здесь
и в каталоге тестов.

Снимка списка протокол не обещает вовсе: ключ сортировки изменяемый, и обычный
keyset по нему такого снимка не даёт — беседа может перепрыгнуть через курсор
между страницами. Поэтому `LIST-002` написан как **статический** обход,
а стабильный список при живой активности остаётся отдельным контрактным
решением (аналог `sync_to_seq` у истории), а не ещё одним тестом.

**`unread_count` списком отдаётся, и это решение `G3-003`.** Здесь стояло
обратное — «не отдаётся: продюсера нет», — и перестало быть верным, когда
потребитель появился: проекция без читателя была бы мёртвым кодом. Число
приходит из проекции, а её **отсутствие ответа не меняет**: строку, которой
нет, восстанавливают из источника истины в момент запроса, и дорогая половина
(`COUNT` по беседе) достаётся только потерянным строкам. Тем же закрыт случай,
до которого проекция не доехала никогда: беседа, чьи события ушли из Kafka
по сроку хранения, не получит их ни от потребителя, ни от уборки — а получит
от первого же списка, в который попала. `None` в ответе поэтому значит не
«проекция потеряна», а «источник истины не даёт числа этому читателю»: он не
в составе беседы. Подставить вместо этого `0` нельзя — «всё прочитано»
и «спросить не у кого» разные ответы, и второй клиент обязан уметь отличить
(`LIST-003`).

Считать `last_seq − last_read_seq` по-прежнему нельзя, но довод сузился:
разность считает собственные сообщения, которых читатель себе непрочитанными
не писал, и складывает это через всю историю беседы. Надгробия при этом
считаются **намеренно**: непрочитанное — это чужие позиции `conversation_seq`
выше `last_read_seq`, а не сообщения с доступным содержимым. Читатель
удалённую позицию не наблюдал и при чтении увидит на её месте надгробие;
исключить её из счёта значило бы сделать пересборку из источника истины строго
меньше приращения и разойтись с ним всегда, потому что события удаления
в потоке нет. А настоящий `COUNT(*)` на каждый список есть ровно тот read
amplification, ради устранения которого проекция и заведена.

**Долг: индекса на `updated_at` нет, и это записано как состояние, а не как
упущение.** На `conversations` сегодня только PK и частичный уникальный
`direct_key`; выборку последнего сообщения покрывает
`messages_conversation_seq_idx (conversation_id, conversation_seq DESC)` —
ровно ключ `DISTINCT ON`, — а сортировка списка идёт по колонке без индекса.
Это осознанно: список — беседы **одного** пользователя, в v1 только direct,
то есть десятки строк, а не миллионы. Индекс `(updated_at DESC,
conversation_id DESC)` понадобится с группами на сотни участников или
с другими путями чтения «все беседы пользователя».

Завести эту миграцию сейчас нельзя не по вкусовой причине, а по техническому
противоречию: `scripts/check-migrations.py:63-71` требует `CONCURRENTLY`
от каждого нового `CREATE INDEX`, а `db/migrate.sh:79-83` применяет миграции
через `psql --single-transaction`, где `CREATE INDEX CONCURRENTLY` невозможен
вовсе. Правила надо сначала развести — и это отдельная работа, а не строка
в этом гейте. Миграция `0010` (`G3-003`) этого долга **не увеличивает**:
индексов в ней нет — оба ключа объявлены в `CREATE TABLE`, где `CONCURRENTLY`
не нужен и не разрешён, — поэтому противоречие она не задевает и разводить
правила ради неё не требуется.

**Долг: страница списка и `last_message` — два отдельных `SELECT` без общего
снимка.** Сообщение, пришедшее между ними, даёт страницу, упорядоченную
по старому `updated_at`, с новым `last_message` в элементе. `LIST-002` это
не задевает: он статический, и данные между страницами не меняются. Снимка
списка протокол не обещает, поэтому долг не блокирующий — но если единый
ответ когда-нибудь понадобится, обычного `READ COMMITTED` для него не хватит:
каждый `SELECT` видит свой снимок, и одним `BEGIN` этого не исправить. Нужен
либо один SQL (последнее сообщение через `LATERAL` к странице), либо
`REPEATABLE READ` на оба чтения. Выбор между ними — по цене: `LATERAL`
дороже планировщику и ломает разделение «репозиторий бесед не знает формы
строки сообщения», уровень изоляции дороже по конфликтам на писателе.

**Проверка совместимости контрактов расширена тем же ревью.** `CTR-001` теперь
видит, кроме полей и маршрутов, две вещи, которых в схемах не видно:

* **параметры запроса** — удаление, появление `required: true` и сужение
  схемы самого параметра: тип, формат, границы, перечисление. Появление
  ограничения там, где его не было, — тот же разрыв, а не «нечего
  сравнивать»: схема без `type` принимает любое значение, а с `type:
  string` — только строку. Параметр разрывом ломает вызывающего ровно
  так же, как удалённое поле ломает получателя, но `flatten_schema` его
  не видит — удаление `before_conversation_id` не тронуло бы ни одной
  сравниваемой строки. Расширение разрывом не считается: проверка,
  находящая любое изменение, запретила бы менять контракт вовсе;
* **ссылка на схему ответа** — по ключу «метод, путь, статус, тип
  содержимого». Подмена `$ref` на другую существующую компоненту иначе
  не видна: обе компоненты на месте, поля в них не менялись, а клиент
  получает другой тип.

Ключ ответа включает статус и тип содержимого не для полноты: у операции
ответов несколько, и запись «метод + путь» выдавала бы разрешение **операции** —
второй inline-ответ добавлялся бы рядом с разрешённым, не сдвинув множество
найденного ни на элемент.

Ответ `GET /conversations` вынесен в компоненту `ConversationListPage` — у
inline-схемы нет имени, и полей её ответа для сравнения не существует. Оба
необязательных поля продолжения (`next_before_*`) стали обязательными: сервер
отдаёт их всегда, `null`-в-`null` — единственный признак конца списка, и
сгенерированный клиент обязан это видеть, а не проверять наличие ключа.
Новый inline-ответ роняет проверку структуры; пять объявленных ранее
перечислены в `INLINE_RESPONSE_SCHEMAS` — список закрыт, как `GRANDFATHERED`
у миграций, а их поля по-прежнему не сравниваются. Это записанная дыра,
а не гарантия.

Чего проверка не видит и теперь — тоже записано, чтобы не читалось как
покрытое: сужение **семантики** уже существующего параметра (одиночный
`before_activity_at`, отвергнутый `400`), тип элемента, заданный ссылкой
(`items: { $ref: … }` сравнивается как «массив»), и ключи схемы параметра,
не названные в `COMPARED_KEYS` (`pattern`, `multipleOf`, `const`). В allowlist
такое не записывается не потому, что не разрыв, а потому что запись требует
находки.

Тогда же у проверки появились собственные тесты
(`packages/contracts/test_validate.py`, из `make contracts` и из джоба
`CTR-001..003`): детектор, который нельзя выключить незаметно, — это
единственный способ не повторить ту же историю на уровень выше.

**Терминология.** `G3` здесь — гейт реализации, «согласованность клиента».
«Этап 3» в [04-decisions.md](docs/messenger/04-decisions.md) — этап выкатки,
AWS stage. Совпадение номеров не означает связи, и путать их нельзя.

**Тесты:** `MSG-005`, `HIST-001…004`, `LIST-001…003`, `DB-001`, `RT-004`,
`RCP-001…006`, `UNR-001…003`, `PRS-001…003`
**Выход:** A получил до seq 100, закрыл ноутбук, B написал 101–150, A вернулся
→ `recovered=false` → `SYNCING` → `after_seq=100` → 101–150 без дублей
и пропусков → снимок закрыт на `sync_to_seq` → счётчик непрочитанных верен →
квитанции монотонны → присутствие верно → `CONNECTED`. Плюс браузерные
сценарии, которых не заменяет ни одна серверная проверка: сон вкладки, сон
ноутбука, фоновая вкладка, переход с Wi-Fi на мобильную сеть.

### G4 — продукт целиком · P1

Только после надёжного пути сообщения.

## Что поднято из укрепления в блокирующее

Четыре проверки — не «улучшение после запуска»:

- `INFSEC-001` публичный доступ к бакету закрыт
- `INFSEC-002` у базы, шины и кеша нет публичных точек входа
- `INFSEC-004` под одного сервиса не принимает роль другого
- `INFSEC-006` секреты отсутствуют в git, образах и журналах

## Форма задачи

Идентификатор из каталога становится идентификатором задачи. Не «сделать
счётчик непрочитанных», а:

```
UNR-001 — непрочитанные
  Требование   показывать счётчик непрочитанных
  Инвариант    повторное message.created не увеличивает дважды
  Реализация   consumer-unread, ReadState, производный счётчик
  Тесты        UNIT, CONS-003, UNR-001, UNR-002, UNR-003
  Метрики      consumer_processing_duration_seconds{consumer="unread"}
  Готово       всё зелёное
```

Метрика в примере — **указатель на существующее**, а не на желаемое: здесь
стояло `unread_consumer_lag, unread_update_latency`, и ни одной из этих двух
в коде нет ни сегодня, ни по итогам `G3-003`. Лаг потребителя требует
`consumer.position()`/`highwater()` из `aiokafka`, которых `adapters/kafka.py`
не отдаёт, а `messenger_duplicate_events_total` существует только строкой
каталога (`06-observability.md`) — как и лаг. Поэтому гейт берёт
`messenger_consumer_processing_duration_seconds{consumer="unread"}` —
единственную реализованную метрику конвейера, и сверяет форму задачи с кодом,
а не наоборот. Повтор и разрыв при этом видны: лог-событие `unread_event`
несёт `result` (`applied`, `duplicate`, `rebuilt`, `ignored`, `invalid`).
Это названный зазор, а не забытая работа.

## Состояния задачи

```
READY → RED (тест написан и падает) → IMPLEMENT → GREEN
      → OBSERVABLE (метрика и трасса есть) → LOCAL VERIFIED → DONE
```

Для отказоустойчивости и нагрузки:

```
GREEN LOCAL → WAITING STAGE → CHAOS/PERF VERIFIED → DONE
```

## Правило на время реализации

С этого момента **новые архитектурные идеи в критический путь не попадают**.
Мысль, возникшая по ходу работы, либо исправляет доказанную ошибку — и тогда
идёт в текущий гейт, — либо уходит в backlog или укрепление. Без этого правила
G0 не начнётся никогда: за время проектирования каждое ревью находило что
добавить, и так будет всегда.

Что уже вынесено за область первой версии и не блокирует gate: `CONS-005`
(потребители поиска и аналитики), `PERF-007` (беседа на 500 участников), вся
группа укрепления.

G0, G1 и G2 закрыты. Следующий шаг — **G3**, согласованность клиента.
