# Как ambient входит в под

> kubernetes-finops-platform · разобрано на local-v1

Istio перехватывает трафик пода, не меняя ни Helm-чарт, ни манифест Deployment, ни один объект Kubernetes у приложения. Разбор механизма по шагам — и что такое STRICT на самом деле. Всё проверено на работающем кластере.

## Загадка

В поде **один контейнер** — приложение. Никакого сайдкара. При этом в его сетевом неймспейсе слушают четыре чужих порта:

```
# ss -ltnp внутри пода, в котором один контейнер
LISTEN  0.0.0.0:8429     ← приложение
LISTEN  *:15008          ← HBONE, входящий mTLS
LISTEN  *:15006          ← входящий открытый
LISTEN  *:15001          ← исходящий
LISTEN  127.0.0.1:15053  ← DNS-прокси
```
Сокеты принадлежат **процессу, который живёт в другом поде** — ztunnel, одном на узел. Дальше — как это возможно.

## Механизм по шагам

1

### Включение — это метка, и её читает CNI

istio-cni дописывает себя в цепочку CNI на узле, и в его конфигурации лежат селекторы. Ничего в Deployment не меняется, потому что решение принимается *не по манифесту пода*, а по метке его namespace.

```
# /etc/cni/net.d/05-cilium.conflist — на узле, а не в кластере
"plugins": [
  { "type": "cilium-cni" },
  { "type": "istio-cni",
    "ambient_enabled": true,
    "cni_agent_run_dir": "/var/run/istio-cni",
    "enablement_selectors": [
      { "podSelector": { "matchLabels": {
          "istio.io/dataplane-mode": "ambient" } } },
      { "namespaceSelector": { "matchLabels": {
          "istio.io/dataplane-mode": "ambient" } } }
    ],
    "exclude_namespaces": ["kube-system"] }
]
```
Отсюда же следует то, обо что легко споткнуться: перехват ставится **при создании пода**. Пометили namespace — существующие поды остаются вне меша, пока их не перезапустят.

2

### Цепочка CNI, а не замена

Когда kubelet создаёт под, плагины выполняются по порядку: `cilium-cni` даёт поду сеть, затем `istio-cni` проверяет селекторы. Именно поэтому Cilium нужно попросить не считать себя единственным CNI — иначе он вычистит второй плагин с узла, и меш молча ничего не перехватит.

```
# gitops/02-infra/cilium/values.yaml
cni:
  exclusive: false   # иначе istio-cni удаляется из conflist
```

3

### Передаётся не конфигурация, а файловый дескриптор

Это самый неочевидный шаг. Агент istio-cni передаёт ztunnel **дескриптор сетевого неймспейса пода** через unix-сокет. Не имя, не путь, не запись в API — открытый fd.

```
# на узле: два сокета, через которые всё и происходит
/var/run/istio-cni/pluginevent.sock  ← плагин -> агент
/var/run/ztunnel/ztunnel.sock        ← агент -> ztunnel (ZDS)
```
Сокет ztunnel смонтирован в его под как том — это единственная связь между ними:

```
# DaemonSet ztunnel
volumeMounts:
  - cni-ztunnel-sock-dir -> /var/run/ztunnel
  - istio-token          -> /var/run/secrets/tokens
  - istiod-ca-cert       -> /var/run/secrets/istio
```

4

### ztunnel входит в чужой неймспейс

Получив дескриптор, ztunnel вызывает `setns()` и открывает слушающие сокеты *внутри неймспейса пода*. Право на это даёт одна возможность:

```
securityContext:
  capabilities: { add: [NET_ADMIN, SYS_ADMIN, NET_RAW] }
  privileged: false      # не привилегированный
  runAsUser: 0
```
`SYS_ADMIN` — это и есть разрешение на `setns()`. Заметьте: контейнер **не** privileged и **не** hostNetwork; у пода ztunnel свой собственный адрес.

5

### Разворот пакета — метка и таблица маршрутизации, а не NAT

Сайдкары разворачивали трафик через `REDIRECT` в таблице `nat`. В ambient таблица `nat` внутри пода **пуста**. Работает другое:

```
# внутри сетевого неймспейса пода
$ ip rule show
32764:  from all fwmark 0x111/0xfff lookup 100

$ ip route show table 100
local default dev lo scope host
```
Помеченный пакет уходит в таблицу 100, где маршрут `local ... dev lo` означает «доставить локально». Пакет попадает в сокет ztunnel, **сохранив исходный адрес назначения** — это подход в духе TPROXY, в отличие от NAT, который адрес переписывает. Поэтому ztunnel знает, куда клиент на самом деле шёл, и может это записать в лог и применить политику.

## Схема целиком

Ни один объект Kubernetes у приложения не меняется. Всё происходит на узле: цепочка плагинов, unix-сокет, `setns()` и правило маршрутизации внутри неймспейса пода.

поправка к сказанному ранее

Я объяснял потерю идентичности на egress тем, что «ztunnel живёт в сетевом неймспейсе хоста». **Это неверно**: `hostNetwork` у него не включён, и у пода ztunnel собственный адрес `10.0.0.253`. Наблюдаемый факт остаётся — исходящий вызов виден Cilium с адреса `10.0.0.104`, который оказался интерфейсом `cilium_host` самого узла, то есть идентичность пода на L3–L4 действительно теряется. Но моё объяснение механизма было ошибочным, а точная причина требует отдельной проверки.

## Что такое STRICT

STRICT — это значение поля в ресурсе `PeerAuthentication`, и оно отвечает ровно на один вопрос: **обязана ли входящая связь предъявить идентичность**.

```
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: prod-strict
  namespace: prod      # в istio-system — на весь меш
spec:
  mtls:
    mode: STRICT      # PERMISSIVE (по умолчанию) | STRICT | DISABLE
```

| Режим | mTLS-связь | Открытая связь | Что это значит на практике |
| --- | --- | --- | --- |
| `PERMISSIVE` по умолчанию | принимается | принимается | Шифрование есть у *части* трафика. Не гарантия, а возможность. |
| `STRICT` | принимается | разрыв | Гарантия: без валидного SPIFFE — отказ на транспорте. |
| `DISABLE` | не принимается | принимается | Точечное исключение, обычно для одного порта. |

### Как выглядит отказ

Это отличает STRICT от авторизации сильнее всего. Отказ происходит **до HTTP**:

```
# из пода вне меша в prod при STRICT
$ curl http://checkout.prod.svc.cluster.local/checkout
curl: rc=56   ← connection reset, код 000, а не 403
```
Если в такой проверке приходит `403` — сработал `AuthorizationPolicy`, а не mTLS. Это разные причины отказа, и путать их дорого при разборе инцидента.

### Чего STRICT не делает

Он доказывает, *кто* пришёл, и ничего не говорит о том, *куда* этому кому-то можно — это задача `AuthorizationPolicy`. Он не распространяется на исходящие связи к тем, кто вне меша. Probes от kubelet он пропускает: тот приходит с узла без идентичности, и ztunnel эту дорогу исключает — иначе все поды разом ушли бы в NotReady.

ловушка, в которую мы попали

STRICT обрывает всех, кто ходит в namespace **снаружи меша**, — и это не только приложения. Оператор CloudNativePG опрашивает `/pg/status` каждого инстанса напрямую; его namespace был вне меша, вызов шёл без идентичности, и STRICT его отверг. Кластеры встали в `Instance Status Extraction Error`, оставаясь `Running` для kubectl: оператор не мог ни переключить primary, ни выполнить рестарт. Перед включением STRICT нужен *список* всех, кто ходит в namespace снаружи — операторы, скрейпы, контроллеры, — а не окно наблюдения за трафиком.

и ещё одно, неочевидное

PERMISSIVE **не возвращает видимость**. Естественное «выключим шифрование, чтобы посмотреть в Hubble» не работает: трафик всё равно идёт туннелем HBONE на `15008`, и Cilium по-прежнему увидит туннель, а не порт приложения. Режим mTLS и наличие туннеля — разные вещи. Видимость возвращает только вывод namespace из меша, а вместе с ней и все политики становятся недействующими.

Проверено на local-v1: Istio 1.30.4 ambient поверх Cilium 1.20.1. Вывод `ss`, `ip rule`, `ip route` и содержимое conflist сняты с работающего кластера; поведение STRICT подтверждено пробой из namespace вне меша.
