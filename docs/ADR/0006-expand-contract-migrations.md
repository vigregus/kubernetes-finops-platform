# ADR 0006: Миграции по схеме расширение–сужение

## Статус

Принято

## Контекст

Для контрактов Kafka и REST правило совместимости есть и проверяется в
конвейере. Для схемы базы такого правила не было, хотя задача та же и причина
та же: **код и схему нельзя обновить одновременно**.

```
джоб миграции отработал
        ▼
поды старой версии ещё живут    ← несколько минут
        ▼
поды новой версии поднялись
```

В это окно старый код работает с новой схемой. Если миграция что-то удалила
или переименовала, окно превращается в отказ — причём в отказ, который
не воспроизводится на стенде, потому что там обе стороны обновляются мгновенно.

## Решение

Любое изменение схемы раскладывается на три выкатки. Одношаговых ломающих
миграций не бывает.

```
1. РАСШИРЕНИЕ    добавить новое, оставив старое
                 схема совместима и со старым, и с новым кодом
        ▼
2. ПЕРЕХОД       код пишет в оба, читает из нового
                 заполнение исторических записей
        ▼
3. СУЖЕНИЕ       удалить старое
                 только когда старого кода не осталось
```

### Что запрещено в одной миграции с выкаткой кода

```
DROP COLUMN            переименование колонки
DROP TABLE             сужение типа
RENAME                 добавление NOT NULL к существующей колонке
```

Переименование — это `DROP` плюс `ADD`, замаскированный одним словом, и потому
самый частый способ нарушить правило не заметив.

### Блокировки: отдельная опасность

Миграция может быть совместимой и всё равно устроить простой — если держит
блокировку на большой таблице.

| Операция | Что делает | Безопасный вариант |
| --- | --- | --- |
| `ADD COLUMN` без значения по умолчанию | мгновенно | — |
| `ADD CONSTRAINT ... CHECK` | **полное сканирование под исключительной блокировкой** | `NOT VALID`, затем `VALIDATE CONSTRAINT` |
| `CREATE INDEX` | блокирует запись | `CREATE INDEX CONCURRENTLY` |
| `ALTER COLUMN TYPE` | переписывает таблицу | новая колонка и переход |
| `SET NOT NULL` | полное сканирование | проверка `NOT VALID`, затем замена |

**В этом репозитории уже есть пример нарушения.** Миграция `0002` добавляет

```sql
ALTER TABLE messages ADD CONSTRAINT messages_payload_matches_state CHECK (…);
```

На пустой таблице это мгновенно, поэтому прошло незамеченным. На таблице
с миллиардом сообщений тот же оператор берёт исключительную блокировку и
сканирует её целиком — то есть останавливает переписку на время сканирования.
Правильная форма:

```sql
ALTER TABLE messages ADD CONSTRAINT … CHECK (…) NOT VALID;   -- мгновенно
ALTER TABLE messages VALIDATE CONSTRAINT …;                  -- без блокировки записи
```

Миграции `0002` и `0003` не переписываются: применённый файл неизменяем.
Правило действует со следующей миграции, а этот случай остаётся здесь как
пример того, что «прошло на стенде» ничего не доказывает про объём.

### Каждая миграция имеет предел времени

Миграция, не уложившаяся в отведённое время, **прерывается**, а не
дорабатывает молча. Оператор с `lock_timeout` и `statement_timeout` откатится,
и выкатка остановится — это лучше, чем незавершённая блокировка на горячей
таблице.

### Заполнение исторических записей идёт отдельно

Не внутри миграции. Обновление миллиарда строк одним оператором — это
длинная транзакция, раздувание таблицы и отставание реплики. Заполнение —
пакетами, с возможностью остановить и продолжить, отдельной задачей.

Миграция создаёт **возможность**; заполнение пользуется ею в своём темпе.

## Обоснование

**Отклонено: останавливать сервис на время миграции.** Работает ровно до того
размера, на котором становится нужно, и для мессенджера означает простой.

**Отклонено: миграции вместе с кодом в одном шаге.** Это и есть источник окна
несовместимости; кажется проще, пока выкатка мгновенна.

**Отклонено: инструмент миграций с автоматическим откатом.** Откат схемы —
иллюзия: `DROP COLUMN` не откатывается, данные уже нет. Безопасность даёт
порядок шагов, а не наличие обратного скрипта.

## Последствия

- Изменение схемы — три выкатки и, возможно, недели между ними. Это цена
  работы без простоя, и планировать надо её, а не один шаг.
- Сужение выполняется по показанию, а не по календарю: старый код должен
  исчезнуть, и это видно по метрике версий — та же логика, что в
  [совместимости клиента](../messenger/13-client-compatibility.md).
- Тесты `MIG-001…003` дополняются проверкой на запрещённые операторы: это
  механическая проверка текста миграции в конвейере, а не ревью.
- Файл применённой миграции неизменяем, поэтому исправление ошибки — всегда
  новая миграция. Проверка контрольной суммы в `db/migrate.sh` это
  обеспечивает.
