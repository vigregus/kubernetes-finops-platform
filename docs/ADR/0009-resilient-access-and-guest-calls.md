# ADR 0009: Устойчивый браузерный доступ и звонки по ссылке

## Статус

Предложен

Дополняет [ADR 0007](0007-calls-after-web-push.md). Номер 0008 занят под поиск контактов. Механика, диагностика, фазы и приёмка —
в [части 18](../messenger/18-resilient-access-and-guest-calls.md); здесь только решения, инварианты, границы и отвергнутое.

## Контекст

Цель — максимальная доля состоявшихся звонков и работающего чата из браузера (компьютер, iPhone, Android) при частичных
блокировках, в том числе ТСПУ и DPI. Звонки 1:1 сейчас держатся на WebSocket, прямом WebRTC и одном coturn на UDP: каждая из этих
опор по отдельности блокируется. Отдельно нужны звонки по ссылке для человека без аккаунта.

## Решение

1. **Устойчивость — многоуровневая и по слоям**: достижимость (IP, DNS) → доставка входящего → сигнализация → ICE → медиа →
   деградация качества. Запасные пути в каждом слое, ни один транспорт не обязателен.
2. **Достижимость IP и имени — предпосылка.** Размещение входа и TURN (разные провайдеры и ASN, российские адреса — решение
   владельца) выбирается **до** транспортной лестницы: при адресной блокировке транспорты не помогают.
3. **ICE — приоритет, а не последовательность.** Кандидаты проверяются параллельно; последовательны только наши управляемые
   переходы: ограниченный срок прямой попытки → ICE restart с `relay` → профиль `RESTRICTED`.
4. **Сигнализация надёжна независимо от транспорта**: записанные сигналы с `seq` и идемпотентностью; WebSocket → SSE → HTTPS-опрос
   ускоряют, но не обеспечивают корректность.
5. **TURN/TLS :443 на отдельном публичном адресе и имени, не менее двух TURN у разных провайдеров** (v1). Общий L4/SNI edge —
   отложенная оптимизация (меньше сигнатура, но общий радиус отказа).
6. **Сеть измеряется по событию, а не сканируется.** Диагностика с диагностическими TURN-данными (30–60 с, малая квота), снимки
   «до» и «после», cohort `country + ASN`, рекомендованный профиль с защитой от отравления (аутентифицированные устройства, вклад
   ограничен, минимум устройств и размер cohort, гистерезис, срок рекомендации); локальные наблюдения клиента приоритетнее.
   IP не сохраняется.
7. **Качество уступает раньше связи**: видео → аудио, а не завершение звонка.
8. **HTTPS-only медиа — аварийный выход, не обязательство.** Допустим только с клиентским сквозным шифрованием чанков; без E2EE
   режим не считается готовым к продакшну. Сначала аудио, видео — гипотеза. Нужен отдельный ADR, снимающий инвариант «никакого
   собственного wire protocol».
9. **Метрики успеха разделяют сеть и человека**: `P(звонок дошёл до «можно ответить» | вызываемый доступен)` и `P(медиа
   поднялись | звонок принят)`; `accepted / started` — продуктовая, не сетевая.
10. **Гостевая ссылка — capability на одну комнату**: секрет во fragment, обмен на краткоживущую `GuestSession` в
    `HttpOnly; Secure; SameSite=Strict` cookie (не в `localStorage`), строгая CSP на странице входа, один гость, TTL 15 минут.
    Гость не `User`: участник — `CallPrincipal` (ровно одно из `user_id` / `guest_session_id`). TURN выдаётся только после допуска.

## Инварианты

- Никакого собственного wire protocol (исключение — только по отдельному ADR, п. 8).
- Только браузер: без сырых сокетов, туннелей и подмены TLS-отпечатка.
- Не обманываем фильтрацию: только стандартные транспорты.

## Граница гарантии

Система переживает блокировку отдельных транспортов, но **не** гарантирует работу, если недоступен сам IP или имя сервиса либо
действует allowlist. Несколько TURN — отказоустойчивость, а не защита от целенаправленной блокировки; дальше шла бы система обхода
цензуры, это другая архитектура. По публичным наблюдениям фильтрация звонков (Telegram, WhatsApp) была селективной, одна из
вероятных техник — распознавание STUN по фиксированной сигнатуре; это не подтверждено регулятором или операторами, и мы исходим из
«UDP/STUN может работать — используем; нет — переходим дальше автоматически».

## Отвергнутые альтернативы

| Вариант | Почему нет |
| --- | --- |
| Собственный фреймовый протокол поверх TCP/UDP | становится устойчивой сигнатурой; браузер не умеет сырые сокеты |
| Перестановка URL как выбор транспорта | ICE выбирает по приоритету; порядок не влияет |
| HTTPS-only вместо WebRTC | теряем jitter buffer, оценку полосы, NACK, ICE restart; блокировка очереди в TCP |
| HTTPS-media через доверенный ретранслятор без E2EE | ретранслятор видит открытые кадры, ломает модель доверия WebRTC |
| Постоянное сканирование сети | нагрузка и шум; нужна диагностика по событию |
| Cohort `ASN × браузер × IP-семейство × класс` с первого дня | пустые ячейки, деанонимизация мелких сетей |
| Гость как временный `User` | смешивает аккаунт и право на одну комнату |
| Секрет в query-параметре | уходит на сервер, в журналы и в `Referer` |
| Один TURN | единая точка блокировки |
| Нативный клиент / MASQUE сейчас | другая архитектура; рассматривается, только если браузера перестанет хватать |

## Последствия

- Часть сетей остаётся способной закрыть сервис целиком — принято.
- `call_participants` меняется (`principal_type`, `guest_session_id`): миграция по правилам [ADR 0006](0006-expand-contract-migrations.md).
- Нужны: домен для страницы гостя, TLS на :443 у TURN, решение о площадках и адресах TURN до `RES-005`.
- Телеметрия сети требует решения о приватности (грубые метки, без IP), которое фиксируется при реализации `RES-009`.
- Гостевые звонки включаются только после защиты от злоупотреблений (`LINK-006`, `CALL-017`).
- Реализация — отдельными PR по фазам из [части 18](../messenger/18-resilient-access-and-guest-calls.md#15-задачи-и-порядок).
