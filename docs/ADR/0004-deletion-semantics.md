# ADR 0004: Семантика удаления

## Статус

Принято

## Контекст

Слово «удаление» в проекте означает три разные операции, и они постоянно
смешиваются:

```
1. пользователь удаляет своё сообщение     ← в v1 НЕ входит
2. пользователь стирает учётную запись     ← в v1 входит
3. срок хранения истёк                     ← в v1 входит
```

Схема и [часть 9](../messenger/09-data-lifecycle.md) описывают механизм —
надгробие с разделением конверта и содержимого. Чего нет: **что видит
пользователь** и какие ограничения действуют. Без этого решения интерфейс
и API будут спроектированы под разные модели.

## Решение

### В v1 удаления сообщения нет

Надгробия в первой версии появляются **только** от стирания учётной записи.
Ручного удаления сообщения пользователю не предоставляется.

Причина не в трудоёмкости: механизм уже готов и проверен. Причина в том, что
удаление тянет за собой продуктовые решения, которых пока нет, — окно, поведение
уже доставленного, различие «у себя» и «у всех».

### Когда удаление появится, оно будет «у всех»

```
удалить у всех     запись остаётся, содержимое стёрто,
                   обе стороны видят «сообщение удалено»

удалить у себя     НЕ реализуется
```

«Удалить у себя» отклоняется сознательно. Оно требует видимости на каждого
участника, то есть превращает чтение истории из выборки по беседе в выборку
с проверкой на пользователя — самый горячий запрос продукта становится дороже
ради возможности, которую просят редко. И оно обманывает: собеседник копию
сохраняет, а интерфейс создаёт ощущение, что сообщения больше нет.

### Окно ограничено

Удалять можно **своё** сообщение в течение ограниченного времени. Конкретное
число определяется продуктом; ограничение — принципиально.

Без окна переписка перестаёт быть надёжной записью: любая договорённость
может исчезнуть задним числом через год.

### Что остаётся видимым

| Остаётся | Исчезает |
| --- | --- |
| позиция `conversation_seq` | текст |
| факт «здесь было сообщение» | вложения |
| время отправки | метаданные вложений |
| отправитель — пока жива учётная запись | отправитель при стирании учётной записи |

Ответ на удалённое сообщение не превращается в ответ в пустоту: он ссылается
на надгробие, и это видно.

### Удаление не отменяет доставленного

Сообщение, уже прочитанное собеседником, удаляется — но прочитанного не
вернуть. Удаление убирает сообщение из системы, а не из чужой памяти,
и обещать иное нельзя.

## Обоснование

Три альтернативы рассмотрены и отклонены.

**Физическое удаление строки.** Ломает нумерацию в беседе, ответы на
удалённое, состояние прочтения и восстановление при переподключении. Разобрано
в [части 9](../messenger/09-data-lifecycle.md).

**Удаление у себя.** Цена в горячем пути чтения плюс ложное обещание
приватности.

**Удаление без окна.** Превращает переписку в изменяемый задним числом
документ.

## Последствия

- В v1 API нет метода удаления сообщения; поля `deleted_at` и допустимость
  `NULL` у `payload` при этом существуют — их использует стирание учётной
  записи.
- Клиент обязан уметь отображать надгробие с первой версии: оно встречается
  при стирании учётной записи собеседника.
- Тест `DATA-004` проверяет сохранение порядка при надгробии и относится
  к v1, хотя ручного удаления в ней нет.
- Введение удаления позже — изменение API по правилам расширения из
  [части 13](../messenger/13-client-compatibility.md), а не ломающее.
