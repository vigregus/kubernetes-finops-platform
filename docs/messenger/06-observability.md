# Наблюдаемость мессенджера

> kubernetes-finops-platform · мессенджер, часть 6

Отдельная архитектурная плоскость. Строится не от VictoriaMetrics и Grafana,
а от обещаний пользователю: инструменты выбираются последними, а не первыми.

```
Путь пользователя
      ↓
SLI — что измеряем
      ↓
SLO — какое качество считаем нормой
      ↓
Бюджет ошибок
      ↓
Оповещения
      ↓
Метрики / журналы / трассы
      ↓
Дашборды, расследование, руководства
```

Главное правило, ради которого написан весь документ:

> Компонентные метрики **объясняют** проблему. SLO **сообщает**, что проблема
> вообще существует. Синтетика **проверяет**, что пользовательский путь
> действительно работает. Журналы отвечают «что произошло», трассы — «где и
> сколько это заняло».

## Часть 1. Каталог SLI и SLO

### Четыре разные вещи, которые постоянно смешивают

| Термин | Что это здесь |
| --- | --- |
| **SLI** | фактически измеренная успешность или задержка |
| **SLO** | внутреннее обещание команды |
| **SLA** | внешнее договорное обещание и последствия его нарушения |
| **RTO / RPO** | восстановление после аварии и допустимая потеря данных |

**Внешнего SLA в первой версии нет.** Порядок обратный привычному: сначала SLI
измеряются несколько недель, потом SLO подтверждается на stage, и только если
бизнесу действительно нужно договорное обещание — появляется SLA.

Когда он появится, внутренняя цель обязана быть строже внешней:

```
внутренний SLO   99.95%
внешний SLA      99.9%
```

Иначе команда начинает нарушать контракт ровно в тот момент, когда нарушает
собственную цель, — то есть без единого дня запаса на реакцию.

### SLO принадлежат пользователю, а не Kafka

Плохой SLO — «доступность Kafka 99.99%». Kafka может быть зелёной, а
потребитель realtime сломан, и сообщения не приходят никому. Зелёные поды и
работающий продукт — разные утверждения.

| SLO | SLI | Стартовая цель |
| --- | --- | --- |
| Запись сообщения | корректная уникальная отправка → коммит в Postgres | 99.95% ≤ 1 с |
| Доставка онлайн | коммит → подтверждение хотя бы от одного онлайн-устройства | 99.9% ≤ 2 с |
| Переподключение | сеть вернулась → согласованная беседа | 99.9% ≤ 10 с |
| Вход | корректный вход или обновление токена → успех | 99.95% ≤ 2 с |
| Web Push | событие → принято провайдером | 99% ≤ 30 с |
| Вложение | корректная загрузка → готово | 99% в срок по классу |
| Синтетика | A отправил → B получил | 99.9% успеха |

Это **стартовые цели для проверки на stage**, а не обещания, высеченные в
камне. Число, выбранное до первого измерения, — гипотеза.

### Цель без числителя и знаменателя — не SLI

«99.9% доставки» ничего не определяет, пока не сказано, что считается удачей
и что вообще входит в счёт. Две команды построят два разных запроса и обе
будут правы. Поэтому каждый SLO задаётся четвёркой.

```
годные      что считается успехом
подходящие  что вообще попадает в знаменатель
срок        граница, после которой успех перестаёт быть успехом
период      окно, за которое считается бюджет
```

**Запись сообщения**

```
годные       коммит состоялся И задержка ≤ 1 с
подходящие   аутентифицированные синтаксически верные отправки
исключены    429 (предел частоты), 403 (блокировка), 413 (размер),
             400 (неверное тело)
период       скользящие 30 суток
```

Исключения не косметика: отказ по превышенному пределу частоты — это работающая
защита, а не отказ сервиса. Считая его неудачей, мы наказываем систему за то,
что она сделала правильно.

**Доставка онлайн** — здесь неопределённостей больше всего, и каждая разрешена
явно:

| Вопрос | Решение |
| --- | --- |
| Кто считается онлайн | есть хотя бы одно соединение на момент коммита |
| Момент замера | коммит, не приём запроса |
| Что считается доставкой | подтверждение хотя бы от одного устройства |
| Сколько ждём | 2 с; дольше — неудача, а не «позже» |
| Вкладка в фоне | считается онлайн: соединение живо |
| Закрыл вкладку через 300 мс | исключается из знаменателя |
| Получатель офлайн | не входит в этот SLO вовсе — это Web Push |

```
годные       подтверждение ≤ 2 с от хотя бы одного устройства
подходящие   сообщения, у получателя которых на момент коммита
             было живое соединение
исключены    получатель офлайн; соединение исчезло в пределах 1 с
             после коммита
период       скользящие 30 суток
```

Последнее исключение спорно и потому названо: клиент, отвалившийся сразу после
коммита, не доказывает ни работу системы, ни её отказ. Считать его неудачей —
значит привязать SLO к качеству чужого Wi-Fi.

**Правило для всех остальных SLO:** пока четвёрка не записана, показатель не
считается определённым и не попадает на дашборд SLO. Вычисление закрепляется
правилом записи в VictoriaMetrics — не запросом в панели, который каждый
перепишет по-своему.

Задержка вложения без разбивки по размеру бессмысленна: один срок на картинку
в 200 КБ и на файл в 20 МБ описывает либо слишком мягко, либо заведомо
недостижимо.

```
image   ≤ 10 МБ
file    ≤ 20 МБ
voice   ≤ N минут
```

### Сохранность — не SLO, а инвариант

Для принятого сообщения:

```
успешный HTTP-ответ  ≡  коммит в Postgres состоялся
```

После этого действует не процент, а запрет:

```
lost_accepted_messages = 0
```

Не «99.99% сообщений не потерялись». Это корректность, а у корректности нет
бюджета. Формулировка через проценты незаметно превращает потерю данных в
приемлемую статистику.

Восстановление — отдельно и по-другому:

```
отказ одной зоны        цель RPO = 0
региональная авария     RPO по политике копий и репликации
                        RTO — часы, согласно текущей архитектуре
```

### Главный SLI: сквозной путь сообщения

Не производный показатель, а объект первого класса.

```
t0  Браузер A          POST /messages
t1  API                коммит в Postgres
t2  outbox-relay       запись взята в аренду
t3  outbox-relay       публикация в Kafka подтверждена
t4  consumer-realtime  получил из Kafka
t5  consumer-realtime  опубликовал в Centrifugo
t6  Браузер B          получил
t7  Браузер B          подтвердил
```

| Отрезок | Что измеряет |
| --- | --- |
| `T_commit` | t1 − t0 |
| `T_outbox` | t2 − t1 |
| `T_kafka` | t3 − t2 |
| `T_consumer` | t4 − t3 |
| `T_realtime` | t6 − t4 |
| `T_delivery` | t7 − t1 |

Ради этого всё и делается. Без разбивки «p99 доставки 8 секунд» — повод для
гадания; с разбивкой:

```
коммит      80 мс
outbox      50 мс
Kafka       40 мс
потребитель 7.5 с   ← вот здесь
Centrifugo  100 мс
```

## Часть 2. Контракт телеметрии

### Наблюдаемость никогда не находится на критическом пути

```
Tempo недоступен
VictoriaLogs недоступен
VictoriaMetrics недоступен
        ↓
отправка сообщений ПРОДОЛЖАЕТСЯ
```

Из этого следует модель: метрики **снимаются** опросом, журналы пишутся в
stdout, трассы уходят асинхронной пачкой. Никогда:

```
send_message()
remote_logging_service.write(...)   ← нет
commit()
```

Инвариант: **потеря телеметрии допустима; потеря сообщения из-за телеметрии —
нет.** Это проверяемое требование, а не пожелание: тест отказа гасит Tempo и
VictoriaLogs и убеждается, что отправка идёт.

### Никаких идентификаторов в метках метрик

Самое дорогое правило всей телеметрии.

```
messenger_messages_total{user_id=…, conversation_id=…, message_id=…}
```

Так нельзя. Кардинальность уничтожит хранилище метрик — причём тихо и
в момент роста нагрузки, то есть ровно тогда, когда метрики нужнее всего.

| Метки метрик | Поля журналов и трасс |
| --- | --- |
| `service`, `environment`, `cluster`, `region`, `az` | `message_id`, `event_id` |
| `route`, `operation`, `result`, `error_class` | `conversation_id`, `user_id` |
| `event_type`, `consumer`, `cache`, `version` | `trace_id`, `span_id` |

Маршрут в метке — шаблон, а не путь: `route="/conversations/{id}/messages"`,
никогда `/conversations/123/messages`.

### `message_id` и `trace_id` — разные вещи

`trace_id` нужен системе наблюдаемости. `message_id` нужен предметной области.
Поэтому поддержка обязана уметь:

```
message_id → журналы → trace_id → Tempo
```

а не требовать от пользователя сообщить идентификатор трассы, которого он
никогда не видел.

**Чего в этом пути ещё нет.** Отправитель и потребитель пишут запись только
тогда, когда что-то пошло не так: отказ публикации, отказ доставки, отсеянный
повтор, неразбираемый тип события. У успешно доставленного сообщения записей
в конвейере нет ни одной, а значит путь «`message_id` → журналы» начинается не
с журналов, а с базы или с Tempo:

```
message_id → строка outbox в Postgres  ┐
                                       ├→ trace_id участка → Tempo
message_id → атрибут спана в Tempo     ┘
```

Это названо, а не умолчано: разбор успешного сообщения по журналам сегодня
не работает, и обещать его нельзя. Записи на успешном пути — отдельная работа
(разбивка SLI по доставке и без них собирается по метрикам).

### Контекст трассировки проходит через outbox и Kafka

Границу контекст переходит двумя разными способами, и это не избыточность:

```
трасса API
   └ trace_id, span_id → тело события → outbox-relay     ← отправитель ставит ссылку
                                            │
                         свой участок ──────┘
                                            └ traceparent → заголовок Kafka → потребитель
```

Тело события несёт **пару участка API**: по ней отправитель ставит ссылку на
запрос, которого к моменту отправки уже нет. Заголовок Kafka несёт **участок
самого отправителя**: он и есть контекст создания записи, и потребитель ставит
ссылку на него. Тело при этом остаётся запасным путём для события, записанного
прежней версией отправителя, — там есть `trace_id`, но нет участка, и ссылка
тогда не строится вовсе (подставить случайный идентификатор значило бы
соврать).

Но **один огромный span на всю дорогу не держится открытым**: асинхронные
участки связываются ссылками между span, а сквозным ключом корреляции остаётся
`message_id`.

**Что из этого уже работает.** Всё, включая экспорт. Посредник API принимает
чужой `traceparent` или заводит свой, кладёт `trace_id` в каждую запись журнала
и в заголовок ответа `X-Trace-Id`, а в outbox — в тело события (`trace_id` и
`span_id` есть в контрактах `message.created.v1` и `message.content.v1`).
Отправитель поднимает пару оттуда и ставит в заголовок записи Kafka
`traceparent` **своего** span `kafka.produce`; потребитель берёт контекст из
заголовка, а тело — запасной путь для записи, отправленной прежней версией
отправителя.

Экспорт идёт **через коллектор**, а не прямо в Tempo: адрес хранилища перестаёт
быть зашитым в каждый сервис, и там же решается, что хранить. Головная выборка
в сервисе — сплошная (`always_on`): решение по ошибке принимается, когда трасса
уже завершена, а головная выборка этого не умеет. Доля хранения задаётся
хвостовой политикой коллектора.

Формат чужой намеренно: это те же 16 и 8 байт, что кладёт в заголовок
OpenTelemetry. Идентификаторы, лежавшие в журналах и в outbox до появления
экспортёра, оказались теми же самыми, и связывать записанное задним числом не
пришлось. `tracestate` не заполняется: своего состояния трассировки у нас
пока нет, а пустое поле в заголовке — это байты
на каждое событие и ничего больше.

**Три трассы, а не одна.** Путь одного сообщения — это трасса запроса API,
трасса отправителя outbox и трасса потребителя, связанные **ссылками**.
Продолжить чужую трассу через границу нельзя: к моменту, когда отправитель
берёт запись, процесс API уже ответил клиенту, и родителя, которому можно быть
ребёнком, больше не существует. Связь ставят ссылки, а не родительство, — так
предписывает и спецификация обмена сообщениями.

Отсюда следствие, которое надо знать **до** первого разбора инцидента:
`trace_id` в записях отправителя и потребителя — идентификатор **их
собственной** трассы, и поиск по `trace_id` из заголовка `X-Trace-Id` найдёт
одну часть пути, а не три. Сквозная связь держится на `message_id` (см. выше):
он выставлен атрибутом `messaging.message.id` на спанах `kafka.produce` и
`centrifugo.publish`, а в записях конвейера — там, где такая запись вообще
появляется (см. ниже).

### Выборка: не 100%

При целевых 2 500 отправок/с и 12 500 доставок/с сплошная трассировка сама
становится нагрузкой сопоставимого размера.

| Поток | Доля |
| --- | --- |
| Обычный трафик | 1–5% |
| Синтетика | 100% |
| Ошибки | максимум возможного |
| Административные операции | 100% |
| Операции безопасности | 100% |

Плюс временное включение подробной выборки для пользователя, беседы или
сервиса на 10–30 минут — иначе расследование редкого дефекта упирается в то,
что его след не сохранился.

**Где принимается решение.** В коллекторе, а не в сервисе. Сервис отправляет
всё, а доля хранения задаётся хвостовыми политиками: ошибки — целиком,
медленные — по порогу своей стадии конвейера, остальное — единицы процентов.
Головная выборка в сервисе стояла бы здесь неправильно дважды: она решает до
того, как ошибка случилась, и потому не может знать, что трассу надо
сохранить, — а выставленная в ней доля отсекала бы 95 % ошибок молча.

Из таблицы выше сегодня исполнены две строки — «ошибки» и «обычный трафик».
Синтетика, административные операции и операции безопасности требуют политики
**по атрибуту** вида операции, а не вероятностной:
вероятность, посчитанная по `trace_id`, у трёх трасс одного сообщения даёт три
независимых решения, поэтому «удержать всю цепочку» вероятностной политикой не
выражается вовсе.

Отдельно: независимость решений по трём трассам означает, что ссылка может
указывать на трассу, которую выборка не сохранила. Это не дефект, а свойство
«трёх трасс» и хвостовой выборки; в таких случаях разбор идёт от `message_id`
по журналам, и делать переход по ссылке обязательным шагом расследования
нельзя.

## Часть 3. Каталог метрик

Четыре уровня. Наверх, в SLO-дашборд, идёт только первый.

### A. Продуктовые метрики — источник SLI

```
messenger_message_send_operations_total{result="success|failed"}
messenger_message_commit_duration_seconds
messenger_message_delivery_total{result="acked|timeout"}
messenger_message_delivery_duration_seconds
messenger_reconnect_total{result="recovered|sync|failed"}
messenger_sync_duration_seconds
messenger_auth_operations_total{operation="login|refresh", result="success|failure"}
messenger_attachment_processing_duration_seconds{type="image|file|voice", result=…}
messenger_push_delivery_duration_seconds{result="accepted|failed"}
```

### B. Метрики конвейера

```
messenger_outbox_pending_events
messenger_outbox_oldest_unprocessed_age_seconds
messenger_outbox_claim_duration_seconds
messenger_outbox_publish_total{result}
messenger_kafka_consumer_lag_seconds{consumer}
messenger_consumer_processing_duration_seconds{consumer}
messenger_duplicate_events_total{consumer}
messenger_realtime_publish_duration_seconds
messenger_client_gap_detected_total
messenger_recovery_total{method="centrifugo|database"}
```

**Возраст самой старой необработанной записи важнее их количества.** Сто тысяч
строк в outbox могут быть нормой при высокой пропускной способности; пятнадцать
минут возраста — отказ при любой. Порог по количеству пришлось бы менять при
каждом изменении нагрузки, порог по возрасту — никогда.

То же и с Kafka: `lag` в сообщениях зависит от размера потока, `lag` в секундах
означает одно и то же всегда.

### C. RED — для каждого сервиса

`API`, `consumer-realtime`, `consumer-notifications`, `consumer-unread`,
`attachment-worker`, `outbox-relay`:

```
http_requests_total{route, method, status_class="2xx|4xx|5xx"}
http_request_duration_seconds{route}
```

### D. USE — для инфраструктуры

| Postgres | Kafka | Redis |
| --- | --- | --- |
| соединения из максимума | скорость записи и чтения | занятая память |
| CPU, память, задержка ввода-вывода | отставание в сообщениях и секундах | вытеснения |
| блокировки, взаимоблокировки | партиции без полного набора реплик | команд в секунду |
| задержка транзакций | недоступные партиции | задержка |
| отставание реплики, рост WAL | задержка запросов | соединения, заблокированные клиенты |
| долгие транзакции, эффективность кеша | занятое место | переключения ролей |

Redis измеряется по трём ролям отдельно — `realtime`, `app-cache`, `security`:
вытеснения в кеше профилей и вытеснения в presence означают разное.

### Centrifugo — отдельный случай

Нагрузка, ориентированная на соединения, ведёт себя не как обычный API.

```
connected_clients              publish/sec
connections/sec                reconnect/sec
disconnects/sec                recovery_success_total
subscriptions                  recovery_failed_total
subscriptions/client           recovered_false_ratio
client_queue_size              slow_consumer_disconnects
задержка публикации в Redis
```

И обязательно **в разрезе подов**. Иначе картина «10 подов, 300 тысяч
соединений» выглядит благополучно, скрывая:

```
под 1   100 000
остальные  22 000 каждый
```

— то есть один под на грани, а среднее прекрасно.

### Телеметрия браузера обязательна

Без неё настоящий SLI не измерить. «Centrifugo опубликовал» — ещё не
«сообщение отрисовано у B».

```
ws_connected      message_received    recovery_success
ws_disconnected   message_rendered    recovery_failed
ws_reconnected    delivery_ack        sync_started / sync_finished
gap_detected      js_error
```

С обязательными пачками, выборкой и ограничением частоты: клиентская
телеметрия от миллиона браузеров — это отдельный входящий поток, и он не должен
уметь положить приём телеметрии.

## Часть 4. Стандарт журналов и трасс

### Только структурированный JSON

Обязательный конверт у каждой записи:

```
timestamp   level      service     environment   version
event       result     error_code
trace_id    span_id    request_id
message_id  event_id
log_stream  logger     _msg
```

```json
{
  "timestamp": "2026-09-13T16:42:07.113Z",
  "level": "INFO",
  "service": "consumer-realtime",
  "environment": "prod",
  "version": "sha256:…",
  "event": "message_realtime_publish",
  "log_stream": "application",
  "logger": "messenger.services.realtime_delivery",
  "_msg": "сообщение отдано в канал",
  "message_id": "…",
  "event_id": "…",
  "trace_id": "…",
  "span_id": "…",
  "result": "success",
  "duration_ms": 37
}
```

**`event` и `_msg` — разные поля, и оба обязательны.** `event` — машинное имя
происшествия: по нему строятся запросы, оповещения и панели, и потому оно
не меняется от правки текста. `_msg` — текст для человека, и имя у него
не случайное: VictoriaLogs берёт содержимое записи из поля `_msg`, а всё
остальное кладёт рядом. Запись, у которой такого поля нет, оседает
в хранилище подсказкой «missing _msg field» вместо текста — так уже
терялось два десятка тысяч записей в час от соседей по кластеру
(см. `gitops/02-infra/observability-objects/promtail/values.yaml`).

**Поле потока называется `log_stream`, а не `stream`, и это не вкусовщина.**
`stream` в Kubernetes уже занят: сборщик ставит такую метку каждой строке
со значением `stdout` или `stderr`. Два разных смысла под одним именем
хранилище сводит в одно поле, и чьё-то значение теряется. Измерено на живом
хранилище до переименования: из 168 617 записей `http_request` за сутки
у 226 поток приложения оказался затёрт меткой контейнера — то есть запись
об обращении молча становилась неотличимой от обычного вывода процесса.

Заметить это по коду нельзя: и приложение, и сборщик по отдельности
работают правильно. Видно только в хранилище, и только если спросить.

**У записи библиотеки событие называется `library`, а не как её журнал.**
Подставлять вместо события имя журнала — привычное умолчание, и оно смешивает
два пространства имён в одном поле: рядом с `login_rejected` оказывается
`aiokafka.consumer.group_coordinator`, после чего запрос по `event` перестаёт
означать «наше событие». Имя журнала при этом не теряется — оно всегда лежит
в `logger`, и «чья это жалоба» видно отдельным полем.

Библиотека, которая завела собственный обработчик, усыновляется: у uvicorn
обработчик снимается, распространение включается, и восемь строк на каждый
жизненный цикл пода («Started server process», «Application startup
complete», «Shutting down») уходят в том же конверте, а не обычным текстом
без уровня и без события. Единственное исключение — журнал, у которого
обработчика нет: он молчит намеренно (так устроен `--no-access-log`),
и включать его обратно значило бы получить вторую копию записи об обращении,
которую посредник пишет сам.

Конверт заполняет обработчик журнала, а не вызывающий код: `service`,
`environment` и `version` приходят из окружения при настройке, а
`trace_id`, `span_id` и `request_id` — из контекста задачи. Забыть про
`service` в одном модуле из сорока — вопрос времени, а запись без него
не связывается ни с чем.

### Содержимое не логируется никогда

Ни при каком уровне подробности:

```
текст сообщения          JWT и токен обновления
пароль                   токен подтверждения адреса
заголовок авторизации    подписанная ссылка на объект
cookie
```

Это проверяется автоматически, а не обещается. Тест `OBS-SEC-001`:

```
отправить сообщение с текстом «MY_SECRET_CANARY_123»
       ↓
поиск по VictoriaLogs
       ↓
ожидается 0 совпадений
```

Подписанная ссылка в списке не случайно: она даёт доступ к объекту тому, кто
её прочитал, то есть журнал превращается в средство доступа к чужим вложениям.

### Потоки журналов разделены

| `log_stream` | Назначение | Срок хранения | Кто пишет |
| --- | --- | --- | --- |
| `application` | работа сервиса и его зависимостей | короткий | все сервисы |
| `access` | обращения HTTP и WebSocket | средний | посредник API |
| `security` | вход, отказы в доступе, злоупотребления | длинный | вход, сессии, ограничитель |
| `audit` | привилегированные действия support/moderator/admin | длинный | никто: ролей в v1 нет |
| `synthetic` | результаты сквозных проб | средний | никто: синтетика в G5 |

Один срок хранения на всё означает либо дорогой отладочный мусор, либо
потерянный аудит.

**`deployment` в этой таблице нет намеренно.** Смена версии и конфигурации —
не запись журнала приложения, а эксплуатационное событие по схеме
`packages/contracts/events/operational-event.v1.json`: у него свой конверт
(`event_type`, `actor`, `git_sha`), свой производитель (Argo CD, а не наш
код) и своя точка входа в хранилище. Часть 5 описывает его отдельно; здесь
он упоминается только чтобы не искать его среди потоков.

### Поток выбирается по вопросу, на который отвечает запись

Правило одно, и оно не про источник записи, а про её смысл:

```
кого пустили, кого нет и почему      → security
обращение снаружи                    → access
привилегированное действие           → audit
что происходит внутри сервиса        → application
```

Отсюда следствие, которое на глаз выглядит ошибкой: «счётчик лимитов
недоступен» уходит в `security`, хотя причина — отказ Redis. Запись отвечает
не «что сломалось», а «какое решение о доступе принято, пока защита
не работает», и окно без работающего ограничителя обязано пережить недельный
срок обычных журналов. Ровно так же «Keycloak не ответил на обмен» и «обмен
отклонён» — одно событие `token_exchange` и один поток: для субъекта это
один и тот же факт — он не вошёл.

### Каталог событий, а не договорённость об именах

Имя события и его поток кладёт вызывающий код, и без проверки через полгода
в хранилище оказывается `auth_fail` рядом с `login_rejected` — два имени
одного происшествия, ни по одному из которых не построить ни запрос,
ни оповещение. Поэтому каталог живёт в `scripts/check-log-streams.py`,
а проверка разбирает вызовы по AST и требует:

```
у каждого вызова журнала есть extra с event и result
имя события есть в каталоге, иначе — впиши и выбери поток
поток совпадает с каталогом; application не пишется явно
событие, которое больше никто не пишет, из каталога убирается
у события в security есть поле субъекта решения (обычно user_id)
```

Проверка стоит в `make local-test` и в конвейере рядом с проверкой слоёв.
Цена вопроса — секунды на сборке; альтернатива — обнаружить расхождение
на разборе инцидента, когда искать уже поздно.

### У security обязан быть субъект, а не только факт

Запись `event=user_created, result=success` и текстом «заведена учётная
запись» выглядит полной, пока не встаёт вопрос «чья». Поток `security`
существует ровно для того, чтобы ответить «кого пустили, кого нет и
почему» — без идентификатора субъекта решения запись отвечает только
на «что», и как расследование ответ бесполезен: `trace_id`/`request_id`
в конверте есть всегда, но по ним не спросить «покажи все security-события
этого пользователя за месяц», только «этого одного запроса».

Найдено не по чтению кода, а по прямому запросу к VictoriaLogs после
одного из деплоев: `user_id` был доступен в коде каждой из восьми точек
вызова — `result.user.user_id`, `auth.user.user_id`, параметр функции —
и просто не передавался в `extra`. Правило было и раньше, но только
в виде таблицы соответствия («Никаких идентификаторов в метках метрик»,
выше): она называет `user_id` полем журналов в противовес меткам метрик,
но не обязывает класть его в каждое событие потока `security`. Разница
ощутима: правило-таблица не ловится проверкой, правило-требование —
ловится (см. `SECURITY_SUBJECT_UNKNOWN`/`SECURITY_SUBJECT_FIELD` в
`scripts/check-log-streams.py`).

Два именованных исключения, а не общая оговорка:

```
субъект по построению неизвестен   token_exchange, token_rejected,
                                    login_rejected — отказ случился
                                    до того, как личность установлена;
                                    требовать user_id значило бы
                                    требовать выдуманное значение

решение не по учётной записи       rate_limit_degraded — лимитер общий,
                                    субъект решения — ключ лимита,
                                    не обязательно пользователь
```

Новое событие в security без поля субъекта проверка отклоняет явно,
а не после первого расследования, где такого поля не хватило.

### Трассы — OpenTelemetry

```
POST /conversations/{conversation_id}/messages
├─ auth.check
│   └─ POST                    ← httpx: обмен с Keycloak
├─ postgres.transaction
│   ├─ membership.check
│   │   └─ SELECT              ← asyncpg: блокировка строки беседы
│   ├─ message.insert
│   │   └─ INSERT              ← asyncpg
│   └─ outbox.insert
│       └─ INSERT              ← asyncpg
└─ response

outbox-relay              consumer-realtime
├─ outbox.claim           ├─ kafka.consume
│   └─ WITH               ├─ SET / GET         ← redis: кеш доставки
└─ kafka.produce          └─ centrifugo.publish
                              └─ POST         ← httpx: API Centrifugo
```

Три трассы, связанные ссылками, а не одна растянутая: асинхронная граница —
это именно граница, и растянутый span скрывает, сколько запись пролежала в
очереди.

Спаны со стрелкой — не наши: их создаёт инструментация библиотек, которой
сервис ходит наружу (см. «Кто спанов не даёт» ниже). Их отсутствие видно не
сразу, поэтому о них стоит сказать отдельно: без них `postgres.transaction`
показывает сорок миллисекунд и не отвечает, на что они ушли.

**Почему `membership.check` внутри `postgres.transaction`.** Проверка членства
*и есть* блокировка строки беседы: `lock_active_conversation` делает
`SELECT … FOR UPDATE` и возвращает `None`, если пользователь не участник. Вне
транзакции она смысла не имеет — между проверкой и вставкой помещается гонка,
и в беседу, из которой только что вышли, уедет сообщение. Вынести её отдельным
чтением до транзакции — тот же разрыв плюс лишний обход базы. Дерево нарисовано
по коду, а не по тому, как удобнее смотреть.

**Имена спанов.** Корень запроса — `{метод} {шаблон маршрута}`, например
`POST /conversations/{conversation_id}/messages`. Шаблон, а не путь:
идентификатор беседы в имени завёл бы имя на каждый разговор, то есть ту же
кардинальность, от которой ушли в метках маршрута.

Спецификация семантических конвенций для обмена сообщениями предписывает
другую форму — `{messaging.operation.name} {destination}`, например
`send messenger.events.v1`. Наши имена короче, и это **осознанное расхождение**:
они совпадают с деревом выше и держат кардинальность низкой. Спецификация его
допускает — системные конвенции «MAY specify different span name format and
then MUST document it», — а обязанность документировать исполнена здесь.

**Вид спана на каждой границе** — не украшение: от него зависит, нарисует ли
прибор связь производителя с потребителем или покажет два несвязанных span.

| Span | Вид | Почему |
| --- | --- | --- |
| Корень запроса API | `SERVER` | принял входящий запрос |
| `kafka.produce` | `PRODUCER` | его контекст и есть контекст создания записи |
| `kafka.consume` | `CLIENT` | операция `receive`, а не `process` |
| `centrifugo.publish` | `CLIENT` | контекст создания записи в Centrifugo не кладётся |
| `consumer-realtime` | `CONSUMER` | обрабатывает принятую пачку |

**Кто спанов не даёт — и чем это не равно «глубоко не видно».** Разделение,
которое легко потерять: **ни один объект на пути сообщения спанов не создаёт** —
Postgres, Kafka, Redis, Centrifugo и Keycloak по OTLP не говорят и говорить не
будут ни при какой настройке. Но спаны даёт **наша сторона**: библиотека,
которой сервис ходит наружу. Драйвер базы, клиент кеша и HTTP-клиент
инструментированы и подключены в `telemetry/tracing.py` — и эти спаны
настоящие.

Разница не косметическая, и на ней легко ошибиться в обе стороны. Сервер
молчит — значит, «трассировать нечего», и на этом вывод обрывается. На самом
деле вопрос стоит иначе: **есть ли инструментированный клиент**. У Postgres он
есть (asyncpg), у Redis есть, у httpx есть — а у самого Postgres, Redis и
Keycloak нет и не нужно.

| Объект | Спан сервера | Спан клиента | Что это даёт на практике |
| --- | --- | --- | --- |
| PostgreSQL | нет | `SELECT` / `INSERT` / `UPDATE` (asyncpg) | время внутри `postgres.transaction` разложено: видно, что было дорого — сам запрос или ожидание блокировки |
| Redis | нет | `SET`, `GET`, а у конвейера — `SET GET` (redis) | обращения к кешу доставки отделены от публикации в Centrifugo |
| Keycloak | нет | `POST` / `GET` (httpx) | обмен токена и выборка ключей видны внутри `auth.check` |
| Centrifugo | нет | `POST` (httpx) | HTTP-вызов API виден внутри `centrifugo.publish` |
| Kafka | нет | нет | брокер **переносит** контекст заголовком, но не создаёт своего; `kafka.produce` и `kafka.consume` — наши |
| Шлюз (Istio) | нет | нет | трассировка в сетке не включена вовсе — это G1, не G2 |

Kafka в этой таблице — единственная строка, где «нет» сказано честно и про
клиент: `aiokafka` не инструментирован, и наши `kafka.produce` / `kafka.consume`
остаются единственным, что на этой границе есть.

**Чего в этих спанах нет.** У полезного здесь есть края, и о них лучше знать
до разбора, а не во время:

* **Ожидание соединения в пуле.** Асинхронный драйвер не оборачивает
  `pool.acquire`, а только работу по уже взятому соединению. Пять секунд,
  отданные в `acquire_timeout_seconds`, внутрь спана запроса не попадают
  отдельной строкой — время видно в спане транзакции, а причина нет.
  Это первое, что стоит вспомнить, увидев медленный `postgres.transaction`
  без медленных запросов внутри;
* **Параметры запросов.** `capture_parameters=False`: в спан едут
  `db.statement` и адрес базы, а значения подстановок — нет. Токенов и
  содержимого сообщений в трассах не появляется по построению, а не по
  договорённости;
* **Аргументы команд Redis.** Инструментация кладёт в `db.statement`
  обезличенный вид — `SET ? ?`, — то есть имя команды без ключа и без
  значения. Ключи кеша образуются из `message_id`, и в трассе их нет.
  У конвейера (`remember_half` кладёт половину и тут же её читает) имя спана —
  **все команды через пробел**, `SET GET`, а в `db.statement` — они же
  построчно, и в атрибуте `db.redis.pipeline_length` их число. Искать конвейер
  по `SET` не выйдет, и это стоит помнить до первого такого поиска;
* **Заголовки и тела HTTP.** Захват заголовков включается только переменными
  окружения (`OTEL_INSTRUMENTATION_HTTP_CAPTURE_HEADERS_CLIENT_*`) и по
  умолчанию выключен; тела не пишутся никогда. На всякий случай: если эти
  переменные кто-то выставит, в спаны уедут ключи доступа — поэтому при
  старте с ними пишется предупреждение `tracing_config`;
* **Имя спана запроса — первое слово SQL.** У вставки это `INSERT`, у выборки
  `SELECT`, а у захвата пачки в outbox — `WITH`, потому что запрос начинается
  с CTE. Искать аренду по `SELECT` бесполезно, и это не дефект имени, а его
  природа.

**Инструментация входа не подключается, и это другое решение.** `-fastapi` не
подключён сознательно: спан входящего запроса у нас свой, и вторая пара на то
же обращение дала бы два корня там, где контракт обещает один. Наружу —
подключается, на вход — нет.

### `span_id` в записи журнала — идентификатор настоящего span

Поле `span_id` в конверте (§ «Только структурированный JSON») обязано совпадать
с идентификатором span, который был текущим в момент записи. Требование звучит
самоочевидно, а нарушается незаметно: выдуманный идентификатор выглядит ровно
так же, как настоящий, и расхождение обнаруживается только тогда, когда запись
из журнала сопоставляют со span в Tempo, — то есть на разборе инцидента, когда
искать уже поздно.

Поэтому генератор идентификаторов один: **`tracing.span()`**. Он создаёт span,
берёт его `SpanContext` и кладёт пару `trace_id`/`span_id` в те же contextvars,
из которых её читает форматтер журнала. `JsonFormatter` при этом не меняется
вовсе, а расхождение становится невозможным по построению, а не по
договорённости. Синтетический путь остаётся один — запуск без коллектора:
идентификаторы тогда выдуманы, но связывают записи между собой согласованно.

**Вложенные span инвариант не нарушают.** Внутри `postgres.transaction` конверт
несёт `span_id` span транзакции, а не корневого: запись принадлежит ближайшей
единице работы, и оба идентификатора настоящие. Именно поэтому цель ссылки из
outbox — **якорь** корневого span запроса, а не «текущий span»: иначе
добавление любого span внутри обработчика молча сдвинуло бы ссылку.

Держится это не честным словом, а проверкой: тест сравнивает `span_id` из
записанного JSON с `format_span_id(span.get_span_context().span_id)` и падает
при любом расхождении.

**У инварианта появилась цена, и её надо назвать.** Спаны библиотек
(см. «Кто спанов не даёт») создаются **в обход** `tracing.span()`: они
становятся текущими — значит, обычная запись журнала получит их `span_id`, —
но в contextvars не пишут. Пока внутри такого спана журнал не пишут,
расхождение невозможно: запись берёт идентификатор охватывающего спана, и он
настоящий.

Отсюда правило, которое держится не дисциплиной, а проверкой: **слой
`repositories` не пишет в журнал ни строки.** Всё, что он делает, — вызовы
драйвера; запись, сделанная внутри спана драйвера, получила бы `span_id`
охватывающего спана, и связь «запись ↔ спан» разошлась бы ровно там, где её
ищут. Идентификатор при этом настоящий, поэтому по отдельности ни в журнале,
ни в трассе этого не видно — то есть заметить нечем. Запрет исполняет
`scripts/check-log-streams.py` рядом с проверкой каталога событий.

## Часть 5. Дашборды, оповещения, руководства

### Бюджет ошибок

Период — **скользящие 30 суток**, одинаковый для всех SLO: разные окна у разных
показателей делают сравнение бюджетов бессмысленным. При `SLO = 99.95%` бюджет —
это `0.05%` за период. Основное оповещение
формулируется не как «CPU > 80%», а как **скорость сжигания бюджета**.

| Скорость | Окна | Во сколько раз быстрее нормы | Действие |
| --- | --- | --- | --- |
| Быстрая | 5 мин + 1 ч | ~14× | будить немедленно |
| Средняя | 30 мин + 6 ч | ~6× | будить |
| Медленная | 6 ч + 3 дня | 1–2× | заявка, предупреждение |

Два окна в каждой строке не для красоты: короткое ловит аварию быстро, длинное
отсекает единичный всплеск, который иначе поднимет человека ночью зря.

Смысл сдвига: не «отставание Kafka 10 000», а «если так продолжится, месячный
бюджет кончится через несколько часов».

### Компонентные оповещения становятся диагностикой

```
БУДИТЬ:
  сжигание бюджета SLO доставки

в контексте:
  отставание Kafka ↑
  возраст outbox ↑
  ошибки потребителя ↑
```

Одно оповещение с контекстом вместо трёх независимых. Именно так уменьшается
усталость от оповещений — не снижением чувствительности, а тем, что одна
авария перестаёт звонить трижды.

Приоритеты уже заданы в каталоге тестов: возраст outbox и Postgres будят,
недоступность индикатора «печатает» не будит вообще.

### Семь дашбордов, а не сорок

| № | Дашборд | На какой вопрос отвечает |
| --- | --- | --- |
| 01 | SLO Overview | пользователи сейчас получают сервис? |
| 02 | Messaging Pipeline | где именно тормозит путь сообщения? |
| 03 | Realtime | WebSocket, Centrifugo, переподключение, восстановление |
| 04 | Data Plane | Postgres, Kafka, Redis |
| 05 | Auth · Push · Attachments | вспомогательные критические пути |
| 06 | Platform | Kubernetes, Istio, Cilium, узлы |
| 07 | Release | что изменилось после выкатки |

Сорок дашбордов означают, что в момент аварии никто не знает, какой открыть.

**Главный дашборд** читается за десять секунд:

```
строка 1   доступность отправки · доступность доставки · p99 доставки
           успех переподключения · успех синтетики · остаток бюджета

строка 2   темп отправки · темп доставки · 5xx · таймауты · p50 / p95 / p99

строка 3   возраст outbox · отставание Kafka в секундах
           публикации Centrifugo · подтверждения клиентов
```

Первая строка отвечает «проблема есть?», вторая и третья — «где она?».

### Эксплуатационные события и отметки на графиках

Расследование начинается с вопроса «что изменилось», и ответ должен быть на том
же графике, а не в чужой истории конвейера.

```
p99 доставки

8 с |                         ╭──────
    |                         │
4 с |                    ╭────╯
    |                    │
1 с |────────────────────┴────────────
           │        │          │
           ▲        ▲          ▲
       выкатка   изменение  переключение
       api abc   таймаута      Redis
```

**Источником истины не является ни Grafana, ни VictoriaLogs.** Хранилище,
потерю которого мы заранее разрешили, не может быть авторитетной записью
о том, что происходило в проде.

```
Git · Argo CD · Terraform · аудит флагов
        авторитетная запись об изменении
                    │
                    ▼
              VictoriaLogs
        поисковая проекция для расследования
                    │
                    ▼
                 Grafana
                отображение
```

Проекция теряется и строится заново из авторитетных источников. Аннотация,
созданная только через API Grafana, не переживает ни переноса, ни самой
Grafana — поэтому она необязательное дублирование, а не запись.

Схема события — `packages/contracts/events/operational-event.v1.json`:

```json
{
  "timestamp": "2026-09-13T20:14:22Z",
  "event_type": "deployment",
  "environment": "prod",
  "service": "api",
  "version": "sha256:abc123",
  "previous_version": "sha256:def456",
  "git_sha": "914b20d",
  "actor": "argocd",
  "result": "success"
}
```

### Событие выкатки берётся из Argo CD, а не из CI

Это не деталь реализации. CI знает «образ собран» — а это ещё не «образ
работает»: между сборкой и запуском лежат запрос на слияние, синхронизация и
выкатка подов, каждый из которых может не случиться или занять часы. Отметка,
поставленная по факту сборки, врёт о времени — а ко времени к ней и обращаются.

```
коммит → сборка образа → PR в gitops → слияние → синхронизация
       → поды готовы → СОБЫТИЕ ВЫКАТКИ
                        ▲
                        здесь, и только здесь
```

Условие: синхронизация успешна **и** приложение `Healthy` **и** запущен новый
digest. Событие отправляется однократно на ревизию — иначе повторная проверка
состояния порождает новое событие, и вместо одной отметки на графике появляется
сплошная полоса.

### Какие события показывать

| Показывать | Не показывать по умолчанию |
| --- | --- |
| выкатка | сборка образа |
| изменение конфигурации | слияние запроса |
| флаг возможности | обычный перезапуск пода |
| изменение инфраструктуры | |
| переключение роли | |
| начало и конец инцидента | |

`build` отделён от `deployment` намеренно: на продуктовом дашборде сборки — это
шум, который приучает не смотреть на отметки вовсе.

### Значения изменённых ключей не пишутся

```
changed_keys: [OUTBOX_BATCH_SIZE, OUTBOX_LEASE_SECONDS]
```

Только имена. Вместе со значениями в журнал попадут пароль, строка подключения,
токен и подписанная ссылка — те же запреты, что и для содержимого сообщений.
За подробностями — ссылка на коммит, а не полный diff в аннотации: иначе
дашборд превращается в просмотрщик git.

### Метрика и событие — разные вопросы, нужны оба

```
messenger_build_info{service="api", version="abc123"} 1
                                   что сейчас запущено

событие deployment в 20:15
                                   когда произошло изменение
```

Строить аннотации из `build_info` нельзя: это непрерывный ряд, и Grafana
поставит отметку на каждой точке. Событие существует только в момент изменения —
именно поэтому оно событие, а не метрика.

### Слои аннотаций и фильтрация

Запрос аннотаций использует те же измерения, что и переменные дашборда
(`environment`, `service`), иначе на дашборде API появятся выкатки
`attachment-worker`. Слои переключаются отдельно:

```
[✓ Выкатки]  [✓ Конфигурация]  [✓ Инфраструктура]
[  Флаги  ]  [  Инциденты   ]
```

На обзорном дашборде SLO — все значимые изменения без фильтра по сервису.

### Отдельный дашборд «Release»

```
текущие версии        api abc123 · realtime e44321 · web 91a550
события за сутки      временная шкала выкаток
до и после выкатки    частота ошибок · p99 · доставка · переподключения
состояние             Argo CD Sync/Health · поды старой и новой версии
```

Полосовая шкала версий («какие версии работали одновременно») особенно полезна
во время постепенного обновления: она показывает то, чего не видно ни в одной
метрике — что в течение восьми минут обслуживали две разные сборки.

### Метрики → журналы → трассы как единая навигация

```
всплеск p99 доставки
      ↓ клик
журналы ±5 минут
      ↓ message_id или trace_id
трасса в Tempo
      ↓
обратно к журналам этого span
```

Не три отдельных продукта, а один граф переходов.

### Синтетика как отдельный SLI

Раз в минуту, целиком через настоящий путь:

```
Синтетический A: вход → беседа → отправка
       ↓
Синтетический B: получение по WebSocket → подтверждение
```

```
messenger_synthetic_success{journey="message_delivery"}
messenger_synthetic_duration_seconds{journey="message_delivery"}
```

Позже добавляются пути входа, вложения, push и переподключения. Доставка
сообщения — P0: если она красная, всё остальное неважно.

## Определение готовности

Не отдельный этап, а сквозное требование к каждой возможности. Возможность не
зелёная, пока нет пяти вещей:

```
метрика существует
структурированные журналы существуют
путь трассировки существует там, где полезен
дашборд или запрос существует
оповещение определено, если отказ виден пользователю
```

Пример для `MSG-001` — отправка сообщения:

| | |
| --- | --- |
| **Метрики** | `message_send_operations_total`, `message_commit_duration_seconds`, `message_delivery_duration_seconds` |
| **Журналы** | `message_commit_failed`, `outbox_publish_failed` |
| **Трасса** | `POST /messages` → Postgres → outbox → Kafka → потребитель → realtime |
| **SLI** | успех коммита, подтверждение доставки |
| **SLO** | 99.95% коммит, 99.9% доставка |
| **Оповещение** | скорость сжигания бюджета |
| **Синтетика** | A → B |

## Как это ложится на гейты

Наблюдаемость нельзя начинать в G5. Попытка оснастить телеметрией четыре уже
готовых слоя приложения задним числом означает переписывать их все.

| Гейт | Что добавляется |
| --- | --- |
| **G0** | проводка телеметрии: VictoriaMetrics, VictoriaLogs, Tempo, коллектор OTel, общий формат журналов, общая библиотека метрик, поток эксплуатационных событий |
| **G1** | метрики, журналы и трассы входа |
| **G2** | оснащение конвейера сообщений, корреляция по `message_id`, span для outbox, Kafka и realtime |
| **G3** | телеметрия браузера, SLI переподключения, разрывов и синхронизации |
| **G4** | телеметрия push, вложений и индикатора набора |
| **G5** | формальные SLO, бюджеты ошибок, оповещения по скорости сжигания, дашборды SLO, синтетика, руководства |
| **G6** | проверка SLO под отказами, нагрузкой и деградацией |
