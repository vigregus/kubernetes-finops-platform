# Решения и план работ

> kubernetes-finops-platform · мессенджер, часть 4

Закрывающий документ. Таблица соответствия «логический компонент → локально → AWS», устранение противоречий между тремя предыдущими частями, окончательные границы первой версии и план из четырёх этапов. Дальше — реализация, а не проектирование.

## Таблица соответствия

Она устраняет большинство противоречий сама по себе. Первые три части описывали механизмы отказоустойчивости так, как их строят самостоятельно — Sentinel, контроллеры KRaft, `synchronous_standby_names`. В AWS этих механизмов нет: там другие продукты со своими способами делать то же самое. Держать в одном документе оба описания — значит спроектировать систему, которую невозможно собрать.

| Логический компонент | Локально (Minikube) | AWS (stage и прод) | Отказоустойчивость обеспечивает |
| --- | --- | --- | --- |
| Реляционная БД | под Postgres | **RDS PostgreSQL Multi-AZ DB Cluster** | AWS: писатель и две реплики в трёх зонах, подтверждение как минимум одной |
| Шина событий | Kafka в KRaft-режиме, один узел | **MSK** | AWS: брокеры по зонам, контроллеры не наши |
| Redis realtime | один Redis, разные базы | **ElastiCache**, отдельная группа репликации | AWS: Multi-AZ, автоматическое повышение реплики. Sentinel не разворачивается |
| Redis app-cache | **ElastiCache**, отдельная группа |  |  |
| Redis security | **ElastiCache**, отдельная группа |  |  |
| Объектное хранилище | MinIO, один узел | **S3** + CloudFront | AWS: многозонная надёжность |
| Realtime-соединения | Centrifugo в кластере | Centrifugo в EKS | наше: реплики по зонам, дренирование |
| Бэкенд и потребители | в кластере | EKS | наше: реплики по зонам |
| Идентификация | Keycloak в кластере | Keycloak в EKS, **БД в том же RDS** | наше приложение, БД от AWS |
| Секреты | локальные файлы | **Secrets Manager** + KMS | AWS |
| Вход снаружи | NodePort | **ALB** + WAF + Route53 | AWS |
| Веб-клиент | dev-сервер Vite | **S3** + CloudFront | AWS |

Правило чтения: **в колонке AWS не должно остаться ни одного механизма, который мы настраиваем сами, если продукт делает это за нас**. Sentinel, кворум синхронных реплик и контроллеры KRaft остаются описанием того, *какая семантика нужна*, — а не инструкцией по настройке.

## Устранённые противоречия

p0 · противоречие между частями

### Уведомления: Web Push, а не APNs

Третья часть говорила про Service Worker и Web Push, первая продолжала описывать APNs/FCM, а потребитель назывался `consumer-push`. Для веб-клиента APNs не существует.

**Решение:** сервис называется `consumer-notifications`, транспорт — свойство устройства: Web Push в первой версии, APNs и FCM появляются вместе с нативными приложениями. Исправлено в первой части.

p0 · смешение моделей

### Самоуправляемая отказоустойчивость против управляемой

Sentinel, три контроллера KRaft и `synchronous_standby_names = ANY 1` — правильные механизмы, если строить самому. С ElastiCache, MSK и RDS они не применяются вовсе.

**Решение:** для AWS выбран **RDS PostgreSQL Multi-AZ DB Cluster** — писатель и две реплики в трёх зонах с подтверждением как минимум одной, что близко к нужной семантике и управляется платформой. Aurora рассматривается позже: у неё принципиально другая модель хранения, и переход на неё — отдельное решение, а не деталь.

p0 · расхождение со scope

### Звонки не входят в первую версию

LiveKit и coturn присутствовали в схеме, но определение готовности проверяет голосовое сообщение, а не звонок. Статус разговоров один-на-один оставался неопределённым.

**Решение:** в первой версии **звонков нет вообще** — ни групповых, ни один-на-один. Голосовые сообщения есть и идут через объектное хранилище. LiveKit и coturn остаются в целевой архитектуре как будущее. Это снимает два самых дорогих компонента, целый пул узлов и несколько сценариев отказа.

p0 · неполное определение

### Путь квитанции о доставке

Состояние `delivered` было описано как «устройство получателя приняло», но сам путь от браузера до записи отсутствовал.

```
POST /conversations/{id}/receipts
{ "delivered_seq": 18382, "read_seq": 18375 }
```
**Решение:** квитанции батчатся по номеру, а не шлются на каждое сообщение. Семантика при нескольких устройствах: **доставлено — если хотя бы одно устройство получило, прочитано — если хотя бы одно прочитало до этого номера**.

p0 · обещание без обеспечения

### Восстановление после потери региона

В SLO стояло «RTO менее 30 минут», при этом мультирегион осознанно не делается. Это несовместимо: тридцать минут требуют заранее подготовленного второго региона.

**Решение:** обещание приведено к правде — **RTO измеряется часами, RPO равен интервалу резервного копирования**. Резервный регион в режиме заготовки появится отдельным этапом, когда понадобится; тогда и вернём тридцать минут.

## Решения уровня P1

| Вопрос | Решение |
| --- | --- |
| Поиск в v1 | **не входит.** `consumer-search` убран из развёртывания первой версии; полнотекстовый поиск Postgres добавится, когда поиск попадёт в объём |
| Голосовые в объёме | записаны явно: «вложения, изображения **и голосовые сообщения** » |
| Обработка вложений | новый сервис `attachment-worker` в существующем репозитории; питается событием `attachment.uploaded` из Kafka — новых распределённых систем не требуется |
| Приватность медиа | приватный бакет, подписанные ссылки CloudFront с коротким сроком, авторизация **до** выдачи ссылки — и повторная проверка при исключении из беседы |
| Отзыв членства | для **записи** — проверка в базе, а не в кеше: инвалидация через Kafka может отстать, и исключённый успеет отправить сообщение. Для чтения короткое устаревание допустимо |
| Лимиты на «печатает» | отдельные, **на стороне Centrifugo**: не чаще одного события в 2 секунды на соединение и беседу. Обычные лимиты API здесь не работают — трафик их не проходит |
| База Keycloak | тот же кластер RDS, отдельная база и пользователь. Общий домен отказа принят сознательно ради экономии в первой версии |
| Права в админке | роли `support` / `moderator` / `admin` в Keycloak, аудит привилегированных действий, второй фактор для администратора, и **поддержка не читает содержимое сообщений без необходимости** |

## Два тонких вопроса корректности

чтение своих же записей

История читается с реплики, отправка идёт в писатель. Пользователь отправил сообщение и сразу обновил список — реплика может ещё не догнать, и в истории своего сообщения не окажется. Данные не потеряны, но выглядит именно как потеря.

**Решение:** свежие страницы — с писателя, глубокая пагинация — с реплики; плюс клиент удерживает оптимистичную запись, пока не увидит её в ответе сервера.

что именно означает блокировка

«B больше не может писать» — только один из четырёх вопросов. Остальные: видит ли B, что A в сети; видит ли, что A печатает; сохраняется ли у B старая переписка; может ли B создать новую беседу.

**Решение для v1:** B не может писать и не может создать новую беседу; presence и «печатает» для A скрыты; старая история у B остаётся. Это продуктовое решение, и оно записано — без него авторизация в бэкенде получится неоднозначной.

## План работ

Этап 1
### Ядро обмена сообщениями

Minikube

- Три репозитория и конвейер: сборка по digest, ArgoCD на локальном кластере
- Вход, беседы один-на-один, отправка и история
- Идемпотентность и порядок: `client_message_id`, `conversation_seq`
- Outbox с арендой, Kafka, потребитель realtime, Centrifugo
- «Печатает» отдельным каналом; онлайн и был в сети
- Квитанции батчами, состояния сообщения в интерфейсе
- Переподключение и догрузка при `recovered=false`
- **Проверка корректности:** убить relay между публикацией и отметкой — сообщение приходит один раз

Этап 2
### Продукт и эксплуатация

Minikube

- Вложения: инициация, presigned-загрузка, `attachment-worker`, состояния, уборка неприкреплённых
- Голосовые сообщения
- Блокировка и жалобы по принятой семантике
- Админка с ролями и аудитом; трассировка по `message_id`
- Наблюдаемость: метрики, логи, трассы, синтетический сценарий раз в минуту
- Флаги функций и маршрутизация оповещений

Этап 3
### AWS stage

Terraform + EKS

- Terraform: сеть, EKS, RDS Multi-AZ, MSK, три группы ElastiCache, S3, CloudFront, ALB, WAF, KMS, ECR, роли
- CI через OIDC, продвижение тем же digest
- Дополнения кластера из зафиксированного списка
- **Ёмкость:** подписки `5k×1`, `5k×20`, `5k×100` и доля печатающих 1–20%, через боевой балансировщик
- **Матрица отказов** сверху вниз, включая потерю зоны, с измерением фактических RTO

Этап 4
### Прод и репетиция восстановления

AWS

- Продвижение проверенного digest
- **Разворачивание из копии в чистое окружение:** база, хранилище, выкатка, вход пользователя, открытие старой беседы
- Сверка семнадцати шагов готовности целиком

## Что зафиксировано и не пересматривается

Решения, которые прошли все ревью и остаются:

- Postgres и транзакционный outbox как путь записи и источник истины
- Kafka как шина доменных событий, не как realtime-брокер
- Centrifugo для постоянных соединений; его history — только кеш восстановления
- At-least-once с идемпотентными потребителями; `conversation_seq` как порядок
- Три домена кеша; история сообщений без Redis
- «Печатает» отдельным best-effort каналом
- Одинаковый Helm на всех окружениях; три репозитория; продвижение неизменяемого digest
- Миграции расширение-сужение; статика за CDN; stage как маленький многозонный прод
- Тестирование отказов и восстановления как часть определения готовности

Проектирование закрыто. Дальше — реализация по этапам выше.
