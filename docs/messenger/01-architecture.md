# Мессенджер на 10 миллионов

> kubernetes-finops-platform · архитектура, редакция 6

Финальная редакция. К runtime-схеме добавлен слой кешей и эфемерного состояния: три роли Redis вместо одной, карта кешей с источниками истины и отдельный класс событий «печатает» — который способен нагружать систему сильнее, чем сами сообщения.

## Принцип

### Восемь ролей, и ни одна не подменяет другую

```
Postgres     = истина
Outbox       = надёжный мост из БД в шину
Kafka        = долговечная шина доменных событий
Centrifugo   = realtime-доставка онлайн
Redis        = эфемерное realtime-состояние
Уведомления  = доставка офлайн (Web Push в v1, APNs/FCM позже)
LiveKit/TURN = медиа (звонки — вне v1, см. ADR 0000)
Object store = вложения и голосовые
```

## Что изменилось в редакции 6

**Redis был одной сущностью.** «Эфемерное realtime-состояние» скрывало три разные роли с разными требованиями и разным радиусом поражения. Разделён на realtime, app-cache и security.

**Не было карты кешей.** Для каждого кеша теперь указан TTL и источник истины. Принцип: после полного сброса всех кешей не должно потеряться ни одно сообщение и ни одно вложение.

**Индикатор «печатает» отсутствовал.** И это не мелочь интерфейса: при 5% печатающих он даёт втрое больше публикаций, чем сами сообщения. Добавлен как отдельный класс событий со своим каналом и своими правилами.

**Кеш членства — вопрос безопасности, а не скорости.** Исключённый из беседы не должен сохранять доступ до истечения TTL. Добавлен путь отзыва через Kafka.

## Что было исправлено в редакции 5

**Реализация outbox была неверной.** Я держал транзакцию и блокировки строк открытыми на время сетевого вызова Kafka. Исправлено на двухфазную схему с лизингом.

**Единственный синхронный standby останавливает запись.** Потеря именно этой реплики блокирует коммиты до перенастройки. Заменено на кворум `ANY 1` из двух.

**Keycloak исчез из итоговой топологии.** Вторая регрессия того же рода, что и с объектным хранилищем. Control plane возвращён и описан отдельно.

**Kafka была строкой «3 брокера».** Добавлен конкретный профиль: RF, minISR, acks, идемпотентность, rack awareness, выделенные контроллеры KRaft.

**Не было контракта событий.** Добавлены реестр схем, версионирование и требование обратной совместимости.

**DLQ была только у outbox.** Ретраи и DLQ нужны и после Kafka, причём с разной политикой для разных потребителей.

**Не было ответа, что если Kafka лежит часами.** 54 миллиона событий за шесть часов — это отдельная ёмкость и пороги деградации.

**Не было приоритетов при перегрузке.** Отказоустойчивость — это не только «пережить потерю зоны», но и «под перегрузом сохранить главное, пожертвовав второстепенным».

## Кеши и эфемерное состояние

Redis в прошлых редакциях был одной строкой — «эфемерное realtime-состояние». За ней прятались три роли с разными требованиями, разной критичностью и разным радиусом поражения.

```
Redis realtime     брокер Centrifugo, history для recovery, presence
Redis app-cache    профили, метаданные бесед, членство
Redis security     лимиты частоты, попытки входа и SMS, счётчики злоупотреблений
```
В stage и проде это три отдельных ElastiCache. Локально достаточно одного с разными базами — разделение нужно не ради мощности, а ради **доменов отказа**: перегруженные счётчики лимитов не должны останавливать доставку сообщений, а сброс кеша профилей не должен ронять realtime.

### Карта кешей

| Данные | Где | TTL | Источник истины |
| --- | --- | --- | --- |
| JS, CSS, ассеты | браузер и CDN | дни–год | S3 |
| Вложения, голосовые | CDN | часы–дни | S3 |
| JWKS Keycloak | память пода API | 5–15 мин | Keycloak |
| Профили | Redis app-cache | 5–10 мин | Postgres |
| Метаданные бесед | Redis app-cache | 1–5 мин | Postgres |
| **Членство в беседе** | Redis app-cache | 15–60 с + отзыв | Postgres |
| История сообщений | **пока не кешировать** | — | Postgres |
| Непрочитанное | сначала без кеша | — | Postgres |
| History Centrifugo | Redis realtime | минуты | **не истина** |
| Presence | Redis realtime | секунды | эфемерно |
| Печатает | **вообще не хранить** | 3–5 с у клиента | нет |
| Лимиты частоты | Redis security | секунды–минуты | эфемерно |

Проверочное правило одно: **после полного сброса всех кешей не должно потеряться ни одно сообщение и ни одно вложение**. Всё, что выше строки «источник истины = Postgres или S3», можно стереть целиком — система восстановится сама, медленнее.

### История сообщений — пока без кеша

Соблазн поставить Redis между API и Postgres для всей истории велик и преждевременен. Сначала — правильный индекс по `(conversation_id, conversation_seq)`, пагинация по ключу вместо `OFFSET`, чтение с реплики и собственный буферный кеш Postgres. Только если метрики покажут проблему на популярных беседах — точечный `recent_messages:{id}` на полсотни последних сообщений с TTL в минуту.

### Инвалидация — через уже существующую Kafka

```
запись в БД → outbox → Kafka ├─ обычные потребители
                             └─ cache-invalidator → DEL user:{id}
```
Отдельная шина инвалидации не нужна: события `user.updated`, `conversation.updated`, `membership.changed` уже идут через Kafka. Но TTL остаётся обязательным — инвалидация *ускоряет* согласованность, а TTL *страхует* на случай, если событие потерялось или потребитель отстал.

членство — это безопасность, а не скорость

Пользователя исключили из беседы. Если запись `membership:500:123 = true` живёт ещё десять минут, он десять минут сохраняет доступ — а это уже не устаревший кеш, это дыра.

```
исключение → commit → Kafka membership.removed
                        ├─ DEL кеша членства
                        └─ отписка и разрыв realtime-доступа
```
Поэтому короткий TTL, явный отзыв и, главное, **зафиксированное допустимое время устаревания** для прав доступа — цифра, а не «быстро».

## Эфемерные события: «печатает»

Индикатор набора — отдельный класс событий, и провести его по общему пути было бы ошибкой. Ему не нужны Postgres, outbox, Kafka, push, история и восстановление. Его **можно и нужно терять**.

```
браузер A ──WebSocket──→ Centrifugo ──Redis PUB/SUB──→ Centrifugo ──→ браузер B
```
Клиент публикует напрямую через Centrifugo, минуя бэкенд целиком. Это штатный сценарий, а не обход: сервер здесь ничего не решает и ничего не сохраняет.

### Отдельное пространство каналов

|  | `chat:{id}` | `typing:{id}` |
| --- | --- | --- |
| История | включена | выключена |
| Восстановление | включено | выключено |
| Presence | по необходимости | выключен |
| Публикация клиентом | запрещена | разрешена |
| Гарантии | at-least-once | best effort |

Если пустить «печатает» в тот же канал, эти события попадут в history и будут восстанавливаться при реконнекте — то есть пользователь после обрыва увидит, кто печатал пять минут назад. Разные свойства требуют разных каналов.

### Протокол клиента

```
первое нажатие      → typing:start
продолжает набирать → heartbeat каждые 2–3 с
отправил, очистил,
ушёл из беседы      → typing:stop

но stop не гарантирован: закрыли ноутбук, пропала сеть, убили вкладку
получатель          → локальный таймаут 4–5 с, индикатор гаснет сам
```
Состояние держит **получатель**, а не сервер. В группе это не флаг, а множество с сроками: `{greg: истекает, maria: истекает}` — отсюда «Greg печатает», «Greg и Maria печатают», «печатают трое». Каждый heartbeat продлевает срок только своего пользователя.

кому верить в payload

Нельзя брать `user_id` из тела публикации — клиент напишет туда что угодно. Идентичность берётся из **аутентифицированного соединения**, которое Centrifugo прикладывает к публикации; в теле остаётся минимум вроде `{"state":"typing"}`.

Подписка на `typing:{id}` разрешается только участникам беседы, публикация — только тем, кто уже подписан. Важное ограничение открытой версии: при прямой публикации клиентом содержимое не валидируется на сервере. Для стенда этого достаточно; для строгого контура нужен либо прокси публикации, либо проверка схемы.

### И это переопределяет расчёт ёмкости

онлайн на пике300 000

печатают одновременно, 5%15 000

публикаций «печатает» при heartbeat 2 с7 500 /с

для сравнения: отправка сообщений2 500 /с

при 10% печатающих15 000 /с — вшестеро больше сообщений

Индикатор набора легко становится **основной нагрузкой на Redis и Centrifugo** — больше, чем сам обмен сообщениями. Поэтому в профили нагрузки добавляется отдельная ось: доля печатающих 1 / 5 / 10 / 20 процентов при heartbeat 1–3 секунды, с замером CPU Centrifugo, пропускной способности PUB/SUB, задержки доставки и доли потерянных событий.

## Kafka: production-профиль

```
brokers                    3, по одному на зону
broker.rack                = AZ                ← реплики расходятся по зонам
replication.factor         = 3
min.insync.replicas        = 2
producer acks              = all
enable.idempotence         = true
unclean.leader.election    = false             ← лучше недоступность, чем потеря

KRaft controllers          3 выделенных, по зонам
                           не совмещены с брокерами
```
Сочетание `RF=3` + `minISR=2` + `acks=all` означает, что подтверждённое событие переживает потерю брокера или зоны: запись подтверждается только после появления на двух репликах из трёх. `unclean.leader.election=false` — сознательный выбор недоступности вместо тихой потери данных при выборе отставшего лидера.

Контроллеры KRaft вынесены отдельно: кворум из трёх переживает потерю одного, а совмещение ролей на критичном контуре не рекомендуется — отказ брокера не должен одновременно быть отказом управляющего слоя.

## Контракт событий

```
message.created.v1              message.content.v1
  event_id                        event_id
  event_type                      event_type
  event_version                   event_version
  occurred_at                     occurred_at
  message_id                      message_id
  conversation_id                 conversation_id
  conversation_seq                payload      ← текст
  sender_id
  type
  has_attachments

→ непрочитанное, аудит,        → realtime, уведомления
  будущие потребители
```

**Содержимое вынесено в отдельный топик.** Ранняя редакция держала текст
в общем событии, и тогда его получали все подписчики — включая счётчик
непрочитанного и аудит, которым он не нужен. Право на содержимое обязано
выдаваться по потребности, а не по факту подписки; разбор — в
[модели угроз](11-threat-model.md), тест — `SEC-010`.

Без реестра схем любое добавление поля — `thread_id`, `edited_at`, `encryption_version`, метаданные вложения — рискует сломать потребителя, который о нём не знает. Требование: **обратная совместимость**, проверяемая в CI, а не договорённостью.

Это тем важнее, чем больше независимых потребителей. В v1 их три — realtime, уведомления и непрочитанное; поиск, модерация, биллинг и аудит спроектированы как будущие и в первую версию не входят. Каждый обновляется в своём темпе.

**Повтор гасится порядком, а не журналом `event_id`.** `message.created` партиционируется по `conversation_id`, поэтому порядок внутри беседы сохраняется, и потребителю достаточно хранить наибольший применённый `conversation_seq`: событие с номером не больше применённого — повтор. Журнал доставленных `event_id` пришлось бы хранить вечно (момент, после которого событие уже не придёт, потребителю неизвестен) и он был бы вторым источником истины рядом с чекпойнтом; `event_id` остаётся идентификатором события и ключом корреляции. Разрыв номеров чекпойнт при этом обнаруживает сам: он значит, что событие пропущено, а не применено, — и производное восстанавливается из источника истины целиком.

## Ретраи и DLQ после Kafka

```
основной топик
   ↓
потребитель
   ├─ успех                  → фиксируем offset
   └─ временная ошибка       → топик ретраев (1 мин → 5 мин → 30 мин)
                                   ↓ исчерпаны попытки
                                 DLQ
```
Бесконечный повтор одной записи блокирует партицию целиком — вместе с сообщениями всех остальных бесед, попавших в неё. Поэтому неудача уводится в отдельный топик, а основной поток продолжается.

Политики у потребителей разные, и это принципиально:

| Потребитель | Допустимая задержка | Поведение при отказе |
| --- | --- | --- |
| realtime → Centrifugo | секунды | быстрый отказ, клиент догрузит по reconnect |
| уведомления → Web Push / APNs / FCM | минуты | ретраи с ростом интервала |
| непрочитанное | секунды | ретраи, счётчик догоняет |
| поиск, аналитика | часы | отставание допустимо |
| биллинг, аудит | минуты | строже всех: DLQ разбирается вручную |

## Если Kafka недоступна шесть часов

```
2 500 событий/с  →  9 000 000 в час  →  54 000 000 за шесть часов
```
Сообщения не теряются — они в Postgres, события ждут в outbox. Но таблица outbox становится очень большой, и это надо спроектировать заранее:

- Частичный индекс только по необработанным строкам — иначе индекс растёт вместе с историей.
- Партиционирование outbox и уборка обработанных строк отдельным процессом.
- Посчитанная ёмкость: сколько часов простоя шины система выдерживает без деградации записи.

И явные пороги, а не «посмотрим»:

| Отставание шины | Состояние | Действие |
| --- | --- | --- |
| < 1 мин | норма | — |
| > 5 мин | предупреждение | алерт дежурному |
| > 30 мин | деградация | отключаем необязательных потребителей |
| > несколько часов | сброс нагрузки | отключаем второстепенные функции продукта |

## Outbox: исправление реализации

так было написано, и так неправильно

```
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED
  publish Kafka          ← сетевой вызов внутри транзакции
  UPDATE processed_at
COMMIT
```
Блокировки строк и открытая транзакция удерживаются на всё время обращения к Kafka. При замедлении шины это превращается в удержание соединений и рост числа долгих транзакций в базе, которая здесь и так самый ценный компонент.

```
правильно — две фазы

BEGIN
  claim batch:  pending → processing
                lease_until = now() + 30s
COMMIT                                  ← блокировки отпущены

publish Kafka                           ← сеть вне транзакции

UPDATE processed_at
```
Если воркер умер между публикацией и отметкой — срок аренды истекает, событие забирает другой воркер, происходит повтор. Это **согласуется с моделью at-least-once**, а не противоречит ей: дубль ожидаем и гасится дедупликацией у потребителя.

## Postgres: кворумная синхронная репликация

неприятный случай прежней схемы

Primary в AZ-A, *единственный* синхронный standby в AZ-B. Падает AZ-B — primary жив, но коммиты останавливаются, пока система не переназначит синхронную цель. Отказ одной зоны блокирует запись, хотя две трети кластера в порядке.

```
Primary   AZ-A
Standby   AZ-B
Standby   AZ-C

synchronous_standby_names = ANY 1 (standby_b, standby_c)
```
Коммит подтверждает **любая одна** из двух реплик. Умерла AZ-B — подтверждает AZ-C, и наоборот. Умер primary — повышается наиболее актуальный standby. Это согласуется с `RPO = 0` и одновременно переживает потерю зоны, чего однокандидатная схема не давала.

## Перегрузка: приоритеты и сброс нагрузки

Отказоустойчивость — это не только «пережить потерю зоны». Это ещё и вести себя разумно под нагрузкой, которой не ждали: массовое событие в популярном канале, атака ботов, шторм реконнекта, сломанный клиент в цикле ретраев, лавина push.

Ограничения, которые должны существовать до того, как понадобятся:

```
лимиты на пользователя, IP и устройство
максимальный размер сообщения
максимум подписок на пользователя
максимум сообщений в беседу в секунду
контроль допуска новых соединений
```
И явная лестница приоритетов — что жертвуется первым:

P0** Запись сообщения.** Отказ здесь виден пользователю немедленно и необратим.

P0** Realtime-доставка онлайн.** Суть продукта.

P1** Push и квитанции.** Задержка заметна, но не разрушительна.

P2** «Печатает» и presence.** Отключаются первыми — флагом, без выкатки. Пользователь теряет надпись, сообщения продолжают ходить.

P2** Индексация поиска, аналитика.** Отстают молча, догоняют позже.

P3** Обогащение аудита и фоновые задачи.** Отключаются первыми.

Практически это означает: отстаёт аналитика — чат работает; отстаёт push — realtime работает; Redis или Centrifugo у предела — **первым гасим «печатает»**, и это разом снимает больше нагрузки, чем весь поток сообщений; Postgres у предела — душим поиск и фоновые задачи, а не запись. Такая система **деградирует предсказуемо**, а не выходит из строя целиком.

## Control plane

Слой, который дважды выпадал из итоговой схемы и без которого ничего из вышеперечисленного не работает.

идентичность

### Keycloak

Многозонный, со своей HA-базой — либо управляемый провайдер. Токены короткоживущие, значит при недоступности IdP пользователи перестают обновлять учётные данные и постепенно отваливаются *все*, даже с живыми соединениями.

### DNS, WAF, защита от DDoS

## Матрица отказов

Полезнее дальнейшего усложнения схемы. Для каждого отказа — что видит пользователь, за сколько восстановится, теряются ли данные и нужен ли человек.

| Отказ | Что видит пользователь | RTO | Потеря данных | Восстановление |
| --- | --- | --- | --- | --- |
| **Под Centrifugo** | обрыв соединения, автоматический реконнект с восстановлением истории | секунды | нет | автоматически |
| **Под backend** | ничего — запрос уходит на другой | < 1 с | нет | автоматически |
| **Узел целиком** | реконнект части клиентов | секунды | нет | автоматически |
| **Зона целиком** | реконнект трети клиентов, кратковременный всплеск задержек | 1–2 мин | нет | автоматически, если есть запас |
| **Redis primary** | пауза в realtime-доставке; отправка и запись работают | < 10 с | эфемерное состояние | ElastiCache Multi-AZ, автоматическое повышение реплики |
| **Redis целиком** | realtime молчит, сообщения сохраняются и догружаются позже | минуты | сообщений нет | автоматически |
| **Брокер Kafka** | ничего | секунды | нет | автоматически, RF=3 |
| **Контроллер KRaft** | ничего | секунды | нет | локально — кворум 2 из 3; в облаке контроллеры MSK не наши |
| **Kafka целиком** | realtime и push стоят; отправка работает, доставка догоняет после | до часов | нет, копится в outbox | автоматически + пороги деградации |
| **Outbox-воркер** | задержка доставки; отправка не затронута | секунды | нет | аренда истекает, подхватывает другой |
| **Postgres primary** | отправка недоступна на время повышения реплики | < 1–2 мин | нет, кворумный синхрон | автоматически, с fencing |
| **Повреждение данных Postgres** | зависит от масштаба | часы | до точки восстановления | вручную, PITR |
| **Балансировщик** | массовый реконнект всех клиентов разом | секунды | нет | автоматически, но проверить запас |
| **Узел LiveKit** ⟨вне v1⟩ | **активный звонок обрывается**, требуется переподключение | < 3 с | запись звонка | клиент пересоздаёт комнату |
| **Узел TURN** ⟨вне v1⟩ | обрыв релеящихся звонков | секунды | нет | автоматически, нужен запас полосы |
| **Keycloak** | новые входы невозможны; старые сессии живут до истечения токена | минуты | нет | автоматически при HA |
| **Объектное хранилище** | голосовые и вложения не загружаются и не открываются; текст работает | минуты | нет | автоматически |
| **Потеря региона** | полная недоступность | **часы** | до точки восстановления | вручную, по регламенту |

Две строки в этой таблице — единственные, где нужен человек, и обе не решаются репликацией: **повреждение данных** и **потеря региона**. Именно поэтому PITR и регламент катастрофы — не бюрократия, а последний рубеж.

И одна строка принципиально отличается от всех — она относится к звонкам, которых в v1 нет, и остаётся здесь как требование к их будущему включению: **смерть узла LiveKit рвёт активный звонок**. Это единственный отказ, который пользователь замечает немедленно и который нельзя спрятать за переотправкой запроса.

## Классификация данных

Тем, с чего стоило начинать. Четыре класса, и правила обращения у них разные:

| Класс | Что | Можно потерять? |
| --- | --- | --- |
| **Долговечное** | Postgres, объектное хранилище | нет — это истина |
| **Журнал событий** | Kafka | нет в пределах retention; восстановимо из outbox |
| **Восстановимый кеш** | Redis app-cache, CDN, память процесса | да — перестроится из истины |
| **Эфемерное состояние** | presence, history Centrifugo | да — пересоберётся из подключений |
| **Эфемерные события** | «печатает», вход и выход, сигналы интерфейса | да — и терять их нормально |

Одно правило, которое стоит держать в голове при любом решении об оптимизации:

### «Печатает» — не сообщение

Его можно терять. Но нельзя позволять ему замедлять доставку сообщений — а при доле печатающих в 5–10% именно он, а не чат, определяет нагрузку на брокер.

## На этом технологии заканчиваются

Схема закрыта. Дальнейшее усложнение даст меньше, чем проверка того, что уже спроектировано. Порядок работ:

- **Корректность раньше производительности.** Убить relay после публикации, но до отметки; повторная доставка ожидаема, пользователь видит сообщение один раз за счёт дедупликации.
- **Ёмкость по подпискам**, а не по соединениям: профили `5k×1`, `5k×20`, `5k×100` — и вторая ось по доле печатающих: 1, 5, 10 и 20 процентов при heartbeat 1–3 секунды.
- **Матрица отказов сверху вниз** — от пода до зоны, с замером фактических RTO против заявленных.
- **Нагрузка через боевой балансировщик**, иначе измеряется система без компонента, который первым упрётся в предел.

Что осталось нерешённым осознанно: мультирегион (ломает порядок, ключи E2EE и локальность комнат — делать только когда потребуется географически) и выбор между двумя медиа-стеками против единого LiveKit, зафиксированный как ADR.
