# Совместимость клиента

> kubernetes-finops-platform · мессенджер, часть 13

Клиент — единственный участник системы, который **нельзя выкатить**. Сервер,
потребители и база обновляются по команде; браузер обновляется тогда, когда
человек его откроет, и ровно до той версии, которую ему отдал его собственный
кеш.

Из этого следует всё остальное в документе.

---

## Часть 1. Service Worker — самый опасный компонент продукта

Не из-за сложности, а из-за единственного свойства: **он может навсегда
помешать собственному исправлению**.

```
выкачена версия с ошибкой в Service Worker
        ▼
Service Worker кеширует index.html «навсегда»
        ▼
браузер берёт index.html из кеша
        ▼
новая версия не загружается никогда
```

Ошибка в любом другом месте исправляется следующей выкаткой. Ошибка здесь
делает выкатку недоступной для уже пострадавших — у них не осталось пути,
по которому исправление могло бы приехать. Единственное средство — очистка
данных сайта вручную, то есть инструкция каждому пользователю.

Отсюда правила, которые не обсуждаются:

| Что | Как отдаётся | Почему |
| --- | --- | --- |
| `index.html` | `no-store` | точка входа обязана быть свежей всегда |
| файл Service Worker | `no-cache` | иначе он не сможет обновить сам себя |
| манифест версии | `no-store` | по нему определяется, устарел ли клиент |
| ресурсы с хешем в имени | `immutable`, год | имя меняется при изменении содержимого |

**Кешируется только то, у чего хеш в имени.** Всё, что решает, какую версию
загрузить, не кешируется никогда. Это `NTF-006`.

Дополнительно: проверка обновления при каждой загрузке страницы, а не по
расписанию, и немедленная активация новой версии вместо ожидания закрытия всех
вкладок — иначе пользователь с постоянно открытой вкладкой не обновится
месяцами.

## Часть 2. Что такое версия клиента

```
сборка → digest образа → манифест версии → заголовок в каждом запросе
```

Клиент сообщает свою версию заголовком, сервер видит её в журнале обращений и
в метке метрики. Без этого нельзя ответить на два обычных вопроса: сколько
людей на старой сборке и стало ли хуже именно им.

```
messenger_client_version_requests_total{version, outcome}
```

Метка `version` здесь допустима, а `user_id` — нет: версий десятки,
пользователей миллионы.

## Часть 3. Контракт совместимости

### Сервер поддерживает клиентов 90 дней

```
0–90 дней     поддерживается полностью
90+ дней      принудительное обновление при следующей загрузке
```

Девяносто дней — не техническое ограничение, а обещание: столько живёт любая
возможность после удаления из контракта. Меньше — пользователь с редко
открываемой вкладкой обновляется каждый раз; больше — каждое изменение
контракта приходится поддерживать кварталами.

Принудительное обновление — это перезагрузка с очисткой кеша, а не сообщение
«обновитесь». Сообщение читают не все.

### Правила обеих сторон

**Клиент игнорирует незнакомые поля.** Добавление необязательного поля в ответ
не должно ломать старую сборку — иначе любое расширение API становится
ломающим изменением.

**Сервер не требует новых полей.** Новое поле в запросе всегда необязательно
и имеет разумное значение по умолчанию, пока не истекли 90 дней.

**Клиент не решает по версии сервера.** Ветвление на стороне клиента по
версии сервера превращает две системы в матрицу сочетаний, где половина
не проверена.

## Часть 4. Неизвестный тип сообщения обязан сохраниться

Самое неочевидное требование документа.

Старый клиент получает сообщение типа, которого не знает — например, появился
новый тип после его сборки. Естественная реакция — пропустить его. Так делать
нельзя:

```
беседа на сервере     seq 41, 42, 43, 44
старый клиент         seq 41, 42, ──, 44     пропустил незнакомый 43
        ▼
клиент видит разрыв в нумерации
        ▼
считает, что потерял сообщение
        ▼
запускает восстановление истории
        ▼
получает то же самое и снова пропускает
```

Пропуск неизвестного ломает не отображение, а **механизм обнаружения
пропусков**, на котором держится согласованность клиента. Плюс счётчик
непрочитанного расходится с сервером навсегда.

Правило: неизвестный тип занимает своё место в ленте с заглушкой «сообщение
не поддерживается этой версией», учитывается в нумерации и в непрочитанном.
Ровно как надгробие удалённого — и по той же причине.

## Часть 5. Соединение переживает выкатку

WebSocket живёт часами, выкатка занимает минуты. Значит, в любой момент
выкатки есть соединения, установленные предыдущей версией сервера.

```
время ──────────────────────────────────▶
сервер   ████ версия A ████│████ версия B ████
клиент   ─────── одно соединение, открытое до выкатки ───────
```

Из этого два следствия.

**Формат сообщений realtime обязан быть совместим внутри жизни соединения.**
Не «после выкатки», а прямо во время неё: клиент получает сообщения от обеих
версий вперемешку.

**Смена протокола требует переподключения, а переподключение — это лавина.**
Триста тысяч соединений, разорванных одновременно, вернутся одновременно.
Поэтому разрыв ради смены протокола делается порциями с разбросом по времени,
а клиент переподключается со случайной задержкой и ростом интервала —
то же требование, что и при отказе узла.

## Часть 6. Как менять контракт, не ломая клиентов

Единственная безопасная последовательность. Ту же схему использует политика
миграций базы, и по той же причине: нельзя обновить обе стороны одновременно.

```
1. расширение     сервер понимает старое и новое
                  клиент постепенно переходит на новое
                  ▼ 90 дней
2. наблюдение     доля запросов от старых версий стремится к нулю
                  ▼
3. сужение        старое удаляется из сервера
```

Шаг 2 — не ожидание, а измерение: удаление делается по показанию метрики
версий, а не по календарю. Если через 90 дней на старой сборке остаётся
заметная доля пользователей, вопрос не в сроке, а в том, почему они не
обновились, — и это, скорее всего, ошибка в Service Worker.

Пропуск первого шага — самый дорогой класс ошибок в продукте с веб-клиентом:
обратного пути нет, потому что откатить клиентов невозможно.

## Часть 7. Офлайн и накопленные отправки

Клиент, потерявший сеть, копит отправки и посылает их при возвращении.

```
офлайн 3 дня → 12 накопленных сообщений → сеть вернулась
```

Что уже работает: повтор идёт с тем же `client_message_id`, поэтому
дублирования нет независимо от того, дошла ли первая попытка.

Что требует решения именно здесь: **накопленное могло устареть**. Отправка
в беседу, из которой автора успели заблокировать, отклоняется — и клиент
обязан показать это как отказ конкретного сообщения, а не как общую ошибку
сети. Иначе пользователь повторяет попытку вручную и получает тот же отказ.

Срок жизни накопленной отправки ограничен: сообщение, пролежавшее в очереди
неделю, отправлять не следует — контекст беседы ушёл далеко вперёд.

## Часть 8. Тесты

| Требование | Тест |
| --- | --- |
| Устаревшая сборка получает принудительное обновление | `WEBSEC-006` |
| Service Worker обновляется и не блокирует сам себя | `NTF-006` |
| Неизвестный тип сообщения сохраняет позицию и непрочитанное | `CLI-001` |
| Соединение, открытое до выкатки, продолжает работать | `CLI-002` |
| Клиент игнорирует незнакомые поля ответа | `CLI-003` |
| Накопленная офлайн-отправка в заблокированную беседу | `CLI-004` |
| Переподключение после смены протокола идёт с разбросом | `CLI-005` |

`CLI-001` — важнейший: его провал проявляется не сразу и выглядит как
загадочное расхождение счётчика непрочитанного, а не как отказ.

## Чего здесь нет

- **Нативные приложения.** Магазин приложений добавляет свои правила и свои
  сроки проверки; в v1 их нет ([ADR 0000](../ADR/0000-v1-scope.md)).
- **Хранение токенов в браузере.** Отдельное решение с собственными
  последствиями для XSS и выхода на всех устройствах — тема ADR, не этого
  документа.
- **Поддерживаемые браузеры.** Продуктовое решение, определяющее объём
  тестирования; принимается вместе с первым релизом.
