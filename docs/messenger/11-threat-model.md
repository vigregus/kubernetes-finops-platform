# Модель угроз

> kubernetes-finops-platform · мессенджер, часть 11

Контролей в проекте уже много — `AUTHZ`, `SEC`, `WEBSEC`, `ABUSE`, `INFSEC`, —
но они появлялись поодиночке, из отдельных соображений. Набор контролей не
является моделью угроз: по нему нельзя сказать, что защищено, что защищено
частично и что не защищено сознательно.

Порядок здесь обратный привычному: не «какие бывают атаки», а

```
активы → границы доверия → кто нападает → что может пойти не так → чем закрыто
```

и в конце — **остаточные риски**, то есть то, от чего защиты нет и не
планируется.

---

## Часть 1. Активы

Ранжирование не формальность: оно решает, куда тратить усилия.

| Актив | Почему ценен | Потеря конфиденциальности | Потеря целостности | Потеря доступности |
| --- | --- | --- | --- | --- |
| **Содержимое переписки** | личная жизнь людей | катастрофа | высокая | средняя |
| **Вложения** | то же, плюс объём | катастрофа | высокая | средняя |
| Граф общения — кто с кем | метаданные выдают не меньше текста | высокая | средняя | низкая |
| Токены сессий | дают доступ ко всему выше | катастрофа | — | средняя |
| Учётные данные инфраструктуры | дают доступ ко всему | катастрофа | катастрофа | катастрофа |
| Присутствие и «был в сети» | раскрывает распорядок дня | средняя | низкая | низкая |
| Журнал аудита | доказательство действий | средняя | **высокая** | низкая |
| Доступность сервиса | продукт | — | — | высокая |

Две строки обычно недооценивают. **Граф общения** — знание о том, кто с кем
переписывается, без единого прочитанного слова: именно поэтому отказ выглядит
как отсутствие ресурса (инвариант И-2). И **целостность аудита**: журнал,
который можно подделать, хуже отсутствующего — на него опираются, а он лжёт.

## Часть 2. Границы доверия

```
   ┌─ браузер ───────────────────── не доверяем ничему
   │  токены, Service Worker, кеш
   ▼  ─────────── граница 1: всё приходящее — данные, не команды
   ┌─ край: cilium-envoy, TLS ───── доверяем транспорту, не содержимому
   ▼  ─────────── граница 2: аутентификация и авторизация
   ┌─ сервисы: API, потребители ── нахождение внутри доверия не даёт
   ▼  ─────────── граница 3: сервис к хранилищу, своя учётная запись
   ┌─ данные: Postgres, Kafka, ─── доверяем; здесь всё открытым текстом
   │  Redis, объектное хранилище
   ▼  ─────────── граница 4: управляющий слой облака
   └─ AWS: IAM, KMS, сеть

   сбоку ─────────── граница 5: третьи стороны
          провайдер Web Push · почта · Keycloak
```

**Внутри кластера — не значит доверенный.** Сервис получает права не за то,
что он внутри сети, а за то, что аутентифицирован как нагрузка: своя учётная
запись, свои права в Kafka, сетевые политики, минимум необходимого. Иначе
скомпрометированный потребитель непрочитанного — сценарий, который эта же
модель разбирает в части 5, — получал бы всё, до чего дотянется по сети.

Существенное про **границу 3**: за ней содержимое лежит открытым текстом.
Шифрование на диске защищает от кражи диска, а не от того, у кого есть доступ
к базе. Из этого следует главный остаточный риск в части 6.

## Часть 3. Кто нападает

Реалистичные профили. Гипотетический противник с неограниченными ресурсами
в модель не входит: против него не строится защита, зато под него удобно
оправдывать отсутствие любой другой.

| Профиль | Возможности | Мотив |
| --- | --- | --- |
| **Любопытный пользователь** | обычный клиент, подбор идентификаторов | посмотреть чужую переписку |
| **Преследователь** | учётная запись, знает жертву лично | контакт после блокировки, слежка за присутствием |
| **Спамер** | автоматизация, много учётных записей | рассылка, фишинг |
| **Похититель сессии** | XSS, украденное устройство, общий компьютер | доступ к чужой переписке |
| **Злоупотребляющий сотрудник** | доступ к админке или к базе | посмотреть переписку знакомого |
| **Внешний исследователь** | сканирование, перебор, известные уязвимости | найти открытую точку входа |
| **Компрометация зависимости** | код в сборке | закрепиться, вынести данные |

«Злоупотребляющий сотрудник» стоит в списке не для полноты. Это самый
вероятный из серьёзных сценариев: у него уже есть доступ, ему не нужно ничего
взламывать, и его действие выглядит как обычная работа.

## Часть 4. Угрозы и контроли

### Граница 1 — браузер

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Разметка и скрипт в сообщении | экранирование, политика содержимого | `WEBSEC-001`, `WEBSEC-005` |
| Вредоносное имя файла | обеззараживание имени, отдача только по подписанной ссылке | `WEBSEC-002` |
| Запрос с чужого источника | проверка источника | `WEBSEC-003` |
| WebSocket с чужого источника | список разрешённых источников в Centrifugo | `WEBSEC-004` |
| Кража токена из хранилища браузера | срок жизни, отзыв, привязка к устройству | `AUTH-004` |
| Устаревший Service Worker отдаёт старый клиент | версионирование, принудительное обновление | `WEBSEC-006`, `CLI-007` |

### Граница 2 — аутентификация и авторизация

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Чужая беседа по идентификатору | отказ неотличим от отсутствия | `SEC-006`, `AUTHZ-004` |
| Подписка на чужой канал | токен с явным списком каналов | `SEC-007` |
| Публикация в чужой `typing` | проверка членства при публикации | `SEC-008` |
| Отправка в чужую беседу | членство из источника истины | `SEC-009` |
| Устаревший кеш расширяет права | свежесть выбирает политика, не вызывающий | `AUTHZ-003` |
| Сессия жива после выхода везде | немедленный отзыв, разрыв соединений | `AUTH-003`, `ADM-003` |
| Перебор паролей | ограничение частоты, счётчики в Redis security | `ABUSE-001` |

### Граница 3 — сервисы и хранилища

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Под принимает роль чужого сервиса | отдельная учётная запись на сервис | `INFSEC-004` |
| Неожиданный трафик между сервисами | сетевые политики | `INFSEC-005` |
| Секрет в git, образе или журнале | вычистка в обработчике, проверка канарейкой | `INFSEC-006`, `OBS-SEC-001` |
| Публичный доступ к бакету | политика бакета, блокировка публичного доступа | `INFSEC-001` |
| Публичная точка входа в базу или шину | только внутренняя сеть | `INFSEC-002`, `INFSEC-003` |

### Граница 4 — вложения

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Заявленный тип не совпадает с фактическим | проверка по содержимому, а не по заголовку | `ATT-007` |
| Проверка на вредоносность недоступна | отказ, а не пропуск | `ATT-008` |
| Доступ к чужому файлу по идентификатору | право выводится из родительской беседы | `ATT-006` |
| Подписанная ссылка утекла | короткий срок, ссылка не пишется в журнал | `INFSEC-006` |

**Подписанная ссылка — это предъявительский документ.** Кто её прочитал, тот
получил файл: ни токена, ни проверки прав она не требует. Отсюда два правила —
короткий срок и запрет записи в журналы, — и оба уже в стандарте журналов.

### Злоупотребления и преследование

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Поток сообщений от одного | предел частоты | `ABUSE-002` |
| Массовое создание бесед | предел на создание | `ABUSE-003` |
| Сотни соединений с устройства | предел на соединения | `ABUSE-004` |
| Сообщение чрезмерного размера | предел размера | `ABUSE-005` |
| Злоупотребление вредит остальным | изоляция, приоритеты под нагрузкой | `ABUSE-006` |
| Контакт после блокировки | запрет записи в обе стороны | `BLK-001`, `BLK-003` |
| Слежка за присутствием | заблокированный не видит присутствие и набор | `BLK-002` |
| Жалоба никуда не доходит | путь до человека | `RPT-001` |

### Привилегированный доступ

| Угроза | Контроль | Тест |
| --- | --- | --- |
| Поддержка читает переписку | запрещено по умолчанию, обхода нет | `ADM-002` |
| Вход в админку без второго фактора | второй фактор обязателен | `ADM-004` |
| Действие админа без следа | аудит; операция без аудита считается несовершённой | `AUTHZ-005` |

## Часть 5. Дыра, найденная этой моделью

**Событие `message.created.v1` несёт текст сообщения всем потребителям.**

```
message.created.v1  { sender_id, payload: {"text": "…"} }
        ├── realtime        текст нужен
        ├── уведомления     нужен фрагмент для предпросмотра
        ├── непрочитанное   НЕ нужен
        ├── аудит           НЕ нужен
        └── биллинг         НЕ нужен  ⟨вне v1⟩
```

Это противоречит собственному принципу авторизации, по которому поддержка и
администратор не получают содержимого по умолчанию: право на текст выдаётся не
по потребности, а по факту подписки на топик.

Последствия конкретны. Потребитель непрочитанного, скомпрометированный или
просто слишком подробно пишущий журнал, становится источником утечки текста,
которого ему никогда не требовалось. И срок хранения топика превращается
в срок хранения переписки во втором месте.

**Решение — разделение контрактов по потребности:**

```
message.created.v1          message.content.v1
  message_id                  message_id
  conversation_id             payload
  conversation_seq
  sender_id                 → realtime, уведомления
  type
→ непрочитанное, аудит, будущие потребители
```

Это изменение контракта Kafka, а не правка кода, поэтому делается **до G2** —
до того, как появятся потребители, которых придётся переписывать. Задача
заведена как `G2-000`; тест — `SEC-010`: потребитель непрочитанного не имеет
доступа к тексту.

## Часть 6. Остаточные риски

То, от чего защиты нет. Названо явно, потому что незаписанный принятый риск
через полгода становится обнаруженной уязвимостью.

### Р-1. Оператор может прочитать любую переписку

Сквозного шифрования в v1 нет ([ADR 0000](../ADR/0000-v1-scope.md)). За
границей 3 содержимое лежит открытым текстом, и любой, у кого есть доступ
к базе, читает его — независимо от того, что говорит модель авторизации.

```
запрещено через API          возможно напрямую
support читает переписку     доступ к Postgres
admin читает переписку       доступ к резервной копии
                             доступ к топику Kafka
```

Шифрование на диске здесь не помогает: оно защищает от кражи диска, а не от
того, у кого есть учётные данные базы.

Частичные меры: раздельные учётные записи, доступ к проду через процедуру
с аудитом, разные сроки хранения, запрет содержимого в журналах. Они
**уменьшают вероятность и повышают заметность, но не устраняют возможность**.

Единственное настоящее решение — сквозное шифрование, и это отдельный продукт:
управление ключами на устройствах, восстановление доступа, несколько
устройств, невозможность серверного поиска и модерации.

### Р-2. Метаданные не скрыты ни от кого внутри

Кто с кем и когда переписывается — видно в базе, в трассах и в метриках. Даже
при сквозном шифровании граф общения остался бы. Скрыть его требует других
механизмов, которые в этом продукте не рассматриваются.

### Р-3. Компрометация устройства пользователя обходит всё

Украденный разблокированный телефон даёт доступ к переписке. Отзыв сессий
помогает только после того, как о краже узнали.

### Р-4. Цепочка поставки проверена слабо

Образы собираются из публичных базовых, зависимости ставятся из публичных
реестров. Есть закрепление версий и сканирование, нет проверки происхождения
и списка состава. Принято на v1; закрывается до публичного stage.

### Р-5. Третьи стороны видят факт события

Провайдер Web Push знает, что пользователю пришло уведомление, и когда.
Почтовый провайдер видит адреса. Метаданные передаются неизбежно.

**Как именно содержимое до него не доходит** — это механизм, а не обещание,
и он должен быть назван. Выбран вариант с пустым уведомлением:

```
сервис уведомлений → провайдеру уходит сигнал без содержимого
                     ▼
Service Worker получает сигнал
                     ▼
сам обращается к API за предпросмотром, по своим правам
                     ▼
показывает уведомление
```

Провайдер видит факт и время, но не текст. Цена: уведомление появляется на
доли секунды позже и не показывается вовсе, если устройство офлайн в момент
доставки сигнала — тогда пользователь увидит его при следующем подключении.

Альтернатива — шифрование полезной нагрузки Web Push ключами браузера — тоже
рабочая и не выбрана: она добавляет управление ключами на каждое устройство
ради выигрыша в доли секунды.

## Часть 7. Что меняет модель

Каждый пункт требует пересмотра, а не дополнения:

| Изменение | Что меняется |
| --- | --- |
| Групповые беседы | граф общения шире, исключение участников становится достижимым, `AUTHZ-001/002` становятся блокирующими |
| Звонки | новый медиатракт, TURN как точка входа снаружи, отдельные учётные данные |
| Оплата | платёжные данные как новый актив высшей ценности, требования соответствия |
| Сквозное шифрование | снимает Р-1, ломает модерацию, поиск и восстановление истории |
| Публичный stage | цепочка поставки перестаёт быть принятым риском |

## Как это проверяется

Модель угроз, которую не проверяют, — документ о намерениях.

```
контроль → тест в каталоге → выполняется в конвейере
```

Прочерков в столбце «Тест» не осталось: обе задачи, которые модель нашла при
написании, доведены до тестов — разделение контракта события (`SEC-010`)
и устаревший Service Worker (`WEBSEC-006`, `CLI-007`).

Отдельно: **`INFSEC-001`, `002`, `004` и `006` блокируют выпуск** — это
зафиксировано в плане исполнения. Остальные контроли — условие закрытия своего
гейта.
