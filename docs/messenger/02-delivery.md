## Чего не хватало

В runtime-схеме порядок работ начинался сразу с проверки корректности и ёмкости, минуя сборку, выкатку и продвижение. И **веб-клиента не было вовсе** — а без него документ описывал бэкенд-платформу обмена сообщениями, но не мессенджер.

### Две плоскости, а не одна

```
плоскость доставки   GitHub → CI → ECR → GitOps → ArgoCD → EKS
плоскость исполнения  пользователь → CloudFront/LB → сервисы → данные
```
Первая отвечает на вопрос «как сюда попал этот код». Вторая — «что происходит с запросом». Документ, где есть только вторая, описывает систему, которую нельзя воспроизвести.

## Окружения и продвижение

главное правило

Одна модель выкатки на все окружения. Не должно возникнуть ситуации «локально docker-compose, на stage голые манифесты, в проде Helm» — это три разных пути и три независимых источника ошибок, причём ошибки третьего пути обнаруживаются в проде.

Один и тот же Helm chart везде, разница только в `values-local.yaml`, `values-stage.yaml`, `values-prod.yaml`.

|  | Local | Stage | Prod |
| --- | --- | --- | --- |
| Kubernetes | Minikube | EKS | EKS |
| Зон | 1 | 3 | 3 |
| Postgres | под | **RDS PostgreSQL Multi-AZ DB Cluster** | то же |
| Kafka | в кластере | MSK | MSK |
| Redis realtime | один, разные БД | ElastiCache | ElastiCache |
| Redis app-cache | он же | ElastiCache | ElastiCache |
| Redis security | он же | ElastiCache | ElastiCache |
| Хранилище | MinIO | S3 | S3 |
| Веб | локально | S3 + CloudFront | S3 + CloudFront |
| Секреты | локальные | управляемые AWS | управляемые AWS |
| Реплик | 1 | 2–3 | по ёмкости |
| Нагрузка | малая | синтетическая | настоящая |

**Stage — это маленький прод, а не Minikube в облаке.** Три зоны обязательны: если stage однозонный, на нём нельзя проверить ровно то, ради чего вся HA-схема и строилась — переживание потери зоны.

И отдельные кластеры EKS, а не namespace внутри одного. Разделение по namespace означает общий control plane, общие CRD и общий радиус поражения; разные аккаунты AWS добавляют к этому ещё и границу IAM.

Локальное окружение при этом не пытается быть HA. Его задача другая: корректность потока сообщений, дедупликация, восстановление, сквозные тесты и фронтенд.

## Terraform и ArgoCD: жёсткая граница

```
Terraform  →  AWS: VPC, EKS, node pools, RDS, MSK, ElastiCache,
                    S3, CloudFront, Route53, WAF, KMS, ECR, IAM

ArgoCD     →  внутри кластера: API, Centrifugo, relay, потребители,
                    Keycloak, наблюдаемость, аддоны
```
Правило простое: **Terraform создаёт то, что существует до Kubernetes; ArgoCD — всё, что живёт внутри него**. Смешение даёт знакомую боль — Terraform пытается управлять ресурсами, которые меняет контроллер, и каждый `plan` показывает дрейф, которого нет.

## CI/CD: собрать один раз

Единственное правило, из которого следует всё остальное: **прод не пересобирается**. Stage проверил конкретный `sha256` — в прод едет он же. Пересборка «той же» ветки даёт другой образ: другие версии зависимостей, другая база, другое время сборки — и проверяли вы не то, что запустили.

### GitOps как источник истины выкатки

```
# clusters/prod/api.yaml
image:
  repository: .../messenger-api
  digest: sha256:abc123     ← digest, а не тег
replicas: 12
```
Тег подвижен, digest — нет. `:latest` или даже `:v1.4.2` можно переписать; digest указывает ровно на те байты, которые прошли проверку.

Отсюда бесплатно получается ответ на два вопроса, на которые обычно отвечают археологией по логам: *что сейчас в проде* — посмотреть файл; *как откатиться* — `git revert`, дальше ArgoCD сам.

## Миграции базы — отдельная стратегия

почему миграция — не часть выкатки контейнера

Во время выкатки одновременно работают поды старой и новой версии. Миграция, несовместимая со старым кодом, ломает их *во время* раската — то есть в тот момент, когда откатиться сложнее всего.

```
нельзя   ALTER TABLE ... DROP COLUMN old_col
        → выкатка
        старые поды всё ещё читают old_col
```

```
расширение → выкатка → перенос данных → переключение → сужение

1. добавить новую колонку, не трогая старую     совместимо в обе стороны
2. выкатить код, умеющий писать в обе
3. перенести данные фоновым процессом
4. выкатить код, читающий только новую
5. удалить старую — отдельным релизом, позже
```
Шаг 5 отделён от шага 1 не формальностью ради: между ними должно пройти достаточно времени, чтобы откат на предыдущую версию оставался возможным.

## Выкатка зависит от типа нагрузки

Единая политика для всех сервисов здесь не работает — у них принципиально разное отношение к разрыву.

| Тип | Сервисы | Политика | Что видит пользователь |
| --- | --- | --- | --- |
| Обычный HTTP | API, потребители | `RollingUpdate`, `maxUnavailable: 0` | ничего |
| **Постоянные соединения** | Centrifugo | новые поды готовы → старый снят с балансировщика → дренирование → клиенты переподключаются с джиттером → завершение | переподключение, история восстанавливается |
| **Сессии с состоянием** | Centrifugo | узел помечен дренируемым → новые соединения не принимаются → открытые доживают до таймаута → завершение | переподключение части клиентов |
| Данные | Postgres, Kafka | по одному узлу, с проверкой кворума между шагами | ничего |

И выкатка Centrifugo сама по себе — **событие отказа**, а не рутинная операция: она порождает тот самый шторм переподключений. Значит её надо прогонять под нагрузкой как отдельный сценарий и мерить, сколько реконнектов в секунду она создаёт и как это отражается на Redis.

## Веб-клиент

Фронтенду не нужен доступ ни к Kafka, ни к Postgres. У него ровно два канала:

```
                    ┌──── HTTPS ──────→ API          история, отправка
браузер ────────────┤
                    └──── WebSocket ──→ Centrifugo   новые сообщения
```

| Сценарий | Как работает |
| --- | --- |
| Вход | Keycloak по OIDC с PKCE → access token → `GET /conversations` |
| Открытие диалога | `GET /conversations/{id}/messages?before_seq=…` — из Postgres через API |
| Новые сообщения | событие `message.created` по WebSocket от Centrifugo |
| Отправка | `POST /messages` → транзакция в Postgres и outbox |
| Переподключение | `recovered=true` — история из Centrifugo; `recovered=false` — `GET …?after_seq=X` |
| **Печатает** | публикация в `typing:{id}` **напрямую через Centrifugo** — без API, Kafka и Postgres |

Последняя строка — не оптимизация, а другой класс события. Индикатор «печатает» нечего сохранять, нечего доставлять офлайн и нечего восстанавливать при переподключении; проводить его через тот же путь, что и сообщение, значит нагружать Postgres и Kafka тем, что разрешено потерять. Подробности — в разделе про эфемерные события в первой части.

Это прямое следствие модели из первой части: **Centrifugo не заменяет HTTP API для чтения истории**. Он доставляет то, что происходит сейчас; всё, что было раньше, приходит из базы.

### Сборка и размещение

```
React + TypeScript + Vite  →  статика: index.html, JS, CSS, assets

Route53 → CloudFront → S3 (приватный бакет)

api.example.com     API
ws.example.com      Centrifugo
media.example.com   вложения
```
Серверный рендеринг сюда не нужен: интерфейс мессенджера после входа целиком динамический, а SEO для приватных переписок не существует. Статика на CDN — это HA почти бесплатно, против необходимости держать и масштабировать ещё один слой серверов.

Ассеты неизменяемые (`/assets/app-a8fc312.js`), переключается только `index.html` — откат фронта тогда мгновенный и не требует пересборки.

## Доступ к AWS без ключей

чего не делать

Не класть `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` в Secret Kubernetes. Это долгоживущие учётные данные, которые утекают вместе с любым доступом к кластеру и не ротируются сами.

```
ServiceAccount  →  роль IAM  →  временные учётные данные

consumer-attachments  →  только s3:GetObject, s3:PutObject
                          в конкретном бакете
```
EKS Pod Identity связывает роль IAM с ServiceAccount, и под получает временные ключи. Дальше — минимальные права на каждый сервис: API не администрирует Kafka, веб вообще не имеет доступа к AWS, потребитель аналитики не пишет в топик сообщений.

## Порядок работ, исправленный

В первой части он начинался с проверки корректности — то есть с середины. Полный:

- **1. Репозитории и конвейер.** Три репозитория, CI со сборкой по digest, ArgoCD на локальном кластере. Пока этого нет, всё остальное разворачивается руками и невоспроизводимо.
- **2. Локально — корректность.** Поток сообщения, дедупликация, восстановление, сквозные тесты с веб-клиентом. Убить relay после публикации до отметки; пользователь видит сообщение один раз.
- **3. Terraform и stage.** Три зоны, управляемые Postgres, Kafka, Redis. Тот же Helm, другие values.
- **4. Ёмкость по подпискам** на stage: профили `5k×1`, `5k×20`, `5k×100`, через боевой балансировщик — и **отдельно по доле печатающих** (1%, 5%, 10%, 20% при heartbeat 1–3 с), потому что она способна превысить нагрузку от самих сообщений.
- **5. Матрица отказов** сверху вниз, включая потерю зоны, с замером фактических RTO против заявленных.
- **6. Прод** — тот же digest, что прошёл stage.

Часть 2 архитектуры мессенджера. Первая часть — runtime-схема с матрицей отказов. Разделение на три репозитория, продвижение по digest, миграции расширение-сужение, политика выкатки по типу нагрузки, веб-клиент на статике за CDN и доступ к AWS через идентичность пода.
