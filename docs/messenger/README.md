## Статус реализации

Подробный журнал выполнения и доказательства готовности находятся в
[мастер-плане](../../IMPLEMENTATION-PLAN.md). На текущем подтверждённом срезе:

| Гейт | Статус | Что реально проверено |
| --- | --- | --- |
| G0 | ✅ | локальная платформа, GitOps, миграции, контракты и телеметрия |
| G1 | ✅ | регистрация, вход, подтверждение адреса, сессии, немедленный отзыв, авторизация и direct-беседы |
| G2-000 | ✅ | раздельные fact/content-топики, SCRAM и ACL; `unread` не может читать содержимое |
| G2-001 | ✅ | доменная модель сообщения и инварианты payload/seq/надгробия |
| G2-002 | ✅ | атомарные message + два outbox-события, идемпотентный повтор и живая инъекция отката |
| G2-003 | ✅ | аренда пачки, идемпотентная публикация со SCRAM; событие из базы доходит до потока |
| G2-004 | ✅ | `POST /conversations/{id}/messages`: 201 при приёме, 200 при повторе, 413 на длинный текст |
| G2-005 | ✅ | сборка пары, дедупликация и публикация в канал беседы; получатель видит сообщение один раз |
| G2 целиком | ✅ | путь целиком: вход → токен → беседа → POST → Postgres → outbox → Kafka → WebSocket |
| G3-000 | ✅ | контракт и схема: `after_seq` и неподвижная точка синхронизации, квитанции вместо `read`, `last_delivered_seq` с проверенным ограничением; `CTR` обязателен в CI, разрыв прошёл через одноразовую запись и она снята — baseline чист |
| G3-001 | ✅ | чтение страницами: история `HIST-001…004` с восстановлением вперёд и обеими половинами `DB-001`, плюс список бесед `LIST-001…003` — курсор принимается только парой, ответ объявлен компонентой `ConversationListPage`, — 47 проверок на живой базе; реплика страниц не обслуживает до stage |
| G3-002 | ✅ | квитанции доставки и прочтения: `POST /conversations/{id}/receipts` — одна запись `INSERT … ON CONFLICT DO UPDATE` с максимумом против хранимой строки, без транзакции; неучастие неотличимо от отсутствия, номер выше головы отвергается `400 invalid_receipt`; монотонность и `read ≤ delivered ≤ last_seq` доказаны живой гонкой двух устройств — 52 проверки на живой беседе; рассылка собеседнику намеренно не делается и остаётся открытой |
| G3-003 | ✅ | проекция непрочитанного: 64 проверки `unread_check.py` на живом кластере, ноль отказов, на том же дайджесте `sha256:6810735…`, которым включён `consumer-unread`. Повтор события не меняет счётчик дважды (монотонный чекпойнт беседы отсекает его порядком `conversation_seq`, а не журналом `event_id`), квитанция пересчитывает проекцию не дальше чекпойнта потребителя, `unread_count` отдаётся списком и восстанавливается из `messages` + `last_read_seq`, когда строки проекции нет, — в том числе для беседы, чьи события ушли из Kafka по сроку хранения; после проверки в базе не осталось следов |
| G3-004 | ✅ | присутствие и «был в сети»: 22 проверки `presence_check.py` на живом кластере, ноль отказов. Человек в сети, пока хоть одно его соединение продлевалось внутри окна 180 с, — агрегат по человеку, а не по соединению, поэтому отключение одного из двух устройств офлайн не делает; `users.last_seen_at` пишется при подтверждении соединения в той же транзакции, что и продление, и наружу отдаётся только она (`UserSummary.last_seen_at`). Перезапуск Centrifugo проверен на живой среде: при двух открытых соединениях уходящий узел закрыл их кодом `3001 shutdown`, отметка до и после совпала посимвольно, а офлайн наступил только по окну |
| G3 | ⬜ | догрузка при `recovered=false` в браузере и веб-клиент ещё не начаты |

То есть сообщение можно отправить и получить через публичный API, повтор
не превращается во второе сообщение, а историю можно читать страницами —
назад по `before_seq` и вперёд по `after_seq` до неподвижной точки
`sync_to_seq`. Читает её писатель: реплика не обслуживает страницы, пока не
умеет отвечать, догнала ли она границу страницы (иначе `before_seq` на
отставшей реплике молча теряет сообщения), — шов под неё есть, включения нет.

Квитанция тоже пишется: устройство сообщает `delivered_seq` и `read_seq`,
а сервер отвечает состоянием **после** применения — этим клиент и отличает
«применено» от «проигнорировано». Обе величины идут только вперёд: опоздавшая
квитанция ничего не откатывает, `read ≤ delivered ≤ last_seq` держится и на
живой гонке двух устройств, а не только на последовательном пересказе.
Номер выше головы беседы отвергается `400 invalid_receipt`, а не ограничивается
молча: клиент, приславший невозможное, обязан узнать об этом, а не получить
`200` и счесть квитанцию применённой. По чужой беседе ответ неотличим от
несуществующей. Собеседник о квитанции не извещается: схемы события нет и
под неё ничего не выдумано — транспорт квитанции к собеседнику это `G3-007`.

Присутствие и «был в сети» разведены и записаны. Человек в сети, пока хоть одно
его соединение продлевалось внутри окна 180 с (каденция продления — 120 с): два
устройства одного человека дают один онлайн, а не два, а офлайн наступает по
времени, а не по сигналу — прокси на отключение у Centrifugo нет, и о разрыве
сервер не узнаёт никогда, ни при закрытой вкладке, ни при оборванной сети. «Был
в сети» — это `users.last_seen_at`, отметка, выставленная при подтверждении
соединения в той же транзакции, что и продление; она переживает и уборку
реестра, и потерю его целиком. Вычислить её из момента ухода нельзя: уборщик
отстаёт на свой период, а при мёртвом уборщике не наступает вовсе. Наружу
отдаются два поля в списке бесед: отметка `UserSummary.last_seen_at` и признак
`UserSummary.online`. Второй считает сервер тем же предикатом по возрасту
отметки (`domain/presence.is_online`, окно 180 с) — отдельного агрегата по
`realtime_connections` для ответа на вопрос «в сети ли человек» нет, потому что
отметка уже прочитана, а признак из неё выводится. Realtime-событие смены
присутствия собеседникам не рассылается: значение верно на момент ответа REST,
а не на текущую секунду. У участника, с которым у зрителя есть блокировка, нет
ни `online`, ни `last_seen_at`: маска метаданных активности, пришедшая с
`G3-007` и записанная в `04-decisions.md`.

Следующий гейт — G3: согласованность клиента, вместе с самим клиентом.

Вне первой версии и не блокирует release gate: `CONS-005` (потребители поиска и
аналитики), `PERF-007` (беседа на 500 участников), группа укрепления.
