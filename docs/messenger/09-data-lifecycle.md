# Жизненный цикл данных

> kubernetes-finops-platform · мессенджер, часть 9

Что за данные, где их источник истины, сколько они живут и что означает их
удаление. Документ существует из-за прямого противоречия внутри уже принятых
решений, и начинается с его разрешения.

## Противоречие

```
схема сообщений     удаление — надгробие, физического DELETE не бывает
право на забвение   персональные данные обязаны исчезнуть
```

Оба требования настоящие. Надгробие нужно, потому что физическое удаление
ломает нумерацию в беседе, ответы на удалённое, состояние прочтения и
восстановление при переподключении. Стирание нужно, потому что человек имеет
право убрать свои данные.

**Разрешается разделением сообщения на конверт и содержимое.**

```
Конверт — остаётся                 Содержимое — уничтожается
──────────────────                 ─────────────────────────
message_id                         text
conversation_id                    метаданные вложения
conversation_seq                   персональные идентификаторы
created_at
deleted_at
type
ссылка на отправителя (может стать NULL)
```

Позиция `seq = 18382` в беседе остаётся занятой навсегда. Кто её занял и что
там было написано — может исчезнуть.

```
до стирания                после стирания
───────────                ──────────────
seq      18382             seq      18382
sender   91b2…             sender   NULL
payload  {"text": "…"}     payload  NULL
type     text              type     text
                           deleted_at проставлен
```

Собеседник видит «сообщение удалено» на своём месте в переписке — порядок цел,
ответы на это сообщение не висят в пустоте, счётчик непрочитанного сходится.

## Часть 1. Классы данных

| Класс | Источник истины | Хранение | Что значит «удалить» |
| --- | --- | --- | --- |
| Конверт сообщения | PostgreSQL | пока жива беседа | надгробие, строка остаётся |
| Содержимое сообщения | PostgreSQL | по политике | стирание значения |
| Вложение | объектное хранилище | по политике | физическое удаление объекта |
| Метаданные вложения | PostgreSQL | пока жив конверт | стирание значений, строка остаётся |
| Профиль | PostgreSQL | пока жива учётная запись | стирание, скелет остаётся |
| Сессии и устройства | PostgreSQL | до истечения или отзыва | физическое удаление |
| Событие Kafka | Kafka | 7 дней | истечение срока хранения |
| Кеш | Redis | минуты | инвалидация |
| Журналы | VictoriaLogs | по потоку, см. ниже | истечение срока |
| Трассы | Tempo | дни | истечение срока |
| Аудит | PostgreSQL | дольше всех | **не удаляется** |
| Резервные копии | RDS и объектное хранилище | срок копий | истечение срока |

Два ряда в этой таблице делают всю задачу трудной, и оба — ниже.

## Часть 2. Где стирание не работает напрямую

### Резервные копии

Копия неизменяема по своей природе. Из неё нельзя вырезать одного
пользователя — это перестанет быть копией, из которой можно восстановиться.

```
запрос на стирание
      ▼
база: стёрто немедленно
копии: содержат данные до истечения срока копии
```

Честный ответ пользователю: данные удалены из системы немедленно, из резервных
копий — по истечении срока их хранения. Срок называется числом, а не словом
«скоро».

**Важное следствие:** восстановление из копии обязано **повторно применить
журнал стираний**. Иначе восстановление воскрешает стёртые данные, и нарушение
происходит ровно в момент аварии, когда его никто не заметит.

```
восстановление из копии
      ▼
применить erasure_log за период после даты копии
      ▼
только потом пускать трафик
```

Это делает `erasure_log` таблицей, которая **сама никогда не стирается**: она
содержит идентификаторы и отметки времени, но не содержимое.

### Событие в Kafka

Событие `message.created.v1` несёт содержимое. Стереть его из середины лога
нельзя — лог append-only.

Решение простое и достаточное для v1: **срок хранения топика короче срока
исполнения запроса на стирание**. Семь дней против тридцати. К моменту, когда
стирание обязано завершиться, событие уже истекло само.

Это накладывает ограничение, которое надо помнить: увеличение срока хранения
топика — не безобидная настройка. Хранение дольше срока исполнения стирания
делает Kafka местом, где стёртые данные продолжают жить.

### Производные данные

Счётчики непрочитанного, кеш профилей, будущие индексы поиска — всё это копии.
Правило: **производное восстанавливается из источника истины, а не хранится
самостоятельно**. Тогда стирание в источнике убирает данные из производного
автоматически при следующем пересчёте, а инвалидация лишь ускоряет это.

Индекс поиска, который нельзя пересобрать из базы, — это второй источник
истины, и он потребует собственного пути стирания. Поэтому поиск и вынесен
за v1 (`CONS-005`).

## Часть 3. Что рассматривалось и не взято в v1

### Криптографическое стирание

Идея: содержимое шифруется ключом пользователя, стирание — уничтожение ключа.
Тогда копии, Kafka и любые производные хранилища становятся нечитаемыми
мгновенно и без обхода всех хранилищ.

Это правильный ответ на задачу — и он не берётся в v1 сознательно:

- требует управления ключами: хранилище, ротация, доступ, восстановление;
- работает только если **каждое** место, где лежит содержимое, шифрует тем же
  ключом — одно пропущенное сводит весь механизм к нулю;
- потеря ключа по ошибке неотличима от стирания и необратима;
- ключ становится новой точкой отказа на пути каждого сообщения.

Для v1 достаточно связки «немедленное стирание в базе + истечение копий».
Переход на криптостирание — отдельный ADR, и к нему готовит одно решение,
принятое уже сейчас: содержимое лежит в **отдельной колонке**, а не размазано
по конверту. Зашифровать одну колонку позже можно; вытащить содержимое из
десяти полей — миграция всей базы.

## Часть 4. Сроки хранения

| Поток журналов | Срок | Почему |
| --- | --- | --- |
| `application` | 7 дней | отладка живёт часами, не месяцами |
| `access` | 30 дней | разбор инцидента и злоупотреблений |
| `audit` | 1 год | требование к привилегированным операциям |
| `security` | 1 год | вход, отказы, злоупотребления |
| `deployment` | 1 год | «что изменилось» через полгода — обычный вопрос |
| `synthetic` | 30 дней | подтверждение SLO за период |

| Данные | Срок |
| --- | --- |
| Сообщения | пока жива беседа |
| Вложения | пока жив конверт; непривязанные — 24 часа |
| Трассы | 7 дней |
| События Kafka | 7 дней |
| Резервные копии | 35 дней |
| Журнал стираний | бессрочно |

Один срок на все журналы означает либо дорогой отладочный мусор, либо
потерянный аудит. Аудит и отладка — разные данные с разной ценой ошибки.

### Непривязанные вложения

Файл загружен, сообщение не отправлено. Такие объекты — оплаченное место
за ничто, и без уборщика их количество растёт монотонно. Через 24 часа
состояние `pending` или `uploaded` означает, что сообщения уже не будет.

## Часть 5. Что меняется в схеме

Документ блокирует заморозку схемы G1, и вот почему конкретно. Текущая
миграция делает стирание **невозможным**:

```sql
messages.payload     jsonb NOT NULL   ← содержимое нельзя обнулить
users.display_name   text  NOT NULL   ← имя нельзя обнулить
messages.sender_id   NOT NULL         ← ссылку нельзя разорвать
```

Стереть содержимое, не удаляя строку, при этих ограничениях нельзя — значит,
надгробие и стирание действительно несовместимы, ровно как и утверждалось.
Исправляется миграцией `0002`:

| Изменение | Зачем |
| --- | --- |
| `messages.payload` допускает NULL | содержимое стирается, конверт остаётся |
| `messages.sender_id` допускает NULL | отправитель стёрт, позиция в беседе цела |
| `users.display_name` допускает NULL | профиль стирается, скелет остаётся |
| `users.erased_at` | отличить стёртую учётную запись от удалённой |
| `attachments.erased_at` | объект удалён физически, строка помнит, что он был |
| таблица `erasure_log` | восстановление из копии повторно применяет стирания |

Проверка целостности переносится из ограничений столбцов в правило:
**у живого сообщения содержимое есть, у стёртого — нет**. Это проверяется
ограничением на уровне строки, а не `NOT NULL` на колонке.

## Часть 6. Операции

### Стирание учётной записи

```
запрос
  ▼
проверка: не под юридическим удержанием
  ▼
одной транзакцией:
  users:       display_name, email → NULL, erased_at
  messages:    payload → NULL, sender_id → NULL (сообщения этого автора)
  devices:     удалить физически
  sessions:    удалить физически
  attachments: пометить к удалению
  erasure_log: запись
  ▼
асинхронно: удалить объекты из хранилища
  ▼
кеши инвалидируются событием
  ▼
события Kafka истекают сами в течение 7 дней
```

Беседы не удаляются: в них остались сообщения других людей, и их переписка
принадлежит не только уходящему.

### Выгрузка данных

Право на забвение редко приходит одно — рядом всегда право на переносимость.
Выгрузка: профиль, список бесед, свои сообщения, свои вложения. Чужие
сообщения в выгрузку не входят: это данные собеседника.

### Юридическое удержание

Стирание при действующем удержании отклоняется, а не откладывается молча.
Отказ записывается в аудит: «стёрли, но не совсем» — худший из возможных
результатов, потому что о нём никто не узнает.

## Часть 7. Инварианты

**Д-1.** Позиция в беседе не исчезает. `conversation_seq` занят навсегда,
независимо от судьбы содержимого.

**Д-2.** Стирание необратимо. Нет «восстановить стёртое»: если восстановление
возможно, стирание не произошло.

**Д-3.** Восстановление из копии повторно применяет журнал стираний — до того,
как на систему пущен трафик.

**Д-4.** Производные хранилища не являются источником истины и восстанавливаются
из базы. Хранилище, которое нельзя пересобрать, требует собственного пути
стирания и отдельного решения.

**Д-5.** Срок хранения событий Kafka строго меньше срока исполнения стирания.

**Д-6.** Журнал стираний не содержит стираемых данных — только идентификаторы
и отметки времени. Иначе он сам становится их хранилищем.

аварии, когда проверять его никто не будет.
