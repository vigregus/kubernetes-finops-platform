**Статус: проект, не реализовано** (кроме отмеченного в части 0). Решение — [ADR 0009](../ADR/0009-resilient-access-and-guest-calls.md);
база — звонки 1:1 из [части 17](17-calls.md).

## 1. Цель

Мессенджер должен оставаться доступным из обычного современного браузера при частичном ограничении сетевых протоколов:

- блокировке UDP;
- блокировке QUIC;
- блокировке WebSocket;
- недоступности прямого WebRTC;
- недоступности отдельного TURN;
- фильтрации отдельных доменов или IP;
- кратковременном отказе realtime-инфраструктуры.

Система **не обещает абсолютную невозможность блокировки**. Оператор, контролирующий IP-маршрутизацию, DNS и HTTPS-доступ, всегда может сделать сервис недоступным достаточно грубой блокировкой.

Цель другая:

> Для прекращения работы мессенджера должно быть недостаточно заблокировать один характерный протокол, один WebSocket endpoint, UDP или один TURN-сервер. Клиент автоматически переходит на стандартные браузерные транспорты.

Дополнительная продуктовая возможность:

> Пользователь может создать ссылку на звонок, отправить её человеку любым способом и начать аудио- или видеозвонок прямо в браузере. Получателю не требуется устанавливать приложение и, для гостевого режима, создавать аккаунт.

## 2. Основные сценарии

### Обычный пользователь

Зарегистрированные A и B используют существующую беседу: чат → позвонить B → WebRTC direct или TURN fallback. Поведение существующих звонков не меняется.

### Звонок по ссылке

A создаёт ссылку `https://call.example.com/j/7f82...`. Интерфейс показывает «Скопировать ссылку» и «Начать звонок». A отправляет ссылку B через любой внешний канал. B открывает её в браузере, разрешает микрофон и камеру и входит в звонок. Регистрация B не обязательна.

A может открыть ту же ссылку сам. Если A аутентифицирован и является владельцем комнаты, он подключается как `host`, а не занимает гостевое место.

```text
             invite URL
                 │
        ┌────────┴────────┐
        │                 │
     Host A             Guest B
   authenticated       anonymous
        │                 │
        └──── call room ──┘
                  │
                WebRTC
```

## 3. Гостевая ссылка: модель безопасности

Ссылка — capability: кто получил её секрет, получает право войти **только в конкретную call-room**. Она не даёт доступа к аккаунту владельца, другим беседам, поиску пользователей, истории основной беседы, созданию обычных сообщений, другим звонкам и постоянному TURN-доступу.

### Где живёт гостевая сессия

`GuestSession` переживает reload, поэтому её секрет где-то хранится. **Не `localStorage` и не `sessionStorage`**: любой скрипт страницы читает их. Только `HttpOnly; Secure` cookie с `Path`, ограниченным страницей и API комнаты, `SameSite=Strict`, TTL короче жизни комнаты, привязкой к origin гостевой страницы и отзывом на сервере (отзыв ссылки, удаление гостя и конец комнаты немедленно обрывают сессию).

### Формат ссылки

Секрет не помещается в query-параметр. Вместо `/join?id=123&token=SECRET`:

```text
https://call.example.com/j/<invite_id>#<invite_secret>
```

Fragment `#…` браузер не отправляет серверу. Фрагмент виден **любому скрипту страницы** до `replaceState()`, хотя сервер его никогда не получает. Поэтому страница входа гостя изолирована: строгая CSP (`script-src 'self'`, без `unsafe-inline`), никаких сторонних скриптов, аналитики и сборщиков ошибок, читающих URL, обмен выполняется как можно раньше, `replaceState` сразу после ответа.

После загрузки frontend делает:

```text
fragment secret
      ↓
POST /guest-invites/{invite_id}/exchange
      ↓
short-lived guest session
      ↓
history.replaceState(...)
```

После обмена адресная строка — `https://call.example.com/j/<invite_id>`, секрет в URL не остаётся. Дополнительно: `Referrer-Policy: no-referrer`, `Cache-Control: no-store`.

## 4. Жизненный цикл приглашения

По умолчанию: TTL 15 минут до первого входа; один гость; повторно не используется; комната — host + 1 guest.

```text
created
   │
   ├── revoke ─────────────► revoked
   │
   ├── TTL ────────────────► expired
   │
   └── guest exchange
             ↓
          consumed
             ↓
       guest session
```

`consumed` не означает, что reload выбрасывает гостя. При первом успешном exchange создаётся отдельная краткоживущая `GuestSession`; она переживает reload до завершения комнаты или истечения TTL сессии. Украденная первоначальная ссылка после входа первого гостя второго участника не создаёт.

## 5. Call principal

Гость не превращается в фиктивного `User`. В домене — обобщённый участник:

```text
CallPrincipal
 ├── UserPrincipal   (user_id)
 └── GuestPrincipal  (guest_session_id)
```

В `call_participants`: `call_id`, `principal_type`, `user_id` nullable, `guest_session_id` nullable. Инвариант: **ровно одно** из `user_id` / `guest_session_id`. Модель зарегистрированного пользователя остаётся прежней.

## 6. Права гостя

```text
call:<room_id>:join
call:<room_id>:signal
call:<room_id>:media
call:<room_id>:leave
```

Нет: `conversations:read`, `messages:read`, `users:search`, `calls:create`, `sessions:read`. Компрометация гостевого токена не превращается в компрометацию аккаунта.

## 7. Текстовый чат гостя

В первой версии ссылка **не открывает основную переписку**. Допустим отдельный временный чат комнаты, существующий только в её контексте и исчезающий вместе с комнатой. Постоянная история — отдельное продуктовое решение, а не побочный эффект гостевого звонка.

## 8. Устойчивость realtime

> WebSocket — быстрый транспорт, но не источник истины.

```text
WebSocket ──fail──► SSE ──fail──► HTTPS long poll
```

Исходящие действия во всех вариантах идут обычным HTTPS API, поэтому блокировка `Upgrade: websocket` не отключает чат и сигнализацию звонка.

```ts
interface RealtimeTransport {
    connect(): Promise<void>
    close(): void
    onEvent(handler: (event: ServerEvent) => void): void
}
```

Реализации: `WebSocketTransport`, `SseTransport`, `PollingTransport`. Логика чата и звонка не знает, какой транспорт используется.

## 9. Надёжная сигнализация звонка

Простого best-effort `publish` недостаточно: потеря `offer` или `answer` ломает установку. Сигнал несёт `call_id`, `generation`, `seq`, `client_signal_id`, `expires_at`, `payload`.

Если публикация не подтверждена, HTTP-успех не возвращается; клиент безопасно повторяет запрос с тем же `client_signal_id`, второй логический сигнал не создаётся. После переподключения получатель может запросить `GET /calls/{id}/signals?after=<seq>`; сигналы хранятся 30–60 секунд и привязаны к `generation`, поэтому старый `offer` не воскресает после reconnect.

## 10. Устойчивость медиа

```text
1. host / direct → 2. STUN / srflx → 3. TURN UDP → 4. TURN TCP → 5. TURN TLS/TCP :443
```

Это **приоритет**, а не последовательность попыток: браузер собирает кандидаты (host, srflx, relay по каждому транспорту)
и проверяет пары параллельно, выбирая лучшую из работающих по вычисляемому приоритету (RFC 8445). Порядок URL в списке
`iceServers` **не** выбирает транспорт: поставить `turns:` первым — не значит, что ICE его предпочтёт. Два следствия для времени
установки. Сбор кандидатов по заблокированному UDP ждёт таймаута, пока TCP и TLS уже готовы; бюджет установки — `SETUP_SECONDS`
= 30 с, а перезапуск ICE при обрыве — 15 с.

Поэтому «липкий» транспорт — не перестановка URL, а явная процедура:

1. Устройство запоминает последний сработавший транспорт (`last_success`: `udp` / `tcp` / `tls`) и сеть, где он сработал.
2. Следующий звонок идёт обычным ICE, а известный рабочий relay заранее доступен (`iceCandidatePoolSize`, раннее получение
   данных TURN).
3. Прямому пути дан **ограниченный** срок (например 8–10 с). Если за него соединение не поднялось, явный перезапуск ICE с
   `iceTransportPolicy: "relay"` (флаг для отладки есть, автоматики нет).

### Матрица блокировок: что работает и что нет

| Что закрыто | Чат и сигнализация звонка | Медиа звонка | Состояние |
| --- | --- | --- | --- |
| Ничего | WebSocket | прямое (`host` / `srflx`) | работает |
| QUIC (UDP 443, HTTP/3) | браузер откатывается на HTTP/2: на нас не влияет | не затрагивается | работает |
| UDP целиком | не влияет | TURN по TCP; без `RES-005` порт 3478 нестандартный и часто тоже закрыт | **частично**: нужен TURN/TLS :443 (`RES-005`) |
| UDP и нестандартные TCP-порты | не влияет | только `turns:` на 443 | нужен `RES-005` |
| WebSocket | запасные SSE, затем опрос HTTPS (`RES-001…003`); отправка по HTTPS работает всегда; пропущенное забирает `GET …/signals?after=` | не влияет | сейчас **сигнализация звонка не поднимается**: «Connecting to the call service…» |
| Потоковые ответы (SSE буферизует прокси) | остаётся только опрос | не влияет | опрос обязателен, SSE нельзя считать надёжным |
| STUN | не влияет | прямое по `host`, иначе relay | работает, доля relay растёт |
| Один TURN | не влияет | второй из набора (`RES-006`) | без `RES-006` звонок не устанавливается |
| Домен или IP звонков по SNI | страница и API открываются, TURN нет | TURN на **отдельном** хосте, другой домен | отдельный хост TURN — решение, не побочный эффект |
| TLS-инспекция (корпоративный прокси) | работает, если прокси пропускает WebSocket | `turns:` через инспекцию обычно **не проходит** | известный предел |
| WebRTC выключен политикой браузера (Lockdown на iOS, корпоративная политика) | чат работает | звонок **невозможен** | кнопки звонка недоступны с причиной (`calls.supported`), без обходов |
| IPv6-only сеть (NAT64, мобильные операторы) | работает | TURN задаётся **именами хостов**, а не IPv4-литералами: DNS64 синтезирует адрес | проверить на сотовой сети |

### Частичные блокировки (в том числе ТСПУ): допущения и границы

Мы **не пытаемся обмануть** систему фильтрации. Строим несколько стандартных транспортных путей и убираем зависимость от одного
легко отключаемого протокола.

```text
СИГНАЛИЗАЦИЯ                          МЕДИА
WebSocket                             direct / host
   ↓ сбой                                ↓
SSE                                   STUN / srflx
   ↓ сбой                                ↓
HTTPS-опрос                           TURN/UDP
   ↓                                     ↓
GET /calls/{id}/signals?after=…       TURN/TCP
                                         ↓
                                      TURN/TLS :443  ──►  TURN A | TURN B
```

Устойчивость даёт сочетание двух цепочек, а не одна из них.

**Что известно и что нет.** Публичные наблюдения: ограничение звонков Telegram и WhatsApp (с августа 2025) было **селективным**:
другие приложения на WebRTC (например Imo) продолжали работать, то есть это не «WebRTC запрещён целиком»
([The Insider](https://theins.ru/en/news/284015)). ТСПУ как оборудование умеет анализировать не только адрес назначения, но и
характер трафика ([Медиазона](https://en.zona.media/article/2026/04/07/russian_internet_censorship_2026)). Разборы пользователей
называют вероятной техникой распознавание STUN по фиксированному magic cookie `0x2112A442` ([Хабр](https://habr.com/en/articles/971480)),
но это не документация регулятора или оператора и не подтверждено для конкретных сетей. Поэтому в решениях мы пишем «по публичным
наблюдениям одна из вероятных техник — распознавание STUN по фиксированной сигнатуре», а не «ТСПУ блокирует STUN именно так».

**Следствия для проекта:**

- Исходим не из «в России UDP не работает», а из «UDP/STUN может работать — тогда используем его первым; не работает — переходим дальше
  автоматически». На сетях, где фильтруется чистый STUN/UDP или закрыт весь UDP, прямой путь, STUN и TURN/UDP **нельзя считать
  надёжными**.
- **Обычный TURN — расширение STUN**: почти все его управляющие сообщения имеют STUN-формат (RFC 8656), поэтому `turn:` по UDP и по
  TCP оставляет протокол наблюдаемым на соединении клиента. **`turns:` на 443** прячет TURN-управление и ретранслируемые данные внутри
  TLS **на участке «браузер → TURN»**. Участок «TURN → собеседник» по RFC идёт по UDP на стороне сервера, и для модели угроз
  достаточно первого: оператор пользователя видит TLS-соединение к TURN, а не открытый STUN/TURN.
- **Это не «единственный путь, который нельзя определить»**, а **наиболее устойчивый стандартный браузерный запасной путь** в нашей
  архитектуре. Снаружи по-прежнему видны IP назначения, порт 443, SNI (если не скрыт), метаданные TLS-рукопожатия, объём и тайминг.
  Блокировка домена `turn.example.com` или его IP выключит эту точку.
- **Два клиента в сетях РФ**: прямое `A ↔ B` по UDP может не подняться, но звонку это не нужно. Нужно, чтобы **каждый клиент отдельно**
  смог установить TLS-соединение хотя бы с одним TURN. Это существенно достижимее.
- **`RES-006` нужен не «потом», а рядом с `RES-005`.** Один идеальный TURN/TLS:443 — это один IP, одно имя, одна точка отказа.
  Схема `TURN A / TURN B`, желательно у разных провайдеров и в разных сетях: это обычная отказоустойчивость, а не маскировка.
  Реализовывать серией PR: `RES-005` и `RES-007` (P0), сразу за ними `RES-006`.

**Что план закрывает, а что нет** (после `RES-001…003`, `RES-005`, `RES-006`):

| Тип ограничения | Помогает ли план |
| --- | --- |
| UDP закрыт | очень хорошо (TURN/TCP, затем TLS:443) |
| STUN/ICE или TURN по UDP режется | хорошо |
| TCP 3478 режется | хорошо, через TURN/TLS :443 |
| WebSocket режется | хорошо, запасные SSE и опрос |
| Один TURN или его IP недоступен | хорошо, второй TURN |
| Фильтрация по сигнатуре чистого STUN/TURN | хорошо: TURN-управление внутри TLS |
| Фильтрация по SNI `turn.example.com` | **плохо** |
| Блокировка IP наших TURN | **плохо** |
| Блокировка домена или API целиком | почти не помогает |
| Allowlist-режим мобильного интернета (разрешён только список сервисов) | **не поможет**, пока нашего сервиса в списке нет |
| TLS-инспекция с доверенным клиентом корневым сертификатом | существенно хуже |

Три уровня противника: **(1) файрвол или простой DPI** (UDP, STUN, 3478, WebSocket закрыты) — здесь план очень силён;
**(2) селективный DPI** (сигнатура чужого мессенджера, чужие relay-адреса, отдельные SNI) — пока Vector не стал отдельной целью, шанс
работы высокий: свой домен, свои TURN, TLS:443, обычный HTTPS для сигнализации; **(3) блокировка именно Vector** (наши домены и IP)
— транспортные запасные пути принципиально не помогают, а `RES-006` (несколько TURN) здесь **отказоустойчивость, а не защита от
решительного цензора**: список наших адресов конечен. Дальше шёл бы уже не мессенджер, а система обхода цензуры (доменный фронтинг,
быстрая смена IP, свои обфускации) — это другая архитектура и вне объёма (§12).

**Формулировка цели:** не «анти-ТСПУ», а «для прекращения работы должна потребоваться более специфичная блокировка именно нашего
сервиса; простого отключения UDP, STUN, WebSocket или одного relay недостаточно». Расширять архитектуру дальше до реальных измерений не
нужно: сначала `RES-005` + `RES-006` + запасная сигнализация, затем измерения у МТС, МегаФона, Билайна, Ростелекома, и только по данным
решаем, есть ли проблема, которую дизайн не закрывает.

**Граница, которую записывает ADR.** Если оператор блокирует сам домен или IP сервиса либо весь доступ к нему, архитектура «только
браузер» звонок не гарантирует. Чат при этом может остаться (другие пути), но обещаний «неблокируемости» нет.

| Сетевое условие | Ожидаемый результат |
| --- | --- |
| Всё разрешено | прямой WebRTC |

| Весь UDP закрыт | TURN/TCP |

| WebSocket пропал во время `offer` | повтор сигнала через REST (`GET …/signals?after=`) |
| Прямой путь умер при смене сети | перезапуск ICE → relay |
| TURN/TLS тоже недоступен | звонок честно «недоступен», чат остаётся |

Эта матрица полезнее заявления «устойчиво к ТСПУ»: каждая строка — проверяемый сценарий (`RES-A…`, фикстурные блокировки в стенде).

### «Проверка сети»: возможности сети, а не детектор

В панели готовности (`CALL-019`) — проверка, что **работает именно у этого человека**:

```text
Realtime:  ✓ HTTPS   ✓ WebSocket   ✓ SSE
Media:     ✗ прямой UDP   ✗ TURN/UDP   ✗ TURN/TCP :3478   ✓ TURN/TLS :443
Ожидаемый путь звонка: TURN/TLS
```

**Нужны диагностические учётные данные TURN.** Сейчас данные TURN выдаются только участнику принятого звонка, а без них настоящий
`Allocate` не выполнить: проверка до звонка невозможна. Отдельная выдача `POST /network-check/turn-credentials`: срок 30–60 с, очень
жёсткий лимит частоты, только текущему аутентифицированному человеку и устройству, малая квота (проверка, а не канал), не
пригодна как публичный TURN. Без этого «Network capabilities» остаётся схемой, которую модель безопасности не позволяет реализовать.

Называется **«Network capabilities»**, а не «детектор ТСПУ»: один и тот же результат дают корпоративный файрвол, гостиничный Wi-Fi,
CGNAT, домашний роутер и сеть без UDP. Приложение не делает вывода «обнаружен ТСПУ». Результаты с реальных операторов (мобильные
и домашние сети) — единственный способ получить данные: из облака эти сети не воспроизвести.

### Телеметрия, чтобы решать по данным

На звонок, **без** меток пользователя, IP и идентификатора звонка (высокая кардинальность): `signaling_transport`
(`websocket | sse | poll`), `initial_media_path` (`host | srflx | relay`), `turn_transport` (`udp | tcp | tls`),
`ice_restart` (`yes | no`), `setup_result` (`success | timeout | failed`).

**Чтобы сказать «в мобильных сетях РФ», нужна грубая сетевая размерность.** Из набора выше она не выводится, а IP в метки нельзя.
Сервер при приёме отчёта вычисляет и пишет **только** низкокардинальный агрегат: `network_country` (`RU | ES | …`, страна по GeoIP)
и `network_class` (`mobile | fixed | unknown`, по классу автономной системы); сам IP не сохраняется и в метки не попадает. Это решение
о приватности: оно записывается в ADR при реализации `RES-009`, по умолчанию набор меток закрытый и короткий. Альтернатива — отдельный
аналитический конвейер событий. Через месяц это даст доли («relay в мобильных сетях РФ — столько, TURN/TLS — столько»), а не
предположения.

Что в матрице блокировок выше ещё **не сделано**: запасные транспорты (`RES-001…003`), TURN/TLS :443 (`RES-005`) и несколько TURN
(`RES-006`) — всё ⬜ в бэклоге. Сейчас стенд даёт только UDP и TCP на 3478.

**TURN/TLS на 443 делит порт с HTTPS шлюза** (`cilium-gateway-edge`). Для первой версии — **отдельный публичный адрес и имя
хоста для TURN** (`app.example.com` → IP A :443, `turn.example.com` → IP B :443), а не разбор по SNI на одном адресе. Причины:
проще отладка, сертификаты и маршрутизация L4, проще оценка ёмкости, меньше радиус отказа, и главное — **проблема TURN не
превращается в проблему основного HTTPS** (изоляция отказов). Разбор по SNI (`ssl_preread`, `TLSRoute`) остаётся возможной
оптимизацией позже. Сертификат для `turns:` выдаёт cert-manager; coturn живёт за собственным именем.

**Качество на TCP и TLS.** Релей по TCP имеет блокировку очереди на потере пакетов, и Full HD 4 Мбит/с на нём может быть
нестабилен, но жёсткое правило «TCP → всегда 1,5 Мбит/с» неверно: хороший короткий TCP-релей тянет больше, плохой — меньше. Поэтому
при выбранном TURN по TCP или TLS задаётся **начальный потолок** (порядка 720p и 1,5 Мбит/с), дальше режим «Auto» адаптируется по
статистике WebRTC: `availableOutgoingBitrate`, `currentRoundTripTime`, `packetsLost`, `framesDropped`, `qualityLimitationReason`.
Что реально выбрано, берётся из `getStats()` у выбранной пары (`relayProtocol: "udp" | "tcp" | "tls"`; поле есть в Chromium, в
Safari и Firefox наличие проверить) — из него же метрика `messenger_call_turn_transport_total`.

## 11. Несколько TURN endpoints

Один TURN — единая точка блокировки. `TurnProvider` возвращает набор endpoint'ов разных регионов или провайдеров:

```text
CompositeTurnProvider
 ├── CoturnProvider A
 ├── CoturnProvider B
 └── external provider
```

Отказ одного не лишает клиента остальных. Формат ответа — список `ice_servers`, у каждого свой `urls`.

## 12. Никакого собственного wire protocol

Не вводятся собственные TCP-фреймы, magic bytes и UDP-рукопожатия: такой протокол быстро становится устойчивой сигнатурой. Используются стандартные HTTPS, HTTP/2, HTTP/3, WebSocket, SSE, WebRTC, TURN, TLS. Цель — не сделать трафик «невидимым», а убрать единственную простую сигнатуру, отключение которой ломает продукт.

## 13. Endpoint discovery

Клиент не привязан навечно к одному realtime/TURN endpoint. Начальная конфигурация (подписана сервером) перечисляет адреса realtime и регионы TURN; при отказе клиент переходит на следующий. Домены не ротируются хаотично, чужие домены и domain fronting не используются.

## 14. Ограничение: только браузер

Клиент **не может** создавать сырые TCP-сокеты, менять TLS-отпечаток браузера, строить IP-туннель, управлять маршрутизацией ОС, перехватывать системный трафик. Поэтому существуют сети, способные запретить сервис полностью; это принимается как ограничение продукта. Более сильная устойчивость потребует отдельного нативного клиента — это другая архитектура.

## 15. Интерфейс звонка по ссылке

Владелец: `[ Позвонить ]  [ Создать ссылку ]`. После создания — ссылка, «Скопировать ссылку», «Войти в звонок», «Отозвать ссылку».

Гость видит имя организатора, переключатели микрофона и камеры и «Присоединиться». **До нажатия «Присоединиться» WebRTC не создаётся.**

## 16. Личность гостя

В v1 аккаунт не нужен. Гость может указать отображаемое имя: 1–64 символа, не уникально, не становится `User.display_name`, не используется для авторизации. В интерфейсе гость визуально отличается от зарегистрированного пользователя.

## 17. Управление хозяином

Владелец может завершить звонок, отозвать ссылку, удалить гостя, запретить повторный вход, закрыть вход новым гостям. Позже (не v1): зал ожидания, пароль/PIN, несколько гостей.

## 18. Защита от злоупотреблений

Гостевой звонок не должен стать бесплатным публичным TURN. Действуют одновременно: TTL приглашения и гостевой сессии, один гость на приглашение, лимиты на создание приглашений, обмен и сигнализацию, пользовательская и общая квоты TURN, короткие TURN-доступы, выдача доступа **только после допуска**: приглашение валидно + гостевая сессия валидна + комната допустила. Одно открытие ссылки TURN-доступа не даёт.

## 19. Переподключение

Гость переживает reload, краткий обрыв Wi-Fi, переход Wi-Fi → мобильная точка, переподключение realtime и ICE restart — пока гостевая сессия валидна, комната жива и хозяин не удалил гостя. Reload не требует повторно использовать секрет приглашения.

## 20. Наблюдаемость

Realtime: `messenger_realtime_transport_total{transport="websocket|sse|poll"}`, `messenger_realtime_fallback_total{from,to,reason}`.

Звонки: `messenger_call_initial_path_total{type="host|srflx|relay"}`, `messenger_call_current_path_total{type}`, `messenger_call_ever_relay_total`, `messenger_call_turn_transport_total{transport="udp|tcp|tls"}`.

Гости: `messenger_guest_invites_total{result="created|consumed|expired|revoked"}`, `messenger_guest_join_total{result="joined|denied|expired|occupied"}`.

`invite_id`, `room_id`, `user_id` и IP **не** являются метками.

## 21. Критерии приёмки

Идентификаторы приёмки отличаются от идентификаторов задач (часть 22) приставкой `A`, чтобы не совпадать.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| LINK-A1 | A создаёт ссылку; B в приватном окне без входа открывает её; A входит как host | аудио идёт в обе стороны |
| LINK-A2 | То же для видео | растут `packetsReceived` и `bytesReceived` |
| LINK-A3 | Второй аноним открывает занятую ссылку | `409 invite_occupied`, звонок первых двоих не меняется |
| LINK-A4 | Отозванная ссылка | не принимается |
| LINK-A5 | Просроченная ссылка | не принимается |
| LINK-A6 | Гость обращается к `GET /conversations`, `/messages`, `/users` | отказ |
| LINK-A7 | Reload браузера гостя | сессия и звонок восстановлены |
| RES-A1 | WSS недоступен | работает SSE; чат и сигнализация живы |
| RES-A2 | WSS и SSE недоступны | работает HTTPS polling; сообщения доставляются |
| RES-A3 | UDP заблокирован | звонок через TURN/TCP |

| RES-A8 | `offer` опубликован, но HTTP-ответ потерян | повтор с тем же `client_signal_id` не даёт двух `offer` |

## 24. Определение готовности

Фича не готова оттого, что два браузера на одном ноутбуке увидели друг друга. Для «готово» одновременно существуют: обычный звонок, звонок по ссылке, forced TURN relay, TURN/TLS :443, realtime fallback, повтор и идемпотентность сигнала, восстановление после смены сети, метрики, тесты отказов.

Контракт для человека:

> Открой сайт или полученную ссылку в современном браузере. Если прямой сетевой путь недоступен, клиент автоматически использует следующий доступный стандартный транспорт. Установка отдельного приложения для чата, аудио- или видеозвонка не требуется.
