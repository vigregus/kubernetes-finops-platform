# Инженерный стандарт

> kubernetes-finops-platform · мессенджер, часть 7

Договорённости, которые должны существовать **до** первой строки кода. Не стиль
ради стиля: каждое правило здесь отвечает на вопрос «что придётся переделывать,
если договориться позже».

## Что уже зафиксировано и здесь не переоткрывается

| Что | Где |
| --- | --- |
| Формат REST | `packages/contracts/openapi.yaml` |
| Схемы событий Kafka | `packages/contracts/kafka/` |
| Каналы и полезная нагрузка WebSocket | `packages/contracts/websocket/` |
| Эксплуатационные события | `packages/contracts/events/` |

| Схема базы | `db/migrations/` |

Этот документ добавляет то, чего в них нет: сквозное именование между слоями,
правила зависимостей, таксономию ошибок и контракты на уровне сигнатур.

## Где проходит граница планирования

```
фиксируем заранее          решаем при реализации
─────────────────          ─────────────────────
границы модулей            внутренние функции
сигнатуры сервисов         структуры данных внутри слоя
сигнатуры репозиториев     порядок операций
коды и типы ошибок         оптимизации
именование во всех слоях   разбиение на приватные методы
правила транзакций
```

Расписать заранее каждую внутреннюю функцию не получится: это и есть
переделывание по сто раз, только на бумаге и без обратной связи от кода.
Границы же переживают любую переделку внутренностей — и именно из-за них
переписывают соседние модули, когда договорились поздно.

## Часть 1. Именование

### Один и тот же смысл в пяти слоях

Главный источник расхождений — одно понятие под разными именами. Правило:
**имя меняет только регистр и разделитель, но не слова**.

| Слой | Стиль | Пример |
| --- | --- | --- |
| JSON в API | `snake_case` | `conversation_id`, `client_message_id` |
| Python | `snake_case` | `conversation_id` |
| TypeScript | `camelCase` | `conversationId` |
| Таблицы и колонки | `snake_case` | `conversation_id` |
| Метки метрик | `snake_case` | `route`, `result` |
| Переменные окружения | `SCREAMING_SNAKE` | `DATABASE_HOST` |
| Топики Kafka | точки и версия | `messenger.events.v1` |
| Типы событий | точки | `message.created` |
| Каналы Centrifugo | двоеточие | `conversation:{id}` |

**Преобразование имён происходит ровно в двух местах**: в сериализаторе API и
в сгенерированном клиенте TypeScript. Нигде больше. Ручное
`snake_to_camel` в середине бизнес-логики — признак того, что граница
размазалась, и это повод для отказа на ревью.

### Слова, которые означают строго одно

Глоссарий важнее стиля. Одно и то же под двумя именами — самая дорогая мелочь
в проекте.

| Слово | Значение | Не путать с |
| --- | --- | --- |
| `message_id` | идентификатор сообщения в системе | `client_message_id` |
| `client_message_id` | идентификатор, выданный клиентом для идемпотентности | `message_id` |
| `seq` | номер внутри беседы, монотонный | временем создания |
| `event_id` | идентификатор события и ключ корреляции; **не** поле дедупликации | `message_id` |
| `applied_through_seq` | наибольший применённый `conversation_seq` беседы; он же признак повтора | `last_read_seq` |
| `trace_id` | идентификатор трассы | `request_id`, `message_id` |
| `delivered` | устройство получателя приняло | `sent` |
| `sent` | транзакция в Postgres завершена | `delivered` |
| `read` | `last_read_seq ≥ seq` | `delivered` |

### Что нельзя называть

```
data, info, obj, item, temp, res, val, helper, utils, manager, handler2
get_data(), process(), handle(), do_work()
```

Причина не в эстетике: `utils.py` — это модуль, в который через полгода
складывают всё, что не нашло места, и он становится узлом, от которого
зависят все слои сразу.

### Логические значения

Имя булева значения — утверждение, а не вопрос и не отрицание.

```
is_deleted     да
has_attachment да
can_publish    да

deleted_flag   нет — «флаг» ничего не добавляет
not_visible    нет — двойное отрицание в условии нечитаемо
check_access   нет — это глагол, значит функция, а не значение
```

### Функции

```
глагол_существительное        send_message, claim_outbox_batch
get_*      только чтение без побочных эффектов и без обращения по сети
fetch_*    чтение с обращением по сети или в базу
list_*     возвращает коллекцию, всегда с пагинацией
ensure_*   идемпотентно приводит к состоянию
*_or_none  возвращает None вместо исключения
```

`get_user()`, который идёт в базу, — обычная причина того, что кто-то вызывает
его в цикле и получает запрос на каждую итерацию.

## Часть 2. Слои и зависимости

```
api/          HTTP: разбор запроса, проверка схемы, коды ответа
   ↓
services/     бизнес-правила: транзакции, идемпотентность, права
   ↓
repositories/ только Postgres: SQL, транзакции, блокировки
adapters/     всё остальное снаружи: Kafka, Redis, объектное хранилище,
              Centrifugo, почта, Web Push
   ↓
domain/       типы и правила, не знающие ни о базе, ни о HTTP
```

Разделение на `repositories` и `adapters` не косметическое. Первая редакция
писала «репозитории не делают сетевых вызовов», перечисляя среди них Kafka,
Redis и объектное хранилище, — то есть требовала невозможного. Разница
существенна: репозиторий участвует в транзакции вызывающего, адаптер —
принципиально не может, потому что откатить отправку в Kafka нельзя.

**Зависимости идут только вниз.** Проверяется автоматически, а не на ревью:

| Слой | Что может импортировать |
| --- | --- |
| `api` | `services`, `domain` |
| `services` | `repositories`, `adapters`, `domain` |
| `repositories` | `domain` |
| `adapters` | `domain` |
| `domain` | ничего из проекта |

Следствия, ради которых правило и существует:

- `domain` не импортирует `fastapi` и `psycopg` — значит, доменные правила
  тестируются без базы и без поднятого приложения;
- `api` не импортирует `repositories` — значит, обработчик не может втихую
  сходить в базу мимо транзакции;
- `services` не импортирует `api` — значит, бизнес-правило не зависит от того,
  пришло оно по HTTP, из потребителя Kafka или из административной команды.

Последнее особенно важно: одно и то же правило вызывается из трёх мест, и если
оно знает про `Request`, два из них сломаются.

## Часть 3. Контракты сервисного слоя

Сигнатуры фиксируются, тела — нет.

```python
async def send_message(
    conn: Connection,
    *,
    sender_id: UserId,
    conversation_id: ConversationId,
    client_message_id: ClientMessageId,
    kind: MessageKind,
    payload: MessagePayload,
    attachment_ids: Sequence[AttachmentId] = (),
) -> SendMessageResult:
    """Принимает сообщение. Идемпотентно по client_message_id.

    Повтор возвращает существующее сообщение с тем же message_id и seq
    и признаком created=False. Дубля не создаёт.
    """
```

Правила, которые здесь видны и обязательны для всех сервисных функций:

**Только именованные аргументы.** `*` после первого параметра. Два подряд
идущих `UUID` в позиционном вызове однажды поменяются местами, и это будет
сообщение, отправленное не в ту беседу.

**Собственные типы вместо `str` и `UUID`.** `UserId` и `ConversationId` —
разные типы, даже если внутри оба `UUID`. Проверка типов ловит перепутанные
аргументы до запуска; `str` не ловит ничего.

**Соединение передаётся, а не берётся изнутри.** Тогда вызывающий владеет
транзакцией, и два вызова можно объединить в одну. Функция, сама берущая
соединение из пула, не может участвовать в чужой транзакции — а именно это
потребуется, когда сообщение и запись в outbox должны лечь одним коммитом.

**Возвращается объект результата, а не кортеж и не словарь.** Кортеж из трёх
элементов меняет смысл при добавлении четвёртого; словарь не проверяется
типами. `SendMessageResult` расширяется без слома вызывающих.

**Ожидаемый отказ — значение, неожиданный — исключение.**

```python
# Ожидаемо: пользователь не участник беседы. Это не ошибка программы.
if not membership:
    return SendMessageResult.rejected(ErrorCode.NOT_A_MEMBER)

# Неожиданно: база недоступна. Ловить это здесь нечем и незачем.
```

Граница простая: если отказ описан в OpenAPI как `4xx` — это значение. Если он
означает «система сломана» — исключение.

### Контракты репозиториев

```python
async def claim_outbox_batch(
    conn: Connection,
    *,
    owner: str,
    limit: int,
    lease_seconds: int,
) -> list[OutboxRecord]:
    """Берёт в аренду пачку неопубликованных записей.

    FOR UPDATE SKIP LOCKED: параллельные отправители не ждут друг друга
    и не берут одни и те же записи. Возвращает управление до сетевого
    вызова Kafka — держать транзакцию открытой на время публикации
    нельзя.
    """
```

Правила, заменяющие прежнюю неисполнимую формулировку:

**Репозиторий работает только с Postgres** и обязан уметь участвовать
в транзакции вызывающего — отсюда `conn` первым аргументом.

**Адаптер обращается только к своей внешней зависимости** и не содержит
бизнес-правил. Один адаптер — одна система: адаптер, ходящий и в Kafka,
и в Redis, прячет в себе решение о порядке, то есть бизнес-правило.

**Ни один адаптер не вызывается внутри транзакции базы.** Это проверяемое
требование, а не пожелание: сетевой вызов внутри транзакции держит блокировки
строк ровно столько, сколько длится его таймаут.

## Часть 4. Ошибки

Единый код ошибки проходит через все слои: одно и то же значение попадает
в журнал — полем `error_code` конверта, — в ответ API и в метку метрики
`error_class`. Имена полей разные не по недосмотру: в журнале имя задано
конвертом телеметрии, в метрике — правилом именования меток, и переименовать
одно ради симметрии значило бы сломать либо разбор записей, либо готовые
запросы к метрикам. Значение при этом обязано совпадать буквально: иначе
переход «панель метрики → записи журнала» перестаёт находить те самые
записи, ради которых его и делали.

**Внутренняя причина и внешний ответ — разные вещи.** Прямое отображение
`NOT_A_MEMBER → 403` нарушило бы инвариант И-2 модели авторизации: `403`
подтверждает, что беседа существует, и перебором идентификаторов выясняется,
кто с кем переписывается. Поэтому отображение двухступенчатое.

```
внутренняя причина       внешний ответ            когда
──────────────────       ─────────────            ─────
NOT_A_MEMBER         →   404 RESOURCE_NOT_FOUND   субъект не должен знать
                                                  о существовании ресурса
NOT_A_MEMBER         →   403 FORBIDDEN            субъект заведомо знает
                                                  (своя беседа, из которой вышел)
CONVERSATION_NOT_FOUND → 404 RESOURCE_NOT_FOUND
DUPLICATE_MESSAGE    →   200                      не ошибка: идемпотентный повтор
PAYLOAD_TOO_LARGE    →   413
RATE_LIMITED         →   429
ATTACHMENT_NOT_READY →   409
UPSTREAM_UNAVAILABLE →   503
INTERNAL             →   500
```

Внутренняя причина попадает в журнал и в метку `error_class` — по ней видно,
что произошло на самом деле. Наружу уходит то, что субъекту позволено узнать.
Преобразование делает **один** функция-отображатель, а не каждый обработчик:
разложенное по сорока местам, оно однажды вернёт `403` там, где нельзя.

Формат ответа — один на весь API, `application/problem+json` (RFC 9457), с
`trace_id` в теле. Свой формат ошибки на каждый метод означает, что клиент
пишет разбор ошибок пять раз.

Тело собирает `_problem_body()` в `api/main.py`, и возвращает его оттуда же
`_problem_response()` — одно место на все обработчики. В теле: `type`
(опознаватель вида отказа в своём пространстве имён, а не страница),
`title`, `status`, `code` и `trace_id` из контекста трассы. `code` схема
не требует, но по нему клиент различает виды отказа: без него остаётся
только код состояния, а `403` выдают три разные причины. `trace_id`
в теле дублирует заголовок `X-Trace-Id` намеренно — в поддержку приходят
со снимком экрана, а не с заголовками ответа.

**Текст ошибки не содержит данных.** Ни идентификаторов чужих объектов, ни
содержимого. `«беседа не найдена»` — да; `«беседа 7f3a… принадлежит
пользователю 91b2…»` — нет: это утечка через сообщение об ошибке.

## Часть 5. Транзакции и внешние вызовы

Правило, из-за нарушения которого переписывают весь путь сообщения:

```
внутри транзакции        вне транзакции
─────────────────        ──────────────
SQL                      Kafka
запись в outbox          HTTP к любому сервису
блокировки строк         S3 и объектное хранилище
                         Centrifugo
                         отправка почты и SMS
```

Сетевой вызов внутри транзакции держит блокировки строк ровно столько, сколько
длится таймаут этого вызова. При недоступной Kafka это минуты — и всё это время
беседа заблокирована для всех.

**Транзакция открывается в сервисном слое, не в репозитории и не в обработчике.**
Только сервис знает, какие операции обязаны лечь одним коммитом.

## Часть 6. Фронтенд

**Типы не пишутся руками.** Клиент генерируется из `openapi.yaml` в сборке;
собственный интерфейс `Message`, написанный рядом, расходится с сервером молча
и обнаруживается в проде.

```
packages/contracts/openapi.yaml
        ↓ scripts/generate-web-client.sh — конфигурация apps/web/openapi-generator.yaml,
        ↓ образ генератора закреплён в apps/web/base-image.lock
apps/web/src/api/generated/     ← не редактируется, в .gitignore
```

**Правило названо вместе с механизмом, потому что без механизма оно было
неверным.** `generated/` не игнорировался ни одним `.gitignore` — запись
добавлена вместе с генератором, и до этого строка выше утверждала то, чего
не было. Конфигурация генератора лежит **в одном файле** для хостовой сборки
и для стадии `codegen` образа: один digest генератора без общей конфигурации
даёт двух разных клиентов из одного контракта. Форму сгенерированных типов
проверяют утверждения `apps/web/src/api/contract.test.ts`, и их красный
приходит от `tsc -b`, а не от прогона тестов.

Структура и именование:

```
src/
  api/          сгенерированный клиент и тонкие обёртки
  features/     по возможностям: conversations, messages, auth
  shared/       ui, hooks, lib
```

```
компоненты      PascalCase       ConversationList.tsx
хуки            useXxx           useConversation.ts
поля данных     camelCase        conversationId
файлы модулей   kebab-case       message-list.ts
```

Состояние сообщения на клиенте — конечный автомат с теми же именами, что в
объёме v1: `sending → sent → delivered → read`, плюс `failed` и `retrying`.
Повтор переиспользует тот же `client_message_id` — это то самое место, где
неверное именование стоит дубля у пользователя.

## Часть 7. Тесты

```
tests/unit/          доменные правила, без базы и сети
tests/integration/   сервис против настоящих Postgres, Kafka, Redis
tests/contract/      совместимость схем
tests/e2e/           сквозные сценарии через клиент
```

Имя теста — утверждение, а не название функции:

```
test_повтор_с_тем_же_client_message_id_не_создаёт_дубля     да
test_send_message_2                                          нет
```

Один тест проверяет одно утверждение. Тест с пятью `assert` про разное при
падении не говорит, что именно сломалось.

## Часть 8. Что намеренно не фиксируется

- внутренние функции и приватные методы;
- структуры данных внутри слоя;
- порядок операций там, где он не влияет на наблюдаемое поведение;
- разбиение модулей ниже уровня слоя.

Это решается при реализации и меняется без согласования, потому что не входит
ни в один контракт. Правило простое: **если изменение видно снаружи модуля —
это контракт, и он в этом документе. Если не видно — это реализация.**
