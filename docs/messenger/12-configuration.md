# Конфигурация

> kubernetes-finops-platform · мессенджер, часть 12

Тесты `CFG-001…004` и `ROT-001…004` уже описывают поведение при изменении
настроек, а [часть 6](06-observability.md) — как это изменение попадает на
графики. Чего не было — самой модели: какие бывают классы настроек, где каждый
живёт, кто вправе его менять и что при этом происходит.

Классификация строится не по месту хранения, а по вопросу

```
что стоит изменить это значение?
```

потому что именно ответ на него определяет, можно ли крутить настройку в три
часа ночи при инциденте.

---

## Часть 1. Пять классов

| Класс | Цена изменения | Где живёт | Кто меняет |
| --- | --- | --- | --- |
| **Код** | пересборка образа, новый digest | исходники | разработчик через PR |
| **Сборка** | пересборка образа | `Dockerfile`, зависимости | разработчик через PR |
| **Выкатка** | перезапуск подов | `gitops/**/values.yaml` | PR в gitops |
| **Секрет** | перезапуск или перечитывание | оператор или внешнее хранилище | процедура с аудитом |
| **Флаг** | мгновенно, без перезапуска | хранилище флагов | дежурный, админ |

Лестница снизу вверх — это лестница скорости реакции. Во время инцидента
доступен только нижний класс: пересобрать образ под нагрузкой невозможно, а
выключить «печатает» флагом — секунда.

Отсюда правило распределения: **если значение может понадобиться изменить
во время инцидента, оно обязано быть флагом, а не значением в values**.
И наоборот — то, что меняется раз в полгода, флагом быть не должно: каждый
флаг это ветвление, которое кто-то обязан тестировать в обоих положениях.

### Почему «переменная окружения» не класс

Переменная окружения — способ доставки, а не класс. Одно и то же значение может
приехать в неё из `values.yaml`, из секрета оператора и из хранилища флагов, и
цена изменения в этих трёх случаях разная. Классифицировать по способу
доставки — значит потерять именно ту информацию, ради которой классификация
и делается.

## Часть 2. Где что лежит на самом деле

```
gitops/04-messenger/*/values.yaml      класс «выкатка»
   ├── адреса зависимостей
   ├── размеры пулов, пределы, таймауты
   ├── ресурсы и число реплик
   └── имена секретов — не значения

секреты
   ├── messenger-db-app        создаёт CNPG
   ├── messenger-idp-*         создаёт оператор Keycloak
   ├── messenger-minio-env     создаёт джоб bootstrap
   └── messenger-centrifugo    создаёт джоб bootstrap

флаги возможностей
   └── таблица в Postgres + кеш в Redis app-cache

аварийные выключатели
   └── ОТДЕЛЬНОЕ хранилище, не Postgres и не Redis приложения

образ
   └── ничего из перечисленного
```

**В образе нет ни одной настройки окружения.** Один и тот же digest едет
в локальное окружение, stage и прод — иначе «проверено на stage» не означает
ничего. Это то же требование, что и `DEP-001`, просто с другой стороны.

## Часть 3. Правила

### П-1. У каждого значения ровно один источник

Цепочки вида «переменная окружения перекрывает файл, файл перекрывает
значение по умолчанию, а удалённая настройка перекрывает всё» приводят к
единственному вопросу, на который никто не может ответить быстро: *какое
значение действует прямо сейчас и откуда оно взялось*.

Одно значение — один класс — один источник. Если нужно переопределение,
значит, класс выбран неверно.

### П-2. Инварианты не настраиваются

Нельзя флагом отключить идемпотентность, проверку членства, требование
источника истины при записи или аудит привилегированной операции.

```
настраивается            не настраивается никогда
─────────────            ────────────────────────
пределы частоты          идемпотентность по client_message_id
размеры пулов            свежесть данных при проверке прав
таймауты                 аудит привилегированных операций
«печатает» вкл/выкл      проверка членства
предпросмотр в push      надгробие вместо DELETE
```

Флаг, которым можно нарушить корректность, — не флаг, а дефект с выключателем.
Разница принципиальная: у дефекта есть исправление, у выключателя — только
инструкция «не трогать», которую однажды не прочитают.

### П-3. Неверное значение обязано валить старт

Сервис с недопустимой настройкой **не запускается**, а не стартует
в ослабленном виде. Наполовину запущенный хуже упавшего: он проходит пробы,
принимает трафик и ведёт себя неправильно — то есть отказ становится невидим.

Проверка на старте, до открытия портов: адреса разрешаются, обязательные
значения присутствуют, числа в допустимых границах, секреты прочитаны.

### П-4. Отказ источника настроек не останавливает отправку

То же правило, что для наблюдаемости. Хранилище флагов недоступно — сервис
работает на последнем известном значении, а если его нет — на **безопасном
значении по умолчанию**.

```
флаг недоступен
      ▼
последнее известное значение
      ▼
безопасное значение по умолчанию
```

Безопасное — то, при котором система работает, а не то, при котором включено
больше возможностей. Для «печатает» безопасное значение — выключено:
недоступный источник настроек не должен добавлять нагрузку. Это `CFG-003`.

### П-5. Одинаковое значение на всех подах

Флаг, применившийся на трёх подах из десяти, даёт поведение, которое
невоспроизводимо и необъяснимо: один и тот же запрос ведёт себя по-разному
в зависимости от того, куда попал. Распространение — через событие, а не через
опрос с разным расписанием; расхождение имеет предел по времени и измеряется.
Это `CFG-004`.

## Часть 4. Флаги

### Выключатель не может жить в том, что он спасает

Первая редакция держала оба вида флагов в Postgres с кешем в Redis. Это не
работает ровно тогда, когда нужно:

```
Postgres перегружен
      ▼
надо выключить фоновые задачи (DEG-003)
      ▼
записать выключатель... в перегруженный Postgres
```

Последнее известное значение позволяет **прочитать** существующее состояние
при недоступном источнике, но не **изменить** его. А инцидент — это всегда
изменение.

Поэтому домены отказа разделены:

| | Флаги возможностей | Аварийные выключатели |
| --- | --- | --- |
| Где | Postgres + кеш | отдельное хранилище |
| Зависит от | приложения | **ни от чего в пути сообщения** |
| Кто меняет | продукт | дежурный |
| Проверяется | тестами | учениями |

Отдельное хранилище не обязано быть сложным — годится объектное хранилище,
файл конфигурации или параметр в облачном хранилище настроек. Требование
одно: **оно не должно отказывать вместе с тем, что выключатель призван
спасти**. Это то же рассуждение, что и про наблюдаемость вне критического
пути, только с обратной стороны.

### Два разных вида под одним словом

| | Аварийный выключатель | Управление возможностью |
| --- | --- | --- |
| Зачем | выключить часть системы под нагрузкой | включить возможность части пользователей |
| Кто дёргает | дежурный | продукт |
| Значение по умолчанию | включено, выключается при беде | выключено, включается постепенно |
| Срок жизни | постоянный | до полного включения |
| Проверяется | учениями | обычными тестами |

Смешивать их вредно: у них разный жизненный цикл и разные права на изменение.

### У каждого флага есть срок

Флаг без даты снятия превращается в постоянное ветвление. Два флага — четыре
сочетания, десять — тысяча, и ни одно из них не проверено. Поэтому у флага
управления возможностью есть дата, после которой он либо снят, либо объяснено
почему нет.

Аварийные выключатели бессрочны — но их число ограничено списком, а не
желанием: каждый обязан быть проверен учениями, иначе в нужный момент
выяснится, что он не работает. Это `DEG-001…004`.

### Что можно выключать

Список совпадает с лестницей деградации из объёма v1 и не шире её:

```
«печатает»              выключается первым, потери нет
предпросмотр в push     выключается, уведомление остаётся
обработка вложений      откладывается в очередь
presence                выключается, «был в сети» остаётся
─────────────────────── ниже выключать нечего
отправка и доставка     не выключаются никогда
```

## Часть 5. Секреты

### Кто создаёт

Настоящих учётных данных в git нет ([`docs/secrets-policy.md`](../secrets-policy.md)).
Значения рождаются в кластере:

| Секрет | Локально | Stage и прод |
| --- | --- | --- |
| Пароль базы | оператор CNPG | управляемое хранилище секретов, путь RDS |
| Начальный админ Keycloak | оператор Keycloak | управляемое хранилище |
| Корневые данные объектного хранилища | джоб `messenger-secrets-bootstrap` | **не существует**: доступ по роли, а не по ключу |
| Ключи Centrifugo | тот же джоб | управляемое хранилище |
| Ключ подписи токенов | оператор Keycloak | управляемое хранилище с ротацией |

Третья строка — не мелочь. Локально MinIO требует корневых учётных данных;
в облаке их нет вовсе, потому что доступ к объектному хранилищу выдаётся ролью
пода. Секрет, существующий только в одном окружении, — обычный источник
кода, который «работает локально».

В `values.yaml` лежат **имена** секретов, а не значения. Это не формальность:
имя в git означает, что состав конфигурации виден целиком, а сами значения —
нет. Полные схемы манифестов `SecretStore` и `ExternalSecret` для синхронизации
из AWS Secrets Manager, а также шаблон для локальной разработки
(`apps/messenger/.env.example`) зафиксированы в [`docs/secrets-policy.md`](../secrets-policy.md).


### Ротация

Ротация — не «поменять значение», а последовательность, в которой не должно
быть окна отказа. `ROT-001…004` проверяют четыре случая, и у них разная
трудность:

| Что | Сложность |
| --- | --- |
| Сертификат TLS | простая: cert-manager, перечитывание на лету |
| Учётные данные базы | средняя: нужен период, когда работают оба |
| Ключ подписи ссылок CDN | средняя: выданные ссылки обязаны дожить свой срок |
| **Ключ подписи токенов** | **сложная**: старые токены проверяются старым ключом, новые — новым, и оба ключа должны сосуществовать |

Последний случай — единственный, где ошибка означает выход всех пользователей
разом. Поэтому проверка подписи обязана уметь несколько действующих ключей
с самого начала: добавить это позже — значит один раз всех разлогинить.

## Часть 6. Изменение как событие

Каждое изменение любого класса порождает эксплуатационное событие по схеме
`packages/contracts/events/operational-event.v1.json` и попадает отметкой на
графики.

```
изменение
   ├── класс «выкатка» → PR в gitops → Argo CD → событие config_change
   ├── класс «флаг»    → админ-API   →           событие feature_flag
   └── класс «секрет»  → процедура   →           событие + запись в аудит
```

**Имена изменённых ключей — да, значения — нет.** Иначе в журнал попадут
пароль, строка подключения и подписанная ссылка. За подробностями — ссылка на
коммит.

Изменение секрета попадает ещё и в поток `audit` со своим сроком хранения:
это привилегированная операция, а операция без аудита считается несовершённой
(инвариант И-5 из [модели авторизации](08-authorization.md)). Своего срока
у потока `audit` сегодня нет — хранилище журналов одно и хранит всё семь
дней; чего это стоит и что нужно, чтобы сроки разошлись, разобрано
в [жизненном цикле данных](09-data-lifecycle.md).

## Часть 7. Кто вправе менять

| Класс | Право | Что остаётся следом |
| --- | --- | --- |
| Код и сборка | PR, зелёный конвейер, слияние | коммит, digest, событие выкатки |
| Выкатка | PR в gitops | коммит, событие `config_change` |
| Флаг возможности | продукт через админ-API | событие `feature_flag` |
| Аварийный выключатель | дежурный | событие + запись в аудит |
| Секрет | процедура с подтверждением | событие + аудит, значение нигде |

Прямое изменение в кластере, минуя git, — не запрещено: во время аварии оно
иногда единственный выход. Но оно идёт по порядку, а не по наитию, и порядок
описан в [части 14](14-incidents.md): приостановить сверку для одного
приложения, применить, записать в аудит, привести описанное состояние
в соответствие, возобновить сверку.

Без первого шага правка бессмысленна — Argo CD отменит её, возможно раньше
окончания аварии. Без последнего приостановленная сверка превращается
в окружение, расходящееся с git месяцами, поэтому приостановка имеет срок.

## Что этот документ не решает

- **Конфигурация клиента.** Веб-клиент получает часть настроек от сервера;
  его собственный жизненный цикл и минимальная поддерживаемая версия — тема
  совместимости клиента, отдельный документ.
- **Настройка сторонних систем.** Параметры Keycloak, Centrifugo и операторов
  живут в их собственных values и подчиняются классу «выкатка», но их
  внутренние модели конфигурации здесь не описываются.
- **Значения по умолчанию для прода.** Конкретные числа пределов и таймаутов
  определяются измерением на stage, а не выбором за столом.
