# Оценка: голосовые и видеозвонки

> kubernetes-finops-platform · мессенджер, часть 16

Документ отвечает на один вопрос: **сколько стоит добавить звонки и стоит ли**.
Он не меняет объём. [ADR 0000](../ADR/0000-v1-scope.md) по-прежнему исключает
звонки из v1, а [`IMPLEMENTATION-PLAN.md`](../../IMPLEMENTATION-PLAN.md) о них
молчит. Если решение «делать» будет принято, следующий шаг — отдельный ADR
(см. [часть 9](#часть-9-что-не-решено)), а не правка этого файла.

Как и [модель затрат](10-cost-model.md), всё ниже — **расчёт и оценка, а не
замер**. Трудозатраты — рабочие дни одного инженера до ревью, с разбросом;
деньги — по прейскуранту; качество связи локально не измеряется вовсе.

---

## Резюме

| Вопрос | Ответ |
| --- | --- |
| Что делаем | звонки **один-на-один, аудио и видео**, внутри существующей беседы |
| Архитектура | прямой WebRTC между браузерами, **без SFU**; сервер делает сигнализацию, выдаёт TURN-доступ и пишет итог звонка в ленту |
| Трудозатраты | **≈ 63 дня** с управляемым TURN (диапазон 50–95); +5 дней, если TURN свой |
| Стоимость при 5% звонящих в сутки | **≈ $1 000 в месяц** с управляемым TURN (Cloudflare), ≈ $2 500 со своим coturn, ≈ $8 800 у Twilio — против ≈ $19 250 всего счёта |
| Главная статья | **трафик через TURN**, а не серверы: серверной нагрузки на медиа нет |
| Главные риски | Safari и мобильные браузеры; звонок без Web Push слышит только открытая вкладка; нечем остановить нежелательные звонки без блокировок; доля релея (15%) — допущение |
| Совет | включать звонки **после** Web Push и блокировок, а не вместо них; начинать с управляемого TURN за интерфейсом |

Если читать только это: звонки один-на-один **дешёвые по серверам и дорогие по
разработке клиента**. Почти половина усилий уходит в браузерную часть и в её
проверки, ещё четверть — в метрики, нагрузку и AWS.

## Часть 1. Принятые допущения

Всё ниже согласовано до написания; если что-то из этого поменяется, пересчёту
подлежит указанное в скобках.

| Допущение | Следствие |
| --- | --- |
| Только один-на-один; групповые, демонстрация экрана и запись — позже | SFU не нужен (стоимость, части 2 и 5) |
| Звонить можно **участнику беседы**; блокировок и лимита частоты нет | риск злоупотребления (часть 6, R5) |
| Медиа идёт напрямую, TURN нужен там, где NAT не пускает | деньги уходят в релей |
| Среды: локальный стенд и AWS | локально качество не проверить (R7) |
| Звонок звонит 30 с, один активный звонок на пользователя, звонит во всех вкладках, принять можно в одной | автомат состояний и многовкладочность (часть 2) |

| Собеседник не в сети: звонок не стартует, в ленте «пропущенный звонок»; Web Push появится позже | зависимость от `NTF-001…004` |
| Видео адаптивное, потолок 720p; в расчёте 1 Мбит/с видео + 40 кбит/с аудио на участника | стоимость (часть 5) |
| Нагрузка: 1%, 5% и 15% из 2,5 млн активных в сутки звонят; звонок 5 минут; один звонок на звонящего | стоимость (часть 5) |

| Качество проверяется функционально и метриками из `getStats()`; сетевые условия AWS — рекомендация перед выкаткой | часть 7 |

## Часть 2. Архитектура

### Что где живёт

```
Браузер A ◄══════════ медиа (DTLS-SRTP, напрямую) ══════════► Браузер B
   │   ╲                                                       ╱   │
   │    ╲════► TURN (только если прямой путь невозможен) ◄════╱    │
   │                                                               │
   │ сигнализация                                     сигнализация │
   ▼                                                               ▲
  API ──► Postgres (call, итог)                       Centrifugo `user:{B}`
   │                                                               ▲
   └───────────────────────── publish ─────────────────────────────┘
```

Роль по [восьми ролям части 1](01-architecture.md): звонок не добавляет
девятой. Медиа не касается ни одной нашей машины, кроме TURN, а TURN —
не часть истины, а транспорт.

### Сигнализация идёт через API, а не через клиентскую публикацию

Клиент не публикует в Centrifugo сам: каналы выдаёт сервер, и
[«подделка автора события»](05-test-catalog.md) закрыта именно тем, что у
клиента нет права публикации. Сигнал звонка — такое же событие, поэтому

```
A → POST /calls/{id}/signals → проверка: A участник звонка → publish в user:{B}
```

Из этого следуют три правила, каждое несущее:

- **Сигналы не восстанавливаются.** Обычный канал с историей после обрыва
  отдаёт пропущенное; устаревший `offer` из прошлого соединения опасен.
  Сигнальные события идут в пространство имён **без истории**, и у каждого
  есть `call_id` и монотонный `seq`: клиент отбрасывает всё, что не от текущего
  звонка или старше уже принятого.
- **Кандидаты ICE идут пачками.** Один звонок — до 20–30 кандидатов с каждой
  стороны; по одному запросу на кандидата это сорок лишних обращений в API.
  Клиент собирает их 100–200 мс и отправляет вместе.
- **Размер и частота ограничены.** Предел на сигнал (≈ 16 КБ — SDP с видео
  обычно 5–10 КБ) и на число сигналов в минуту на звонок. Иначе звонок
  превращается в бесплатный канал записи в чужой `user:{id}`.

### Автомат звонка

Живёт на сервере; клиент не решает, жив ли звонок.

```
            ┌─ отклонён ──────────────► ended(declined)
            ├─ 30 с без ответа ───────► ended(missed)
 ringing ───┼─ звонящий отменил ──────► ended(cancelled)
            ├─ у вызываемого занято ──► ended(busy)
            └─ принят
                 ▼
             accepted ── ICE не собрался за 15 с ──► ended(failed)
                 ▼ клиент сообщил «медиа пошло»
              active ── обрыв дольше 15 с ──► ended(failed)
                 ▼ повесили трубку
            ended(completed)
```

- Номер состояния **монотонный**, переходы идемпотентны: повторный `accept`
  или `hangup` ничего не меняет — как повтор отправки в
  [части 2](02-delivery.md).
- `ringing` и зависшие `active` закрывает **подметальщик** по образцу
  `presence-sweeper`: аренда, `FOR UPDATE SKIP LOCKED`. Клиент шлёт
  keepalive раз в 30 с; тишина 90 с — звонок завершён сервером.
- Один активный звонок на пользователя обеспечивает **частичный уникальный
  индекс** в таблице участников `call_participants` по
  `(user_id) WHERE active`, где строка участника на обе стороны гасится при
  завершении звонка, а не проверка в коде: два одновременных звонка друг другу
  разрешаются базой, а не гонкой. «Встречный» звонок (A звонит B, B звонит A
  одновременно) сводится к принятию уже существующего.
- Вызываемый «не в сети» определяется по реестру соединений
  (`realtime_connections`), а не по окну присутствия в 180 с: окно даёт
  «онлайн» ещё три минуты после закрытия вкладки, и звонок звонил бы в пустоту.
  Такой звонок пишется сразу как `ended(unavailable)` — без звонка у
  собеседника.

### Многовкладочность

```
B открыл три вкладки → call.incoming во всех трёх
B нажал «принять» в одной → server: accepted
                         → остальным: call.state accepted_elsewhere → экран гаснет
```

Принятие — условное обновление `ringing → accepted`: побеждает первый запрос.
Устройство для медиа — то, где нажали.

### TURN-доступ

`GET /calls/ice-servers` выдаёт **краткоживущие учётные данные** (≈ 10 минут,
выдаются только участнику активного или создаваемого звонка). Выдача спрятана
за интерфейсом `TurnProvider` — по образцу `Scanner` и `ObjectStore`:

```
TurnProvider ─┬─ Cloudflare (REST API, ключ в секретах)
              └─ coturn    (HMAC от общего секрета, `use-auth-secret`)
```

Так выбор между своим и управляемым — настройка, а не переписывание, и
договорённость «начать с управляемого» ничего не закрывает. Постоянных
учётных данных TURN в клиенте нет: иначе он становится бесплатным прокси
для кого угодно.

### Итог звонка — сообщение в ленте

`ended(...)` пишет **системное сообщение** в беседу в той же транзакции, что и
смена состояния: «Звонок, 4 мин 12 с» или «Пропущенный звонок». Вид
`system` в [модели сообщения](03-v1-scope.md) уже есть, нумерация
`conversation_seq` общая. Поэтому история, непрочитанное и восстановление
после обрыва работают без изменений; незнакомый старому клиенту вид
обязан сохраняться (см. [часть 4 документа 13](13-client-compatibility.md)).

### Клиент

Три слоя, как в `features/realtime`:

| Модуль | Знает | Не знает |
| --- | --- | --- |
| `callMachine.ts` | события звонка и состояние | `RTCPeerConnection`, `window`, React |
| `peerConnection.ts` | WebRTC — **единственный** модуль с ним | состояния интерфейса |
| `useCall.ts`, компоненты | React, `getUserMedia` | протокол сигнализации |

Автомат — чистая функция, как `connectionMachine.ts`: каждый переход
доказывается прогоном **без сети и без камеры**. Это единственный способ
протестировать «15 секунд на переподключение» без живых сетей.

### Телеметрия

Из `getStats()` раз в 5 секунд, через уже существующий конвейер браузерной
телеметрии (G3-008):

```
messenger_call_setup_seconds                 время от «принять» до «медиа пошло»
messenger_call_ended_total{reason}           completed|declined|missed|cancelled|busy|failed|unavailable
messenger_call_connection_type_total{type}   host|srflx|relay   ← доля релея, измеряет допущение
messenger_call_rtt_seconds, _packet_loss_ratio, _jitter_seconds
```

Метки — только перечисления; `call_id` и `user_id` в метки нельзя
(правило из [части 6](06-observability.md)). Доля `relay` — главная метрика
стоимости: она заменит допущение «15%» измерением в первую же неделю.

Флаг `calls_enabled` — в ряд к существующим `voice_enabled` и
`push_enabled` ([часть 12](12-configuration.md)): выключенные звонки не
показывают кнопку и отвечают `404` на маршруты.

## Часть 5. Стоимость

### Что платим

При прямом соединении медиа **не проходит через нас вообще**: ни CPU, ни
трафика. Платим за три вещи:

| Статья | Определяется | Порядок |
| --- | --- | --- |
| Релей TURN | долей звонков через релей × гигабайты на звонок | **главная статья** |
| Сигнализация | ≈ 50 событий на звонок | пренебрежимо |
| Итог в ленте | одно сообщение на звонок | пренебрежимо |

Серверная часть звонка при 5% звонящих — **≈ 36 сигналов в секунду** в
среднем на фоне 833 отправок в секунду по [модели](10-cost-model.md). Стенд
с 76% памяти звонки по серверной части выдержит; плохо ему станет только
от нагрузочной проверки, а она сигнальная.

### Вывод цифр

```
трафик одного звонка   (40 кбит/с аудио + 1 Мбит/с видео) × 2 участника
                       × 300 с = 624 Мбит ≈ 0,078 ГБ (видео); 0,003 ГБ (аудио)
звонков в месяц        звонящих_в_сутки / 2 × 30
через релей            15% звонков; цена — за исходящий от релея трафик
пик                    среднее × 3 (как в модели нагрузки)
```

Допущение «каждый звонящий делает один звонок в сутки» заложено в сценарии;
звонков с video-выключенным аудио в расчёте нет — это нижняя граница
(в таблице отдельной строкой).

### Три сценария

| | **1%** | **5%** | **15%** |
| --- | --- | --- | --- |
| звонящих в сутки | 25 000 | 125 000 | 375 000 |
| звонков в месяц | 375 тыс. | 1,9 млн | 5,6 млн |
| одновременных звонков в пик | 130 | 651 | 1 953 |
| из них через релей, пик | 20 | 98 | 293 |
| полоса релея в пик | 41 Мбит/с | 203 Мбит/с | 609 Мбит/с |
| трафик через релей в месяц | 4,4 ТБ | 21,9 ТБ | 65,8 ТБ |
| **Cloudflare TURN** ($0,05/ГБ, первые 1 000 ГБ бесплатно) | **$169** | **$1 047** | **$3 241** |
| **свой coturn** (исходящий $0,09/ГБ + ≈ $517 постоянно) | **$912** | **$2 491** | **$6 440** |
| **Twilio TURN** ($0,40/ГБ) | $1 755 | $8 775 | $26 325 |
| сигнализация (по $2,10 за млн событий) | $39 | $197 | $591 |
| **добавка к счёту ≈ $19 250 (свой coturn)** | +5% | +14% | +37% |
| только аудио, свой coturn, исходящий | $15 | $76 | $228 |

Цены проверены на страницах Cloudflare Realtime TURN и Twilio Network
Traversal; прейскуранты меняются, и они стареют так же, как всё в
[модели затрат](10-cost-model.md). «Постоянно ≈ $517» — два узла по
≈ $241 (как в модели), балансировщик для UDP ≈ $25, адреса ≈ $10.

### Что из этого следует

- **Свой coturn не дешевле управляемого** ни в одном сценарии: исходящий
  трафик AWS ($0,09) дороже, чем Cloudflare ($0,05), а к нему добавляется
  постоянная часть и эксплуатация. Свой вариант оправдан отказом от внешней
  зависимости, а не деньгами. Против Twilio он выигрывает кратно.
- **Видео — почти вся стоимость.** Аудио-звонок дешевле видео в 26 раз.
  Рычаги: потолок битрейта, опция «аудио по умолчанию», отключение видео на
  плохой сети. Поэтому адаптивное качество — не прихоть, а статья расходов.
- **Утверждение «звонки: порядки больше файлового» верно не для нас.**
  Файлы — 81 ТБ в месяц; релей при 5% — 22 ТБ, то есть четверть. Для
  P2P+TURN модель не инвалидируется, а получает новую строку. Для SFU
  утверждение остаётся в силе.

### Чувствительность

| Что меняется | Эффект при 5% | Почему |
| --- | --- | --- |
| Доля релея 10% → 20% | $0,7 тыс. → $1,4 тыс. (Cloudflare) | линейно по доле |
| Режим «только релей» (приватность, ICE `relay`) | ×6,7 → ≈ $7 тыс. | весь трафик идёт через TURN |
| Битрейт видео 1 → 2 Мбит/с | ×≈ 2 | потолок 720p часто упирается в 1,5–2,5 |
| Длительность звонка 5 → 10 мин | ×2 | линейно |

Строка про «только релей» заслуживает внимания: прямое соединение показывает
участникам IP-адреса друг друга. Если для продукта это недопустимо, звонки
становятся **дороже до ×6,7**, и это решение, которое надо принять до
запуска, а не после (R6).

## Часть 6. Риски

| № | Риск | Вероятность | Цена ошибки | Что делаем |
| --- | --- | --- | --- | --- |
| **R1** | **Safari и мобильные браузеры.** Автовоспроизведение, повторный запрос разрешений, фоновая вкладка засыпает, в Playwright WebKit нет надёжных фейковых устройств | высокая | +10–30 дней, ручное тестирование | решить матрицу браузеров до старта; Safari — отдельная задача и отдельный бюджет |
| **R2** | **Звонок без Web Push слышит только открытая вкладка.** Мобильный браузер убивает фон, вызов не звонит | очевидна | звонок для половины пользователей «не работает» | поставить Web Push (`NTF-001…004`) **до** включения звонков в продукте; до этого — только флагом на тест |
| **R3** | **Сети, где нет UDP** (корпоративные, мобильные). Нужен TURN поверх TCP/TLS на 443 | средняя | связь не устанавливается у 5–10% | TURN-провайдер должен отдавать `turns:` на 443 (у Cloudflare заявлено, не проверено); проверить в `CALL-011` |
| **R4** | **Устаревший сигнал** после переподключения: старый `offer` принимается как новый | средняя | звонок «из прошлого» | пространство имён без истории; `call_id` + `seq`; `CALL-007` |
| **R5** | **Нечем остановить нежелательные звонки.** Блокировок нет, а беседу может начать кто угодно | средняя | злоупотребление, жалобы | не входит в оценку; минимум — лимит попыток звонка на пользователя (+2 дня, как ATT-006); `BLK-001…004` до включения |
| **R6** | **Утечка IP через P2P** | высокая | юридически и репутационно зависит от продукта | решить политику: прямое соединение по умолчанию или только релей (цена — часть 5) |
| **R7** | **Качество не измеряется локально.** Два браузера на одной машине связываются напрямую через `host`-кандидаты; релей, потери и задержки не проявляются | гарантирована | ложная уверенность | метрики `getStats()` и проверка из разных сетей в AWS — условие выкатки, а не рекомендация |
| **R8** | **Доля релея 15% — допущение.** Реальная может быть вдвое больше или меньше | средняя | ±$0,7 тыс. при 5% | `messenger_call_connection_type_total` измеряет её с первого дня |
| **R9** | **Зависимость от внешнего TURN** | средняя | цена или недоступность | `TurnProvider` за интерфейсом; свой coturn — запасной вариант (+5 дней) |
| **R10** | **Окно «онлайн» 180 с** даёт ложное «в сети» | высокая | звонок звонит в пустоту | реестр соединений вместо окна (часть 2) |

Один риск я не включил, но он существует: **согласие и приватность камеры**.
Не технический, а продуктовый вопрос — показывать ли превью до принятия,
по умолчанию включённая или выключенная камера. Решается в интерфейсе
`CALL-006`, но влияет на ожидания людей сильнее любого из пунктов выше.

## Часть 7. Тесты

Правило каталога: возможность не считается сделанной, пока нет пяти вещей
([часть 5](05-test-catalog.md)). Ниже — что именно проверять.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| `CALL-001` | A звонит B, B принимает, оба кладут трубку | состояния проходят по порядку; в ленте «Звонок, N с»; один раз |
| `CALL-002` | B не отвечает 30 с | `ended(missed)`, в ленте «Пропущенный звонок»; звонок у B пропал |
| `CALL-003` | повторный `accept` и повторный `hangup` | второй ничего не меняет |
| `CALL-004` | A звонит B, B звонит A одновременно | один звонок, а не два |
| `CALL-005` | не участник беседы пытается позвонить или прислать сигнал | `403`/`404`, сигнал не опубликован |
| `CALL-006` | подделка: A присылает сигнал от имени звонка, в котором не состоит | отказ, в `user:{B}` ничего не ушло |
| `CALL-007` | **устаревший `offer`** после переподключения вызываемого | отброшен по `seq`, звонок не оживает |
| `CALL-008` | выдача TURN-доступа не участнику или после завершения | отказ; срок учётных данных ≈ 10 мин |
| `CALL-009` | звонок завершён, сообщение уже записано, процесс упал до ответа | при повторе итог не дублируется |
| `CALL-010` | два браузера с фейковыми камерой и микрофоном | медиа идёт: счётчик принятых пакетов растёт, `connected` |
| `CALL-011` | обрыв сети у одной стороны на 10 с и на 20 с | 10 с — звонок продолжается; 20 с — `ended(failed)` |
| `CALL-012` | B открыл три вкладки, принял в одной | в двух остальных вызов погас, `accepted_elsewhere` |
| `CALL-013` | у B уже идёт звонок | `ended(busy)`, у A понятная причина |
| `CALL-014` | у B нет подключённых клиентов | звонок не стартует; «Пропущенный звонок» в ленте |
| `CALL-015` | нагрузка сигнализации: тысячи звонков, пачки кандидатов | задержка отправки сообщений у остальных не растёт |
| `CALL-016` | узел coturn недоступен (при своём TURN) | релейные звонки переустанавливаются за секунды; прямые не затронуты |

`CALL-010` и `-011` исполняются **в Playwright на двух браузерных контекстах**
с флагами Chromium для фейковых устройств; на Firefox — с эквивалентными
настройками. Safari в автоматических проверках **отсутствует** (R1).
`CALL-015` — единственная нагрузка и она сигнальная: медиа локально не
нагружается и не должно (R7).

**Выход:** при `CALL-007` и `CALL-006` зелёных и измеренной доле релея в
первую неделю — звонок можно включать флагом для процента пользователей.
Это сильнее, чем «установилось на стенде».

## Часть 8. Порядок и зависимости

```
Web Push (NTF-001…004)   ─┐
Блокировки (BLK-001…004) ─┼─► включение звонков в продукте
Матрица браузеров        ─┘

CALL-001 → 002 → 003 → 005 ─┐
              └─► 004       ├─► 006 → 007 → 009 → 010
                            └─► 008 (параллельно с 006)
                                              CALL-011 → 012
```

Разработку можно вести **до** Web Push и блокировок, под флагом
`calls_enabled`, и показывать на стенде. Включать для людей — после. Так
принятый порядок «звонки раньше Web Push» сохранён для разработки, а
для продукта действует ограничение R2.

## Часть 9. Что не решено

Решения, без которых нельзя начинать, а не тонкости:

1. **Идти или нет.** Рекомендация — нет, пока не закрыты Web Push и
   блокировки: звонки без них работают у части пользователей и не
   останавливаются у остальных.
2. **ADR 0007** «звонки после v1»: фиксирует отказ от SFU для 1:1, выбор
   `TurnProvider`, политику IP (R6) и закрывает пробел «два медиа-стека против
   LiveKit» из части 1.
3. **Матрица браузеров** (R1).
4. **Прямое соединение или только релей** (R6).

Что не оценивалось: групповые звонки, демонстрация экрана, запись, шум и
эхоподавление сверх встроенных в браузер, мобильные приложения, звонки
в офлайн с push (после Web Push — отдельная задача: уведомление с кнопкой
«принять» в Service Worker, +5–8 дней).

## Что нужно, чтобы эту оценку проверить

Оценка остаётся гипотезой, пока два числа не измерены. Оба можно получить
**до** большой разработки, прототипом на два дня:

- доля релея в реальных сетях — прототип с `getStats()` и тремя тестовыми
  сетями (домашняя, мобильная, корпоративная);
- реальный битрейт 720p на тех же сетях.

Прототип не входит в 63 дня и стоит 2–3 дня. Он снимает две самые дорогие
неопределённости — R8 и порядок стоимости — раньше, чем кто-то начнёт
`CALL-001`.
