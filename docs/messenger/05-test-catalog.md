# Каталог тестов мессенджера

> kubernetes-finops-platform · мессенджер, часть 5

Архитектура, переписанная как исполняемая спецификация. Требования с идентификаторами, сценарии Given/When/Then, негативные пути и хаос — одновременно backlog и критерии приёмки. Покрывает весь объём первой версии, а не только обмен сообщениями: вход и сессии, presence, уведомления, выкатку, миграции, админку, эксплуатацию и жизненный цикл данных.

## Правило проекта

### Возможность не считается сделанной, пока нет пяти вещей

```
требование  +  приёмочный тест  +  тест отказа  +  метрика  +  инвариант
```
Пятый пункт добавлен последним и оказался важнее остальных. Вопрос формулируется так:

```
какой инвариант эта возможность обязана сохранять при
дубликате, повторе, переупорядочивании, устаревших данных
и частичном отказе?
```
Именно эти четыре состояния — дубликат, переупорядочивание, устаревание, частичный успех — остаются последним классом дефектов, которого **не видно ни на одной архитектурной схеме**. Схема показывает стрелки между компонентами; она не показывает, что произойдёт, если стрелка сработала дважды или наполовину.

Обратная проверка работает так же: **требование без теста — найденная дыра; сервис без требования — возможно, лишний сервис**.

| Возможность | Инвариант, который обязана сохранять |
| --- | --- |
| Отправка сообщения | один `client_message_id` — одно сообщение, сколько бы раз ни повторили |
| Нумерация | `conversation_seq` монотонен и без пропусков в пределах беседы |
| Квитанции | номера только растут; клиент не может их занизить или завысить |
| Непрочитанные | повторное событие не увеличивает счётчик |
| Кеш | полная потеря кеша не меняет ни одного ответа по существу |
| Уведомления | одно событие — не более одного уведомления на устройство |
| Вложения | недоступное до проверки остаётся недоступным при любом сбое проверки |
| Права | устаревшие данные не расширяют доступ, только сужают |

Уровни тестирования разделены по назначению, а не по инструменту:

| Уровень | Что проверяет | Где выполняется |
| --- | --- | --- |
| `UNIT` | доменная логика: идемпотентность, нумерация, права, квитанции | в процессе сборки |
| `CONTRACT` | схемы REST, Kafka и WebSocket — совместимость | сборка, блокирует слияние |
| `INT` | сервис против настоящих Postgres, Kafka, Redis, Centrifugo | локально и в конвейере |
| `E2E` | сквозные продуктовые сценарии через веб-клиент | Minikube и stage |
| `CHAOS` | матрица отказов: что видит пользователь и за сколько | только stage |
| `PERF` | ёмкость: соединения, подписки, «печатает», шторм | только stage |
| `DR` | восстановление из копии в чистое окружение | отдельное окружение |

чем это является, а чем нет

Сценарии ниже — это **приёмочная спецификация**, а не модульные тесты. Превращать каждый Given/When/Then в unit-тест не нужно и вредно: они описывают поведение системы, а не единиц кода.

Классический TDD живёт *внутри* реализации и покрывает то, у чего есть собственная логика: выдача `conversation_seq`, идемпотентность по `client_message_id`, монотонность номера прочтения, проверки членства и блокировки, конечный автомат вложения, инвалидация кеша. Каталог стоит над этим слоем и говорит, что система обязана делать снаружи.

## Два решения, принятых для снятия двусмысленности

решение 1 · Web Push входит в первую версию

В объёме стояло «Web Push — либо явно отсутствует», а каталог уже содержал полноценные сценарии. Для release-gate «либо-либо» не годится.

**Входит.** Мессенджер, где о сообщении узнаёшь только при случайно открытой вкладке, мессенджером не является. Весь путь уведомления уже спроектирован — outbox, Kafka, отдельный потребитель; новой работы ровно на транспорт: Service Worker, подписка, ключи. Группа `NTF` — блокирующая.

решение 2 · отзыв сессий бывает двух видов

`AUTH-003` требовал немедленного закрытия WebSocket, а `SEC-005` допускал потерю доступа при следующем обновлении токена. Это противоречие, и оно разрешается разделением:

```
истечение токена      → отложенный отзыв: доступ пропадает при обновлении
«выйти везде», смена
пароля, бан           → немедленный отзыв: событие → разрыв соединений
```
Немедленный отзыв требует отдельного пути: событие об аннулировании сессии доходит до Centrifugo и рвёт соединения этого пользователя. Это надо *спроектировать*, а не подразумевать — поэтому оно записано здесь, а не в списке тестов.

## CONV — жизненный цикл беседы

CONV-001
### Встречное создание беседы

UNIT + INT

```
Given у A и B ещё нет общей беседы
 When A создаёт беседу с B
  And одновременно B создаёт беседу с A
 Then существует ровно одна беседа
  And оба запроса возвращают один и тот же conversation_id
```
Все сценарии обмена начинались с уже существующей беседы — то есть самый первый шаг пользователя не проверялся ничем. А это классическая гонка: два запроса, одна сущность.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| CONV-002 | повторный запрос на создание | возвращается существующая беседа, дубликат не создаётся |
| CONV-003 | беседа с самим собой | либо разрешена явно, либо отклонена — но не «как получится» |
| CONV-004 | создание с заблокировавшим пользователем | отказ (см. BLK-003) |

## LIST — список бесед

LIST-001
### Детерминированный порядок списка

UNIT + INT

```
Given у читателя пять бесед, из них четыре тронуты одной транзакцией
  And у пятой отметка активности выше группы равных
 When читатель запрашивает список
 Then порядок ответа — по паре (updated_at DESC, conversation_id DESC)
  And повторный запрос даёт тот же порядок
```
Список бесед — экран, с которого начинается работа, и он же открывает класс дефектов, которого у истории не было: **ключ сортировки здесь изменяемый и неуникальный**. `conversations.updated_at` двигает единственная запись в системе — `allocate_sequence` при отправке сообщения, — но `now()` в Postgres есть время *транзакции*, а не момента: беседы, созданные или изменённые одной транзакцией, получают одинаковую отметку до микросекунды. В проверке это не редкое совпадение, а норма — четыре беседы из пяти делят одну отметку. При строгом сравнении по одному времени такая группа **теряется** на стыке страниц, при нестрогом — **дублируется**.

Пары компонентов достаточно ровно потому, что второй компонент уникален: тот же приём, которым стык закрыт у истории, где `conversation_seq` уникален сам по себе.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| LIST-002 | статический обход страницами по 2 | каждая беседа ровно один раз — ни дублей, ни пропусков на стыке группы равных; продолжение отдаётся парой целиком и отсутствует ровно на последней странице |
| LIST-003 | беседа без единого сообщения; беседа с надгробием | беседа без сообщений в списке есть, а последнего у неё нет; последнее — самое новое по `conversation_seq`, и надгробие последним остаётся надгробием |

**Чего здесь нет — и это решение.** Проверки «во время пагинации у беседы изменилась активность» не будет. Обычный keyset по изменяемому ключу снимка списка не даёт: беседа может перепрыгнуть через курсор между страницами. Это известное свойство протокола, а не дефект реализации, и закрывается оно не тестом, а отдельным контрактным решением — замороженной границей вроде `sync_to_seq` у истории. Поэтому `LIST-002` сформулирован как **статический** обход: данные между страницами не меняются, и утверждение — про стык, а не про устойчивость списка во времени.

**Курсор задаётся только парой, или его нет вовсе.** Половина пары — «только `before_activity_at`» или «только `before_conversation_id`» — отвергается `400 invalid_cursor` до обращения к базе, а не обслуживается «по более слабой границе». Причина в данных, а не в форме: предикат «строго старше отметки» на группе бесед с равным `updated_at` вычитает её целиком, то есть отдаёт неполный список. Пустая страница на месте отказа была бы хуже ошибки — она неотличима от конца списка, и клиент на ней останавливается, о потере не узнав. Поэтому `ActivityCursor` не оставляет места для третьего состояния: оба компонента обязательны, и собрать половину нельзя даже в обход HTTP-границы.

Соблазн «оставить одиночную отметку законной, раз она объявлена контрактом» отвергнут сознательно. Объявленный контракт закреплял не поведение существующего клиента — клиента нет, веб-клиент это `G3-005`, — а известную потерю данных. Настоящая проверка этой границы — модульная (`test_одиночная_отметка_даёт_400` и `test_половину_курсора_нельзя_собрать_типом`); в кластере её проверять нечем, до запроса дело не доходит.

**`unread_count` отдаётся, и это решение `G3-003`.** Здесь стояло обратное — «не отдаётся: продюсера нет», — и перестало быть верным, когда появился потребитель. Число берётся из проекции, а её отсутствие ответа не меняет: строку, которой нет, восстанавливают из источника истины в момент запроса, и дорогая половина (`COUNT` по беседе) достаётся только потерянным строкам. Это же закрывает случай, до которого проекция не доехала никогда: беседа, чьи события ушли из Kafka по сроку хранения, получит число от первого же списка, в который попала. Поэтому `None` в ответе значит не «проекция потеряна», а «источник истины не даёт числа этому читателю» — он не в составе беседы; подставить `0` нельзя, «всё прочитано» и «спросить не у кого» — разные ответы (`LIST-003`).

Считать `last_seq − last_read_seq` по-прежнему нельзя, но довод сузился: разность считает собственные сообщения и складывает это через всю историю. Надгробия же считаются **намеренно** — непрочитанное это чужие позиции `conversation_seq` выше `last_read_seq`, а не сообщения с доступным содержимым. А настоящий `COUNT(*)` на каждый список есть ровно тот read amplification, ради устранения которого проекция и заведена.

## CTR — контракты

Уровень был объявлен обязательным и блокирующим слияние, но в матрице отсутствовал — то есть формально не проверялся.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| CTR-001 | изменение OpenAPI | обратная совместимость; удаление поля или сужение типа ломает сборку |
| CTR-002 | изменение схемы события Kafka | старый потребитель читает новое сообщение; проверка в реестре схем |
| CTR-003 | изменение события WebSocket | старый клиент не падает на незнакомом поле |
| CTR-004 | сгенерированный клиент TypeScript | соответствует OpenAPI; расхождение ловится в сборке, а не в браузере |

**Что именно сравнивает `CTR-001`, — часть контракта самой проверки.** Зелёный CTR ничего не говорит о том, чего проверка не видит, поэтому список того, что она видит, назван явно: поля и их типы внутри `components.schemas`, обязательность у схем, присутствующих в обеих ревизиях, удаление маршрута, и отдельно — то, чего в схемах не видно:

* **параметры запроса** — удаление, появление `required: true` и сужение схемы самого параметра: тип, формат, границы (`minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems` и исключающие их варианты), перечисление. Появление ограничения там, где его не было, — сужение, а не «нечего сравнивать»: схема без `type` принимает любое значение, а с `type: string` — только строку, и запрос, вчера законный, сегодня получает `400`. Это верно для каждого из перечисленных ключей, включая тип. Расширение разрывом не считается;
* **ссылка на схему ответа** — по ключу «метод, путь, статус, тип содержимого». Подмена `$ref` на другую существующую компоненту иначе не видна вовсе: обе компоненты на месте, поля в них не менялись, а клиент получает другой тип. Ответ, объявленный ссылкой на `components.responses`, разыменовывается — иначе он не участвовал бы в сравнении вовсе, а так объявлены все двадцать два ответа-ошибки контракта. Сравнивается схема **тела**, а не имя компоненты: `Unauthorized` и `NotFound` отличаются статусом и описанием, но тело у обоих `Problem`, и подмена одной на другую сгенерированного клиента не меняет.

Класс параметров добавлен по итогам ревью `G3-001`. Разрыв в них **тише всех прочих**: параметр не поле схемы, `flatten_schema` его не видит, и удаление `before_conversation_id` из `GET /conversations` не тронуло бы ни одной строки, которую проверка умеет сравнивать, — то есть протокол пагинации стал бы другим при зелёной сборке. Тогда же ответ `GET /conversations` вынесен в компоненту `ConversationListPage`: у inline-схемы нет имени, и полей её ответа для сравнения не существует.

Новый inline-ответ роняет проверку структуры; пять ответов, объявленных inline раньше, перечислены в `INLINE_RESPONSE_SCHEMAS` — список закрыт, как `GRANDFATHERED` в проверке миграций, и поля этих пяти по-прежнему не сравниваются. Это известная дыра, а не гарантия. Записи списка названы **ответами**, а не операциями: «метод + путь» выдавало разрешение операции, и второй inline-ответ — с другим статусом — добавлялся рядом с разрешённым, не сдвинув множество найденного ни на элемент.

Чего проверка не умеет и после правки: заметить, что **сужена семантика** уже существующего параметра; увидеть тип элемента, заданный ссылкой (`items: { $ref: … }` сравнивается как «массив»); заметить изменение ключа схемы параметра, не названного в `COMPARED_KEYS` (`pattern`, `multipleOf`, `const`). Одиночный `before_activity_at` отвергнут `400` — параметр на месте, схема его не изменилась, и в allowlist такой разрыв не записывается не потому, что он не разрыв, а потому что записывать его нечем. Такие изменения фиксируются прозой — в контракте, плане и каталоге.

**Проверка проверяется тоже.** `packages/contracts/test_validate.py` закрепляет тринадцать вещей, которые `CTR-001` обязан видеть (удаление параметра и удаление параметра, объявленного ссылкой, параметр, ставший обязательным, сужение схемы параметра и сужение схемы, объявленной ссылкой, появление ограничения типа у параметра без объявленного типа, каждый ключ, названный в `COMPARED_KEYS`, подмена ссылки ответа, сравнение ответа, объявленного компонентой, ответ, ставший inline, второй inline-ответ в разрешённой операции, inline-ответ как таковой и содержимое закрытого списка), и семь, которые видеть не обязан (добавление параметра, снятие обязательности, расширение схемы параметра, разные места одного имени, вынос inline-ответа в компоненту, подмена компоненты ответа с тем же телом, новый статус ответа) — второй список не менее важен: проверка, находящая всё, запретила бы любое изменение контракта. Смысл ровно тот же, что и у всей этой правки: удали детектор из `validate.py` — и прогон обязан покраснеть, а не остаться зелёным, как раньше. Запускается из `make contracts` и из джоба `CTR-001..003`, обычным `python3`: заводить проверке контрактов вторую систему тестов ради нескольких функций значило бы платить установкой пакетов на каждой правке.

**`CTR-004` доказан тем, что расхождение краснеет в сборке, а не в браузере** — и доказан в трёх местах, потому что одного мало.

Первое: клиент вообще производится из контракта, а не живёт рядом с ним. Генерация идёт закреплённым по digest образом, корень репозитория берётся у git (`openapi.yaml` лежит выше приложения, и отсчёт `..` не нашёл бы его), и **конфигурация генератора — один файл** на обе сборки, хостовую и внутри образа: один digest без одного конфигурационного файла даёт двух разных клиентов из одного контракта. Проверяется это не совпадением digest'а, а `diff`-ом двух собранных деревьев; изменение **только** `openapi-generator.yaml` обязано сделать `diff` непустым, иначе конфигурация объявлена, но ни на что не влияет.

Второе: рантайм не может обратиться к полю, которого в контракте нет, и это проверяет **не** прогон тестов. Сгенерированное дерево компилируется отдельным проектом (`tsc -b tsconfig.api.json`), приложением подключённым по project reference, и дефект типа внутри сгенерированной модели роняет именно этот проект. Иначе отдельный проект превратился бы в способ спрятать сгенерированный код от TypeScript, а форма типов — в непроверяемую.

**Форма сгенерированных типов — замер, а не предположение, и утверждения на неё постоянны.** Шесть полей объявлены compile-time утверждениями: `Message.created_at` — `string` (при снятом `typeMappings` умолчание отдаёт `Date`, и адаптер, собирающий display-строку из строки, получил бы объект); `Me.email` — единственный `nullable` из 3.0 посреди документа 3.1, и аннотацию генератор **не применил**, `null` сворачивается в `undefined` в самом конвертере, — принят замер, а не ожидание; `UserSummary.last_seen_at` — `undefined` и `null` **разные**; `Conversation.last_message` — `Message | undefined`; `Conversation.unread_count` — `number | undefined` без `null`, иначе «неизвестно» получило бы второе представление; `next_before_*` — `string | null` и **не** необязательное, иначе клиент проверял бы наличие ключа там, где протокол обещает значение. Утверждения проверяют не только наш OpenAPI, но и поведение закреплённой версии генератора на OAS 3.1: поднятие `GENERATOR_DIGEST`, меняющее любую из шести форм, обязано покраснеть.

Красный у этого уровня приходит **от `tsc -b`, а не от `vitest run`** — это сказано затем, чтобы «красного не было» не смешалось с «искали не там».

Третье: обязательный набор операций (`exchangeAuthorizationCode`, `refreshAccessToken`, `whoAmI`, `listConversations`) проверяется как набор, а не как закрытый список, — шестнадцатая совместимая операция в контракте фронт ронять не должна. И базовый путь проверяется **у обёртки**, а не у сгенерированной константы: браузер обязан звать собственный origin относительным `/api/v1`, а абсолютный `servers` — достояние публичного адреса.

## TX — атомарность записи

Проверялся счастливый путь и падение relay *после* транзакции. Но сама транзакция — и есть то, на чём держится вся схема outbox, а её отказы не проверялись.

| ID | Точка отказа | Ожидание |
| --- | --- | --- |
| TX-001 | сообщение записано, запись outbox не удалась | откат целиком — **ни сообщения, ни события** |
| TX-002 | оба INSERT прошли, коммит не удался | нет ни того, ни другого; клиент получает ошибку и повторяет |
| TX-003 | коммит прошёл, ответ потерян по сети | повтор с тем же `client_message_id` возвращает **ту же запись**, а не создаёт вторую |

Три строки, которые доказывают транзакционный outbox. Без них он остаётся схемой на картинке: сообщение без события молча не доставится, событие без сообщения доставит несуществующее.

## CONS — идемпотентность каждого потребителя

`MSG-003` доказывает, что пользователь не увидит дубль. Но повтор из Kafka вызывает и другие побочные эффекты, у каждого потребителя свои — и каждый обязан быть идемпотентным **отдельно**.

| ID | Потребитель получил событие дважды | Ожидание |
| --- | --- | --- |
| CONS-001 | realtime | одно видимое сообщение |
| CONS-002 | уведомления | **одно** Web Push, а не два |
| CONS-003 | непрочитанные | счётчик `+1`, а не `+2` |
| CONS-004 | инвалидация кеша | повтор безвреден |
| CONS-005 | поиск и аналитика **— вне v1** | запись не дублируется (потребителей нет в первой версии; тест появляется вместе с ними) |

Это прямое следствие сознательно выбранного at-least-once: раз транспорт может повторить, каждый получатель обязан это пережить. Один неидемпотентный потребитель превращает архитектурное решение в дефект.

## UNR — непрочитанные

UNR-001
### Счётчик переживает повтор

UNIT + INT

```
Given у B непрочитанных 3
 When приходит новое сообщение
 Then становится 4
 When B читает до seq N
 Then счётчик пересчитывается от номера, а не уменьшается на единицу
 When событие message.created приходит повторно
 Then счётчик не увеличивается второй раз
```
Потребитель `consumer-unread` существовал в архитектуре, но требования к нему не было вовсе. Для мессенджера счётчик непрочитанных — базовая вещь, и он же первым ломается от дубликатов.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| UNR-002 | чтение с одного устройства из двух | счётчик общий для пользователя, а не для устройства |
| UNR-003 | собственное отправленное сообщение | непрочитанным **не считается** |

**Чем это доказано.** Предикат непрочитанного живёт в двух экземплярах — на Python и на SQL, — поэтому тождество путей не постулируется, а проверяется: сверка `reconciliation` в `unread_check.py` доводит проекцию **только событиями**, затем пересобирает её из источника истины до того же номера и сравнивает числа поимённо по каждому участнику. Оракул там написан руками: считать ожидание вызовом боевой функции значило бы сделать проверку зелёной при любой ошибке, общей для обоих путей.

Повтор доказывается дважды. Модульно — `test_повтор_не_меняет_ничего`: номер, равный чекпойнту, уже применён, потому что чекпойнт и есть наибольший применённый. Живьём — `replay_is_idempotent`: строке outbox возвращается `published_at`, и настоящий отправитель перепубликовывает событие заново, то есть повтор приходит из Kafka, а не из подставленного вызова.

Сверх требований проверяются две вещи, без которых проекция не имеет права на существование. Удаление её строки восстанавливается из источника истины (`projection_deleted_*`), а удаление строки чекпойнта — тоже: беседа, чьи события ушли из Kafka по сроку хранения, чинится первым же списком, в который попала, и никакого события для этого не нужно.

Лаг потребителя остаётся **долгом**, а не забытой строкой: метрика `unread_consumer_lag` не реализована, потому что `adapters/kafka.py` не отдаёт `consumer.position()` и `highwater()`. Наблюдаются длительность обработки (`messenger_consumer_processing_duration_seconds{consumer="unread"}`) и лог-события `unread_cycle` и `unread_event`.

## HIST — история и пагинация

MSG-005
### Обнаружение пропуска, а не только сортировка

E2E

```
Given последний известный клиенту seq = 100
 When клиент получает seq = 102
 Then клиент обнаруживает пропуск 101
  And не считает своё состояние полным
  And догружает сообщения после seq 100
  And в итоге содержит 101 и 102 ровно по одному разу
```
Сортировка по номеру помогает, только когда всё пришло. Если 101 задержался или потерялся, сортировать нечего — и клиент тихо показывает неполную переписку, не зная об этом. Разница между «переупорядочено» и «потеряно» — именно здесь.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| HIST-001 | граница двух страниц | ни дублей, ни пропусков на стыке |
| HIST-002 | во время листания приходят новые сообщения | уже загруженные страницы **не сдвигаются** |
| HIST-003 | удалённое сообщение внутри страницы | надгробие не ломает нумерацию и размер страницы |
| HIST-004 | `before_seq` ровно на границе | включительно или исключительно — но одинаково всегда |

## DEG — деградация под нагрузкой

Хаос проверяет «компонент умер». Здесь другое состояние: **всё живо, но перегружено** — и система обязана жертвовать в заранее назначенном порядке.

| ID | Под давлением | Ожидание |
| --- | --- | --- |
| DEG-001 | Centrifugo или Redis у порога | «печатает» отключается, **сообщения продолжают идти** |
| DEG-002 | растёт отставание Kafka | притормаживаются уведомления, обработка вложений и уборка; realtime и путь сообщения не страдают. Прежняя формулировка называла аналитику и поиск, которых в v1 нет |
| DEG-003 | Postgres у предела | фоновые задачи придушены, **запись сообщений в приоритете** |
| DEG-004 | давление снято | всё возвращается само, без вмешательства |

Проверяется не поведение системы, а готовность людей к её отказу. Подробности —
[часть 14](14-incidents.md).

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| INC-001 | **обход всех будящих оповещений** | у каждого есть ссылка, и ссылка ведёт к существующему тексту. Оповещение с битой ссылкой хуже отсутствующего: будит и ничего не подсказывает |
| INC-002 | аварийный выключатель дёргают на учении | нагрузка действительно снимается; выключатель, который никогда не дёргали, не работает |

| INC-004 | оповещение заглушено | тишина имеет срок и сама заканчивается; бессрочная — это удаление проверки, сделанное незаметно |
| INC-005 | руководство выполняет тот, кто его не писал | выполнимо без вопросов автору — иначе это заметки, работающие пока автор доступен |

Последняя строка проверяет то, о чём забывают: деградация должна быть обратимой автоматически, иначе она превращается в постоянно выключенные функции, о которых никто не помнит.

## AUTHZ — модель авторизации

Пять правил из [модели авторизации](08-authorization.md), у которых не было
приёмочного теста. `AUTHZ-003…005` — P0: их провал уязвимость, а не дефект.
`AUTHZ-001` и `AUTHZ-002` касаются выхода из беседы, недостижимого в v1 при
беседах один-на-один, и релиз не блокируют — они условие включения групп.

| ID | Попытка | Ожидание |
| --- | --- | --- |
| AUTHZ-001 ⟨вне v1⟩ | вышедший из беседы читает историю | видит сообщения до `left_at`, не видит появившиеся после |
| AUTHZ-002 ⟨вне v1⟩ | исключённого удалили, он остаётся подключён | подписка разорвана немедленно, новые сообщения не приходят |
| AUTHZ-003 | **членство изменено в базе, кеш не сброшен** | запись отклонена: устаревшее состояние не расширяет права |
| AUTHZ-004 | запрос несуществующей и чужой беседы | ответы неотличимы — иначе перебором выясняется, кто с кем переписывается |
| AUTHZ-005 ⟨вне v1⟩ | привилегированная операция админа | запись в поток `audit`; операция без аудита считается несовершённой. Ролей в v1 нет — проверять нечего, и это единственная причина, по которой проверка не написана |

`AUTHZ-003` — главный из пяти: он проверяет центральный инвариант модели, и
проверяется единственным способом — изменить членство в базе, не трогая кеш.

## WEBSEC — безопасность браузера

PERF-010
### Догон после простоя шины

PERF + CHAOS

```
Given Kafka недоступна и накопилось отставание
 When Kafka возвращается
  And новый трафик продолжает поступать
 Then накопленное разбирается быстрее, чем поступает новое
  And Postgres, API и realtime не перегружаются догоном
  And задержка обычных сообщений возвращается к норме за измеренное время
```
Самое опасное начинается не во время отказа, а после него: накопленное догоняет одновременно с живым трафиком. `HA-006` проверяет, что отказ пережит; этот тест — что *восстановление* не добивает систему.

`PERF-011` проверяет конкретное проектное решение — частичный индекс по необработанным строкам и партиционирование outbox. Ждать шесть часов не нужно: достаточно синтетически создать десятки миллионов строк и посмотреть, как ведёт себя выборка.

условие достоверности

Все профили идут **через боевой балансировщик**, а генератор стоит на отдельном узле. Иначе измеряется система без компонента, который первым упрётся в предел, и конкуренция за CPU вместо ёмкости.

## PRS — присутствие

PRS-001
### Присутствие при нескольких устройствах

INT + E2E

```
Given B подключён с устройств B1 и B2
 When B1 отключается
 Then B остаётся в сети
 When B2 отключается
 Then B становится офлайн
  And last_seen_at обновляется в Postgres
```
Важная гонка: присутствие нельзя считать по одному соединению. Статус пользователя — агрегат, и правило агрегации должно быть проверено, а не подразумеваться.

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| PRS-002 | обрыв сети без корректного закрытия | статус меняется по таймауту, не зависает «в сети» |
| PRS-003 | «был в сети» после перезапуска Centrifugo | значение из Postgres переживает потерю эфемерного состояния |

**Чем это доказано.** Статус — не событие, а предикат о времени: у Centrifugo
нет прокси на отключение (проксируются `connect`, `refresh`, `subscribe`,
`publish`, `sub_refresh`, `rpc`), поэтому о разрыве сервер не узнаёт никогда
и единственная authority офлайна — окно. Человек в сети, пока хоть одно его
соединение продлевалось внутри окна 180 с (каденция продления — 120 с), и это
проверяется `presence_check.py` на живой системе: два входа владельца и один
вход собеседника открывают настоящие WebSocket, после чего агрегат
спрашивается у боевой функции `count_online_users` **разностью** — до сокетов
и после. Три соединения двух человек дают прирост 2, а не 3 (`PRS-001`);
состаривание одного из двух соединений владельца прироста не меняет, а
состаривание второго уводит его офлайн — и это единственный способ, каким
офлайн наступает (`PRS-002`). Обрыв сокета без кадра закрытия
(`transport.abort()`) не меняет **ничего**: ни статуса, ни отметки — ровно
потому, что узнавать о нём серверу нечем.

Отметка «был в сети» проверяется отдельно от статуса и не выводится из него.
Она пишется при подтверждении — при подключении и при каждом продлении —
в той же транзакции, что и `refreshed_at` соединения, поэтому
`users.last_seen_at` **равна** наибольшему подтверждённому продлению:
тождество проверяется, пока ни одна строка ещё не снята. Вычислять её как
«момент, когда уборщик заметил уход» нельзя — уборщик отстаёт на свой период,
а при мёртвом уборщике не наступает вовсе; поэтому проверка утверждает и
обратное: тот же такт уборки (`services/presence.sweep`), что крутит воркер,
снимает протухшую строку владельца, оставляет живую и **не двигает отметку**.
Пропажа реестра соединений целиком — то, что делает перезапуск Centrifugo, —
отметку не трогает (`PRS-003`); настоящий `rollout restart` с проверкой
значения до и после делает приёмка живой среды, у пода проверок нет ни
`kubectl`, ни прав в кластере.

Наружу из всего этого отдаётся ровно одно поле — `UserSummary.last_seen_at`
в ответе списка бесед; «онлайн» остаётся серверным агрегатом и HTTP-пути
не имеет. «Ни разу не был в сети» — отсутствие ключа, а не `null` и не эпоха:
в проверке это отдельный человек, который в realtime не заходил никогда.

Метрики присутствия — `messenger_presence_online_users` и
`messenger_presence_online_share` — снимаются одним тактом уборщика, поэтому
доля не бывает собрана из двух разных моментов. Смерть уборщика по ним не
видна и видна быть не может: они считаются по времени и при мёртвом уборщике
остаются верными, а признак живого процесса даёт `up` цели скрейпа.

Realtime-событие смены присутствия собеседникам в этот гейт не входит: его
транспорт — `G3-007`, там же решаются «кому слать», дедупликация и приватность.

```

## DEP и MIG — выкатка и миграции

DEP-001
### Собрано один раз, продвинуто без пересборки

CONTRACT

```
Given коммит C прошёл конвейер
  And stage использует образ с digest D
 When версия продвигается в прод
 Then прод использует тот же digest D
  And новая сборка образа не выполняется
```
Главное решение второй части, которое до сих пор не проверялось ничем. Нарушение обнаруживается только в проде и выглядит как «на stage работало».

**Чем это читается на живом стенде, а не заявляется.** Артефакт берётся **четырьмя чтениями**, и четвёртое — не одно равенство: у мультиплатформенного образа `W` — это OCI-**индекс**, ссылающийся на платформенные манифесты, и у индекса с манифестом дигесты **разные**. Требовать их равенства значило бы требовать, чтобы рантайм отчитался не тем объектом, который запустил; но и обратное — требовать одной лишь принадлежности — неверно. Поэтому утверждение формулируется как **дизъюнкция**:

```
values.services.<н>.image.digest        ==  sha256:W            ← что продвинули
pod.spec.containers[*].image            ==  <repo>@sha256:W     ← что запросил под
imagetools inspect sha256:W             →   amd64 и arm64 в составе индекса
pod … status.containerStatuses[*].imageID  ЛИБО == W, ЛИБО ∈ дети W:
  imagetools inspect --raw <repo>@sha256:W | jq -r '.manifests[].digest'
отдельно:  архитектура узла              ∈  .manifests[].platform индекса W
```

Третье чтение — то, чем «две архитектуры» перестают быть намерением: состав индекса читается в реестре после публикации, а не проверяется по `platforms:` в файле workflow. Четвёртое — **развилка с двумя верными исходами**: у рантайма спрошен дигест, и он законно равен **либо** самому индексу, **либо** одному из его детей — containerd вправе отчитаться и тем, и другим, это два наблюдения одного и того же, а не сильное и слабое. Обе крайности неверны симметрично: требование равенства отвергло бы платформенный манифест, требование одной принадлежности — законный ответ самим индексом, и на живом стенде `G3-005` случился именно он (`imageID == W`). Хуже обеих крайностей то, что поиск `W` внутри `.manifests[]` — детектор, **молчащий на верном состоянии**: печатает пустой список, и это читается как «прошло». Отдельно от четырёх чтений проверяется **архитектура запущенного узла**: она обязана присутствовать среди `.manifests[].platform` индекса — только этим «две архитектуры» становятся исполненными, а не заявленными.

**Чего эти чтения не доказывают, и это сказано, а не умолчано.** Равенство `imageID` не показывает, пересоздавался ли под: под мог быть создан заново с тем же образом. «Pod template работающих нагрузок не изменился» доказывается **до слияния** — сравнением вывода общего шаблона чарта из HEAD и из неподвижного базового SHA PR для пяти python-нагрузок целиком (Deployment, Service и оба вида скрейпа). Здесь же подтверждается только то, что в кластер поехал прежний **артефакт**. База сравнения неподвижна намеренно: `origin/main` движется, и сравнение с ним краснело бы от чужого слияния и зеленело от своего, а на копии с `fetch-depth: 1` его могло бы просто не найтись — молчаливый зелёный на отсутствующей базе опаснее падения, потому что выглядит как доказанная неизменность.

| ID | Сценарий | Ожидание |

Точечно вычистить пользователя из уже созданной копии нельзя, и это записано, а не умолчано |
| DATA-002 | выгрузка данных | содержит беседы, сообщения и вложения пользователя |

| DATA-005 | **восстановление из резервной копии** | журнал стираний применяется повторно **до** подачи трафика; стёртое не воскресает. Нарушение происходит в момент аварии, когда проверять его никто не будет |

| DATA-007 | выгрузка не содержит чужого | сообщения собеседника в выгрузку не входят: это его данные |

**Сходимость счётчика в `DATA-004` — проверяемое свойство, а не пожелание.** Счётчик непрочитанного считает чужие **позиции** `conversation_seq` выше `last_read_seq`, а не сообщения с доступным содержимым, поэтому удалённая позиция остаётся непрочитанной: читатель её не наблюдал и при чтении увидит на её месте надгробие. Это не послабление, а условие сходимости. Пути удаления сообщения в v1 нет вовсе — ни маршрута, ни сервиса, ни события в потоке, — поэтому вычитание надгробий сделало бы пересборку из источника истины строго меньше приращения: расходились бы они не иногда, а всегда, и чинить это было бы негде. Тождество обоих путей и проверяет сверка `reconciliation` в `unread_check.py`. Если продукт потребует, чтобы удаление непрочитанного **немедленно** уменьшало badge, это будет новое решение и новая работа: пересчёт под замком беседы вешается на операцию удаления, а `deleted_at IS NULL` появляется в единственном месте — в `_unread_predicate`.

## Раскладка тестов и порядок написания

```
tests/
  unit/         идемпотентность, нумерация, права, квитанции, блокировка
  contracts/    openapi, kafka, websocket
  integration/  postgres, kafka, redis, centrifugo, object_store

  chaos/        kill_api, kill_centrifugo, redis_failover, kafka_failure,

  dr/           restore_from_backup

Порядок написания повторяет этапы плана, а не структуру каталогов:

- **Сначала MSG-001 и MSG-003.** Они проверяют путь записи и модель доставки — то, на чём стоит всё остальное.

- **HA и PERF только на stage**, после того как продуктовые сценарии проходят локально.
- **DR-001 репетируется до прода**, а не после первого инцидента.
