# Первая рабочая версия

> kubernetes-finops-platform · мессенджер, часть 3

Хватит добавлять распределённые системы. Здесь: модель предметной области, жизненный цикл сообщения, что входит в первую версию и что откладывается, эксплуатационные пробелы — и определение готовности из семнадцати сквозных шагов.

## Смена рамки

Первые две части отвечали «как это устроено» и «как это доставляется». Обе описывают систему, но ни одна не описывает **продукт**: есть событие `message.created`, но нет жизненного цикла сущностей; есть доставка, но нет состояний, которые видит пользователь; есть модерация как потребитель Kafka, но нет пути, по которому жалоба доходит до человека.

Дальше добавлять технологии вредно. Полезно — пройти пользовательские сценарии от регистрации до эксплуатации и назвать то, чего в них не хватает.

## Модель предметной области

```
User                Device / Session
Conversation        ConversationMember
Message             Attachment
ReadState           Block            Report
```
Даже если правка, ответ и удаление не входят в первую версию, схема базы обязана позволять их добавить без перелома:

```
message_id            client_message_id   ← идемпотентность
conversation_id       conversation_seq    ← порядок
sender_id
type                  text | image | file | voice | system
created_at            edited_at | deleted_at
reply_to_message_id   payload
```
Удаление — **надгробие, а не физический `DELETE`**: запись остаётся, `deleted_at` проставлен, содержимое стёрто. Иначе ломаются нумерация, ответы на удалённое, состояние прочтения и восстановление при реконнекте.

## Состояния сообщения

Пользователь видит не «доставку», а четыре состояния — и у каждого должно быть *техническое* определение, иначе интерфейс будет врать.

| Состояние | Что это значит технически | Где живёт |
| --- | --- | --- |
| `sending` | запрос отправлен, ответа нет | только клиент |
| `sent` | транзакция в Postgres завершена | ответ API |
| `delivered` | устройство получателя приняло | квитанция через Kafka |
| `read` | `last_read_seq ≥ message.seq` | Postgres |
| `failed` / `retrying` | таймаут или ошибка; повтор с тем же `client_message_id` | клиент |

Отсюда — **оптимистичный интерфейс**: сообщение появляется в ленте сразу со статусом `sending`, после ответа сервера временная запись заменяется настоящей с её `message_id` и `seq`. Повтор после сбоя переиспользует тот же `client_message_id`, поэтому дубля не возникает — это прямое следствие идемпотентности из первой части.

## Три механизма, которые выглядят как один

В интерфейсе рядом стоят три подписи, и за ними три совершенно разные системы:

| Что видит пользователь | Механизм | Где хранится | Можно потерять |
| --- | --- | --- | --- |
| «печатает…» | эфемерная публикация | нигде, только у получателя | да |
| «онлайн» | presence соединений | Redis realtime | да |
| «был в 14:42» | отметка времени | Postgres | нет |

И presence считается сначала **по устройству, а не по пользователю**: у человека может быть открыт ноутбук и телефон, а один из них отвалиться. Статус пользователя — агрегат над соединениями, и правило агрегации это продуктовое решение.

## Несколько устройств

Кажется, что это про мобильные приложения, и поэтому откладывается. Но **два открытых браузера создают ту же задачу** уже в первой версии.

```
device_id      user_id        session_id
created_at     last_seen_at   user_agent
push_subscription             revoked_at
```
Сущность нужна сразу, потому что от неё зависят операции, которые придётся делать с первого дня: выйти на этом устройстве, выйти на всех, отозвать токены при смене пароля, показать список активных сессий.

## Ошибка в моей схеме: push для веба

APNs и FCM здесь не работают

В runtime-схеме офлайн-доставка описана как APNs/FCM. Но клиент первой версии — **веб**, а это другой механизм: Service Worker и подписка Web Push. APNs и FCM понадобятся тогда, когда появятся нативные приложения, и не раньше.

```
браузер → Service Worker → Web Push subscription → сервис уведомлений
```
Для первой версии есть честный выбор: либо сделать Web Push, либо прямо записать, что **офлайн-уведомлений в вебе пока нет**. Второе допустимо — недопустимо оставить в схеме APNs и считать, что вопрос закрыт.

## Вложения: конвейер целиком

```
клиент → POST /attachments/init → API → presigned URL
клиент ──────────────────────→ хранилище
                                   ↓ object.created
                                проверка типа, размера, антивирус
                                   ↓
                              attachment ready → сообщение ссылается
```
Состояния: `uploading` → `processing` → `ready`, плюс `rejected` и `failed`. Для голосовых сюда же извлечение длительности, для изображений — превью.

мелочь, которая быстро становится горой мусора

Пользователь загрузил фотографию и закрыл вкладку, не отправив сообщение. Объект остался в хранилище, ссылки на него нет ни у кого. Через месяц таких объектов тысячи, и отличить их от нужных уже нечем.

Поэтому у вложения с самого начала есть `attached_to_message_id` (может быть пустым) и `created_at`, а в расписании — уборка неприкреплённых старше суток.

## Поиск: не OpenSearch

В структуре репозитория есть `consumer-search`, но не было сказано, куда он пишет. Для первой версии ответ — **полнотекстовый поиск Postgres**.

```
v1      Postgres FTS
позже   Kafka → consumer-search → OpenSearch
```
OpenSearch для десяти миллионов пользователей логичен, но это ещё один распределённый кластер со своей эксплуатацией, отказоустойчивостью и стоимостью. Поднимать его до того, как поиск станет узким местом, — ровно та ошибка, от которой это ревью и предостерегает.

## Эксплуатационные пробелы

Самые часто забываемые компоненты — те, которых не видно в архитектуре, но без которых первая же жалоба превращается в поиск по пяти системам.

поддержка

### Админский интерфейс

Хотя бы внутренний. Найти пользователя, беседу, сообщение по идентификатору. Отключить пользователя, отозвать сессии. Посмотреть статус доставки, содержимое очереди неразобранного, повторить неудавшееся событие.

диагностика

### Трассировка сообщения

`/admin/messages/{id}/trace` — и весь путь с отметками времени: принято API, коммит, outbox, публикация в Kafka, получено потребителем, отдано в Centrifugo, подтверждено клиентом.

Основа для этого уже есть — сквозной `message_id`. Стоит дёшево, а отвечает на самый частый вопрос эксплуатации.

мониторинг

### Синтетический сценарий

Раз в минуту тестовый пользователь входит, открывает беседу и отправляет сообщение, а второй его получает. Метрика — время сквозной доставки.

Это важнее любой панели: система бывает полностью «зелёной», а сообщения при этом не доходят.

управление

### Флаги функций

`typing_enabled`, `presence_enabled`, `voice_enabled`, `attachments_enabled`, `search_enabled`, `push_enabled`.

Это и есть механизм плавной деградации из первой части: под нагрузкой гасим «печатает» **без выкатки**. Начать можно с таблицы настроек, а не с платформы управления флагами.

### Маршрутизация оповещений

Иначе десятки метрик превращаются в усталость от алертов. Каждому сигналу — свой адресат:

| Условие | Реакция |
| --- | --- |
| Возраст события в outbox > 5 мин | будить дежурного |
| Postgres недоступен | будить дежурного |
| Отставание потребителя Kafka | предупреждение, при росте — будить |
| Failover Redis | предупреждение |
| «Печатает» недоступно | не будить вообще |
| Отставание аналитики | задача в очередь, не инцидент |

И приоритеты подов планировщика должны повторять эту же лестницу: `PriorityClass` выше у API, Centrifugo и outbox, ниже у аналитики, поиска и фоновых потребителей. Тогда деградация из первой части существует не только на бумаге — при нехватке ресурсов планировщик вытеснит именно второстепенное.

## Веб-клиент: состояния соединения

`recovered=true/false` — недостаточно. Интерфейс должен различать:

```
CONNECTED     всё работает
CONNECTING    переподключаемся
DISCONNECTED  связи нет, показываем это честно
DEGRADED      сообщения идут, «печатает» отключено
SYNCING       восстановление не удалось, догружаем историю
```
```
ноутбук спал час → реконнект → recovered=false → SYNCING
                → GET messages?after_seq=X → CONNECTED
```
Пока идёт синхронизация, **нельзя показывать старое состояние как актуальное** — это самый заметный способ обмануть пользователя.

И проверять это надо на реальных сценариях браузера, а не только сквозными тестами: сон вкладки, сон ноутбука, фоновая вкладка, переход с Wi-Fi на мобильную сеть, офлайн и возвращение. Для мессенджера это важнее обычного HTTP-тестирования.

## Контракты и данные

контракты

### Три схемы рядом с кодом

```
packages/contracts/
  openapi.yaml    REST
  kafka/          события
  websocket/      realtime
```
Из OpenAPI генерируется клиент на TypeScript — тогда фронт и бэкенд не расходятся молча.

пагинация

### По ключу, не по смещению

```
GET /messages?before_seq=83721&limit=50
OFFSET 100000
```
На миллионах сообщений смещение линейно деградирует, и деградирует именно на старых беседах — то есть у самых лояльных пользователей.

хранение

### Политика срока жизни

Определить до первого прода: сообщения, удалённые сообщения, вложения, логи, события Kafka, очередь неразобранного, аудит. Иначе хранилище растёт без правил, и вопрос «почему счёт вырос» не имеет ответа.

приватность

### Удаление и выгрузка учётной записи

Данные размазаны по Postgres, хранилищу, retention Kafka, логам, поиску и кешам. Нужно понимать, где авторитетная копия и что физически удаляется — архитектурно, даже если юридическая сторона откладывается.

**Блокировка и жалобы — не «потом».** Публичный мессенджер без возможности заблокировать собеседника выпускать нельзя, а жалоба должна хотя бы доходить до человека — полноценная платформа модерации для этого не нужна.

И наоборот: биллинг, аудит, модерация и поиск уже присутствуют в схеме как потребители Kafka. Их *наличие в архитектуре* не означает, что они входят в первый релиз — шина спроектирована так, чтобы их можно было добавить, не трогая путь сообщения.

## Определение готовности версии 1

Не «все поды запущены». Семнадцать сквозных шагов, каждый проверяется целиком:

Два пользователя регистрируются и входят.

A создаёт беседу с B.

A видит, что B в сети.

B начинает печатать — A видит «печатает…».

B отправляет сообщение.

Оно сохранено, появилось у A в реальном времени, **не продублировалось**, прошло состояния `sent → delivered → read`.

A закрывает ноутбук.

B отправляет ещё одно сообщение.

A возвращается через час: переподключение, восстановление или догрузка — **ничего не потеряно**.

Пользователь отправляет изображение и голосовое.

A блокирует B — и B больше не может писать.

**Убиваем по очереди:** под API, под Centrifugo, primary Redis, брокер Kafka, целую зону доступности.

**Поведение соответствует заявленным SLO** — не «сервис поднялся», а измеренные RTO против обещанных.

Новый релиз проходит local → stage → prod **без единой ручной команды**.

Откат делается через `git revert`.

**По `message_id` можно восстановить весь путь доставки** с отметками времени.

**Из резервной копии разворачивается новое окружение**: чистая среда, восстановление базы и хранилища, выкатка, вход пользователя, открытие старой беседы.

Четыре выделенных шага — те, которые обычно не делают, и именно они отличают работающий продукт от набора запущенных сервисов. Последний особенно: «PITR настроен» и «из копии реально поднимается система» — разные утверждения, и второе проверяется только попыткой.

## Что это меняет в плане работ

Дальнейшая работа строится от этого списка, а не от перечня технологий. Практически:

- Ни одна новая распределённая система не добавляется, пока семнадцать шагов не проходят целиком.
- Порядок — по шагам, а не по компонентам: сначала 1–6 локально, затем 7–11, затем отказы и выкатка на stage.
- Шаги 12, 13, 16 и 17 планируются как *работа*, а не как «проверим в конце»: трассировка и восстановление из копии требуют кода и репетиций.

Отдельно про стоимость, раз стенд про неё: HA-архитектура в облаке дорожает не там, где ожидаешь. Основные статьи — шлюз NAT, управляемая Kafka, трафик между зонами и исходящий трафик медиа. Разметка по окружению, сервису и команде нужна с первого дня, иначе через месяц вопрос «почему счёт такой» останется без ответа.
